## 0. 结论速览

> **先读这一条**：第 10 章确立了「**无标签基线**」这一前提 —— 用户的实测复现是
> 「**没启用任何 Kratos 功能标签**，只把 Kratos 加进游戏，用 `Ctrl+Shift` 指挥**地面步兵**索敌前进就失同步」。
> 因此 §2 的 `JumpjetCarryall`（需喷气单位 + 吊运）与 §8.4 的「AE 浮点末位」（需挂 AE）**都无法解释该复现**，
> 已在 10.4 / 10.6 中修正。
>
> **第 11 章又用开源平台 Phobos 做了交叉验证，结论出现重要变化**：
> ① 「层序改动」从「P1 纪律」**升级为 P0 直接成因候选**。但必须先讲清两者的**真实关系**（详见 §12.1）：
> **Phobos 的 Attach Unit 源自 Kratos 的 Stand（经原作者亲自授权）**，「飞行单位上挂接物的分层」
> 这个**需求**也随之被继承过去；而 **KratosPP 是 DPKratos（C# 版）的 C++ 移植**，
> 本仓库的提交日期是**移植时间**、不是发明时间，**不能用来判断先后**。
> 因此 Phobos 在 0.4 记录 `Fixed a desync error caused by air/top layer sorting` 并回滚这件事，
> 性质不是「两个项目独立踩到同一个坑」，而是「**同一个需求的下游实现者在真实联机里吃到失同步后退役了它**」——
> 证据强度因此**上升**。
>
> **⚠️ 但「同需求」≠「同代码」（本轮 git 溯源新发现）**：Phobos 用的**不是** Kratos 这段 `0x55DBC3`
> （`git log --all -S "55DBC3"` 在 Phobos 仓库内**为空**），而是另一段 `0x4A9750`——
> 把 Air/Top 也交给引擎的**有序插入**。**两套不同代码、同一失败面** ⇒ 被否决的是**做法类别**，
> 覆盖面比上一版以为的更宽。详见 §11.1 附表与 §12.1「事实三」。
>
> ② **关键推论**：Phobos 退役时**只删掉了排序、完整保留了功能**（改成 `DisplayClass_Submit_Wrapper` 里
> 调 `UpdateAttachedAnimLayers`）⇒ **被否决的是「让 Air 层的顺序由 Y 排序键决定」这个做法，
> 不是 Stand / Attach Unit 这套功能本身**。
> 这也是 §12.5 方案 A 的依据。
> ③ Kratos 的 Stand 相关 Hook（层序 + 共享 FLH 都集中在此）是**无条件挂载**的 ——
> 这正好解释了「没有任何标签也会失同步」。④ `CrawlingFLH` 维持 P0，Phobos 的读侧写法可作修正参照。

## 1. 判定机制：YR 联机同步到底在比什么

先把「什么情况才会报丢失同步」钉死，后面的排查才有意义。

### 1.1 主循环

`sub_647260`（`Main_Loop`）每帧依次做三件事（反编译见 `ida_work/sync_fns_dump.txt:7-57`）：

```c
sub_64DAB0();                          // 1) 计算本帧同步校验值
dword_B04474[Frame] = dword_AC51FC;    // 2) 写入帧校验表（下标 = 当前帧号）
...
DoList(v4, indexInArray, 0, 0, 0);     // 3) 执行本帧命令流
```

### 1.2 校验值里到底装了什么 —— `sub_64DAB0`

反汇编见 `ida_work/sync_check_core.txt`。它把全局 `dword_AC51FC` 反复
「乘 2 再累加」，遍历下列对象集合：

| 集合 | 参与哈希的字段 |
| --- | --- |
| `inf_vec`（步兵） | `[obj+0x9C]`（坐标 X/Y/Z 中的 X、Y）+ `Desired_Facing256([obj+0x388])` 换算出的 8 向朝向 |
| `vec_Units`（载具） | 同上，另加 `[obj+0x3A0]`（炮塔朝向） |
| `vec_Buildings`（建筑） | 同上 |
| `vec_Houses`（阵营） | `[house+0x241]` 单字节（状态标志） |
| `vec_ObjectsInLayers` | 位置 `[obj+0x9C]` + 虚函数 `[vt+0x2C]` 的返回值 |
| `vec_Logics` | 同上 |
| —— | **`ScenarioClass->Random`（`Random2Class::operator()`）当次取值** |
| —— | `Frame & 0xFF` |

注意三点：

1. **X、Y 都被 `/10` 取整后再入哈希**（`imul 66666667h; sar edx,2`），所以位置抖动约 10 单位以内不会立刻被抓到；
   **Z 不参与**。
2. **朝向（步兵主朝向、载具主+炮塔朝向）是被直接比较的**。
3. **共享随机数流的当前值被直接混进校验值** —— 这是最关键的一条。

### 1.3 怎么判定「丢失同步」

`DoList` 里拿收到的网络包校验值和本地表比对（`sync_fns_dump.txt:562-592`）：

```c
if (NetworkPackets1[v17].ev.TimeStamp != Frame
 || dword_B04474[...] == NetworkPackets1[...].ev.CRC) { /* 正常 */ }
...
MsgBox(Get_String("TXT_OUT_OF_SYNC", ...), Get_String("TXT_STOP", ...), 0, 0, 0);
```

不相等就弹 **`TXT_OUT_OF_SYNC`（游戏失去同步）** 并停局。

### 1.4 由此得到的两条铁律

> **铁律 A**：任何在两端「消耗共享随机数（`ScenarioClass::Instance->Random`）
> 次数不同」的代码，都会在下一次校验时被判同步失败。
> 这是 YR 联机最经典的失同步机制。
>
> **铁律 B**：任何在两端「位置 / 步兵朝向 / 炮塔朝向」产生分歧的代码，同样会立刻失同步。

反过来说：**只要两端执行路径完全一致（输入、配置、调用次数都一致），
哪怕消耗共享随机数也是安全的**。所以问题不在「用没用共享随机数」，
而在「有没有让两端走上不同分支」。

## 2. P1 —— `JumpjetCarryall::CanLift` 使用本机玩家判定

### 2.1 代码

`src/Ext/TechnoType/JumpjetCarryall.cpp:74-80`

```cpp
bool JumpjetCarryall::CanLift(TechnoClass* pTarget, bool& toPayload)
{
    FootClass* pTargetFoot = abstract_cast<FootClass*>(pTarget);
    if (pTechno && pTargetFoot && pTechno != pTargetFoot
        && pTechno->Owner->IsControlledByCurrentPlayer()      // ← 问题所在
        && pTechno->Owner->IsAlliedWith(pTargetFoot->GetOwningHouse())
        && !pTargetFoot->ParasiteEatingMe && !pTargetFoot->IsIronCurtain()
        && !pTargetFoot->WarpingOut && !pTargetFoot->IsImmobilized && !pTargetFoot->IsAttackedByLocomotor)
```

### 2.2 `IsControlledByCurrentPlayer()` 在联机下是本机语义

`YRpp/HouseClass.h:460-466`：

```cpp
// Whether the human player on this computer can control this house.
bool IsControlledByCurrentPlayer() const {
    if (SessionClass::Instance->GameMode != GameMode::Campaign) {
        return this->IsCurrentPlayer();           // ← 联机走这里
    }
    return this->IsHumanPlayer || this->IsInPlayerControl;
}
```

`YRpp/HouseClass.h:692-695`：

```cpp
bool IsCurrentPlayer() const { return this == CurrentPlayer; }
```

即：**非战役（遭遇战 / 多人联机）下，`IsControlledByCurrentPlayer()` = `this == HouseClass::CurrentPlayer`，
是纯本机值。** 一台机器上只有自己阵营为真。

> 对比：同一个头文件里的 `IsControlledByHuman()`（`HouseClass.h:451-458`）在联机下只返回
> `IsHumanPlayer`，那是**所有客户端一致**的「这一方是否由人类操作」，是安全的。
> 两者语义完全不同，极易误用 —— 这正是本处的问题。

### 2.3 `CanLift` 的两个调用点，其中一个是每帧模拟路径

```
CanLift
├── (a) Hooks/UnitExtHook.cpp:629  0x74041B  UnitClass::What_Action(ObjectClass*)
│         └── 只有本机鼠标指向时才会执行 → 本机 UI，安全
└── (b) Hooks/UnitExtHook.cpp:676  0x7388FD  UnitClass::ClickedMission
          └── JumpjetCarryall::ActionClick → CanLift
```

对 (b) 做调用链核对（IDA 输出：`ida_work/carryall_resolve.txt`、
`ida_work/caller_area.txt`、`ida_work/carryall_disasm.txt`、`ida_work/vt_calls3.txt`）：

* `0x7388FD` 落在 `UnitClass_ClickedMission`（`0x738890-0x73890D`）。
  反汇编显示其签名为 `ClickedMission(Action act, ObjectClass* target, int)`，
  函数末尾 `push ebx / push edi / push ecx; mov ecx, esi; call FootClass_ClickedMission` ——
  Kratos 的 Hook 就读 `ECX=Action`、`ESI=this`、`EDI=pTarget`，读取位置**正确**。
* `UnitClass_ClickedMission` 只出现在**一个虚表槽**：`0x7F5DB4`（`.rdata`，偏移 `0x144`）。
* 全 `.text` 段中唯一对该槽的间接调用是
  `0x4DCA93  call dword ptr [edx+144h]  in FootClass_ExecutePlanningWaypoint`。
* `FootClass_ExecutePlanningWaypoint`（`0x4DC8C0-0x4DCE7A`）的调用者：
  * `AircraftClass_Mi_Move`
  * `AircraftClass_Mi_Patrol`
  * `FootClass_484`
  * **`FootClass_UpdatePosition`**  ← 每帧单位位置更新
  * `FootClass_ProceedToNextPlanningWaypoint`

也就是说 (b) 这条路径处在 **AI 任务 / 每帧位置更新** 里，**所有客户端都会执行**。

> 顺带说明：已知的另一个候选 `0x74041B UnitClass::What_Action(ObjectClass*)`（鼠标指针判定）
> 由 `BuildingClass_GetCursorOverObject`(0x447267)、`FootClass_GetCursorOverObject`(0x4DDEE2)、
> `BuildingClass_GetCursorOverCell`(0x447587)、`FootClass_GetCursor_MouseOverCell`(0x4DDDF9)
> 调用 —— 这些都是**本机光标**函数，只在本机执行，所以那一处用本机判定没有问题。

### 2.4 会发生什么

在 (b) 路径上，同一段代码在两端得到不同结果：

| | 载具所属方的客户端 | 其他客户端 |
| --- | --- | --- |
| `IsControlledByCurrentPlayer()` | `true` | `false` |
| `CanLift(...)` | `true` | `false` |
| `ActionClick(Tote, target)` 行为 | `StartMission()` → `SetDestination(cell,true)` + `QueueMission(Move,true)`，`_status = FLYTO` | 分支不成立；`action != Tote` 时还会走 `CancelMission()`，`_status` 被重置为 `READY/STOP`，`CarryallLanding = false` |

结果：**同一台吊运机在两端的目的地、任务、状态机、坐标全部不一致**。
而目的地 / 任务 / 坐标正是校验值和作者自带的 `SyncLogger` 都在盯的东西
（`SyncLogger` 专门埋了 `*_AssignDestination` / `*_OverrideMission` 采点），
下一帧比对即报 `TXT_OUT_OF_SYNC`。

* `StandEffect` 的两处在 `GuardCommandClass::Execute`(0x730D60) / `StopCommandClass::Execute`(0x730EA0) 里。

  因此只有按键那端生效 ⇒ 必须挪到同步路径（事件执行体或同步隧道）。
  > 注：与虚函数上方的 `VocClass_Play(RulesClass+720h/724h)` 一样，
  > 说明它同时也是「命令生效时播音效」的地方；但循环体本身是模拟逻辑。
  一旦 `pStand->IsSelected` 在两端不同，被下发的组件里若有
  `JumpjetCarryall::OnStopCommand → CancelMission()`、
  `AircraftGuard::OnStopCommand → CancelAreaGuard() + State = STOP`
  这类会写状态机/目的地的逻辑，就会产生分歧。

* `IsInPlayerControl` 在 `YRpp/HouseClass.h:773` 的注释为
  `// Is controlled by current player.`，同样是本机语义，请勿在模拟路径使用。

**建议**：这类判断统一改成两端一致的等价条件，或把判定整体上移到本机 UI 层

## 5. 已确认安全的项（不必改）

排查过程中同时验证了一批**曾经怀疑、实际安全**的点，记录在此以免重复劳动。

### 5.1 容器遍历序 —— 已按 UniqueID 排序，确定序

`YRpp/AbstractClass.h:143-145`：

```cpp
bool operator < (const AbstractClass &rhs) const {
    return this->UniqueID < rhs.UniqueID;
}
```

因此：

* `src/Ext/Helper/Finder.h:21` 的 `DereferenceLess`（`std::less<>()(*lhs, *rhs)`）对
  `TechnoClass*` 解引用后调用的就是上面这个 `operator<` → **按 UniqueID 排序**，
  与注释「按对象值（UniqueID）排序，保证多人同步安全」一致。
* `DistinctCollector<T> = std::set<T, DereferenceLess>` 的遍历顺序两端一致。
  使用点：`Finder.cpp:150,245,321,381,391`。
* `Ext/Extension/TechnoExt.h` 的 `TechnoClassLess`（`a->UniqueID < b->UniqueID`）同理；
  `StandArray` / `ImmuneStandArray` / `BaseUnitArray` / `BaseStandArray` 均为确定序。
* `std::map<Point2D,int>` / `std::map<int,...>` 等按值键的容器天然确定序。

### 5.2 `Container` / `ExtMap` 不参与顺序决策

`src/Utilities/Container.h:151` 的 `ContainerMapBase` 用
`std::unordered_map<const void*, void*>`，**理论上遍历序是稳定的**（同一进程内
插入序相同则桶序相同），但代码里：

* 所有 `ExtPointerOffset` 都被注释掉了（`Extension/*.h`），
  即 `HasOffset<T>` 为 false，`Find()` 走 `unordered_map::find`，**O(1) 查找**，
  与遍历顺序无关；
* 全工程**没有任何地方遍历 `ExtMap` 做逻辑决策**（已 grep 确认）。

### 5.3 `IsControlledByHuman()` 在联机下两端一致

`YRpp/HouseClass.h:451-458`：非战役下等于 `IsHumanPlayer`（来自多人玩家列表），
所有客户端一致。因此下列用法安全：

* `Ext/TechnoType/AircraftGuard.cpp:258`（`OnUpdate` 里的人类玩家门槛）

* `Ext/AnimType/AnimStand.cpp:40`、`Ext/EffectType/Effect/StandEffect.cpp:31`
* `Ext/Common/FireSuperManager.cpp:72`（`SuperClass::Launch(..., isPlayer)`）

### 5.4 `AnimClass::Invisible` 只影响绘制

`YRpp/AnimClass.h:113`：`bool Invisible; // don't draw, but Update state anyway`。
`Ext/AnimType/AnimStatus.cpp:162-176` 用本机的 `GetRelationWithPlayer(pAnim->Owner)`

## 8. 追加：「Ctrl+Shift + 左键」（移动攻击）失同步专项定位

> 触发条件（实测）：**开始游戏后 → 选中部队 → 按 `Ctrl+Shift` 点敌方位置 → 部队开始「索敌前进」→ 很快报「游戏失去同步」**。

### 8.1 指令确认

官方热键：`Ctrl+Shift+左键 = 移动攻击（Attack Move）` —— 部队在赶往目的地的途中**自动攻击所有进入警戒范围的敌军**（注意与 `Ctrl+Alt`（守卫指定点/区域防守）、`Ctrl`（强制开火）、`Alt`（强制移动）、`Shift`（路径点）区分）。
引擎侧对应 `Mission::AttackMove`；Kratos 自身也把它编号为 29（`Common/INI/INIBuffer.h:83`，映射表在同文件 `:122` 的 `"attackMove"`），与官方 `Mission` 枚举一致（该枚举里 `AreaGuard=11`、`Guard=5`，均已被 IDA 反编译交叉验证）。

含义：移动攻击会把单位**长期置于「持续重新索敌 + 边移动边开火」状态**，所以它恰好把「索敌判定」和「开火时机」这两条最敏感的链路同时拉满。

### 8.2 移动攻击真正踩到的引擎函数（IDA 实证）

| 地址 | 函数 | 作用 |
| --- | --- | --- |
| `0x6F8DF0`–`0x6F9DAF` | `TechnoClass::Greatest_Threat` | 自动索敌主逻辑；内部计算**扫描半径**并逐环扩展搜索候选格 |

### 8.3 关键发现：Kratos 恰好改写了「索敌半径」

`src/Hooks/TechnoExtHook.cpp:554`：

```cpp
DEFINE_HOOK(0x7012DF, TechnoClass_In_WeaponRange, 0x6)   // ← 名字叫 In_WeaponRange，
{                                                        //   实际位于 TechnoClass::GetWeaponRange 内
	GET(TechnoClass*, pTechno, ESI);
	GET(WeaponTypeClass*, pWeapon, EAX);
	int range = pWeapon->Range;
	AttachEffect* aeManager = nullptr;

	{

			return 0x7012E5;
		}

```

IDA 反汇编核对（**寄存器用法正确**，正是提交 `1d363d0「修复Range加成的错误地址」` 修好的结果）：

```
0x007012DD  mov  edx, [esi]
0x007012DF  mov  ebx, [eax+0B4h]   ; ← 被替换的原指令（6 字节）= WeaponType->Range
                                   ;   YRpp/WeaponTypeClass.h：Projectile 之后紧接 Range
0x007012E5  mov  ecx, esi          ; ← Hook 返回点
```

回归取值链：`call [eax+3F8h]`（GetWeaponStruct）→ `mov eax,[eax]`（取 `WeaponStruct.WeaponType`）→ `mov ebx,[eax+0B4h]`（取 Range）。**EAX 确实是 `WeaponTypeClass*`，`+0xB4` 确实是 `Range`，EBX 确实是返回值** —— Hook 成立。

同址还有一处在 `0x6F72E3`（位于 `TechnoClass_IsCloseEnoughToTarget` 内），写法相同，改的是 `R->EDI(range)`。

**⇒ 结论：因为 `GetWeaponRange` 就是 `Greatest_Threat` 的扫描半径来源，Kratos 注入的 AE 射程加成等价于「直接改写自动索敌半径」。这是「移动攻击」链路上 Kratos 唯一的直接干预点。**

### 8.4 为什么它能造成「移动攻击立刻失同步」

第 4 节的渲染随机数嫌疑已在 8.5 排除，因此只剩「索敌结果 / 开火时机」分歧。而下列三处都会把**浮点末位差异放大成整数差异**：

```cpp
// TechnoExtHook.cpp:554 / :594 —— 射程（leptons）
range = (int)(range * data.RangeMultiplier);      // double → int 截断
R->EBX(range);  /  R->EDI(range);

// TechnoExtHook.cpp:995 —— ROF（单位是「帧」！）
double rofMult = aem->CountAttachStatusMultiplier().ROFMultiplier;
R->EAX(rof * rofMult);                            // double → int 截断
```

而 `CountAttachStatusMultiplier()`（`src/Ext/ObjectType/AttachEffect.cpp:203`）是**用 `ForeachChild`（`std::vector<Component*>` 的**插入序**）对所有 AE 做浮点连乘**：

```cpp
multiplier.RangeMultiplier *= temp->AEData.CrateBuff.RangeMultiplier;   // 连乘
multiplier.RangeCell       += temp->AEData.CrateBuff.RangeCell;          // 累加
multiplier.ROFMultiplier   *= temp->AEData.CrateBuff.ROFMultiplier;
```

浮点乘法**不满足结合律**。只要两端 AE 的挂载顺序有任何差异（或某端多/少挂了一个「乘 1.0」的效果器使乘序不同），乘积末位就不同；再经 `(int)` 截断：

* **射程**：可能差 1 个 lepton → 扫描半径差 → **一台客户端的车会看到而另一台看不到某个目标** → 索敌结果分歧 → 目标/朝向/开火全部分歧 → 立即失同步；
* **ROF**：`rof` 本身就是帧数，差 1 就是**差一帧开火**，随后随机数消耗次数也错开。

> **⚠️ 本节（8.4）整体结论已在第 10 章修正，请以 §10.4 为准。**
>

### 8.8 修复建议（针对 8.4）

```cpp
// 1) 射程：可预期取整 + 按「格」量化，消除末位敏感
int delta  = (int)std::lround(data.RangeCell * (double)Unsorted::LeptonsPerCell);

// 2) ROF：先把倍率量化到 1e-6，再取整（rof 是帧数，差 1 就是差一帧）
double q = std::lround(rofMult * 1e6) / 1e6;
R->EAX((int)std::lround((double)rof * q));

// 3) AE 倍率聚合：固定乘序 + 量化（AttachEffect::CountAttachStatusMultiplier）
//    按 AE 类型名排序后再相乘；或每个倍率先 round 到 1e-6

### 10.1 Syringe 的返回语义（本轮实证，框架级）

这是本轮最重要的发现，它改变了对全部 430 个 Hook 的审计模型。

| 写法 | 实际语义 |
| --- | --- |
| `return 0;` | **先执行被替换的原始指令**，再从 `addr + size` 继续 |
| `return X;`（`X != 0`） | **跳过**被替换的原始指令，直接跳到 `X` |
| `R->REG(v); return 0;` | 寄存器写回发生在 Hook 体**之后**、**重放之前** ⇒ 若「被替换指令」也写同一个寄存器，**写回值会被重放覆盖**（该写回是死代码） |

**反证**：`0x55B719 LogicClass_Update_Late`（`src/Hooks/GeneralHook.cpp`）替换的是
`add esp,28h; retn`（字节 `83 C4 28 C3`）。
若 `return 0` 会「跳过」被替换指令，这个函数就永远回不去 ⇒ 只能是「先重放再继续」。
（该 Hook 体本身不 push，正体 `sub esp,28h` / `add esp,28h` 配对，栈平衡正确。）

* 对照 `YRpp/Interfaces.h` 的 `ILocomotion` 方法序（`IUnknown` 占 0–2，之后第 26 个方法）`In_Which_Layer` 恰好是**索引 29 = `0x74`**；IDA 也把 Walk 槽命名为 `LocomotionClass_ILocomotion_InWhichLayer`。
* 旁证：Jumpjet 版 `sub_54B8D0` 以 `mov esi, [esp+arg_0]` 取参数，随后 `mov ecx,[esi+8]` 并 `call [ecx+1C8h]`、再读 `[LinkedTo+8Ch]` / `[LinkedTo+9Ch]`（坐标）—— 因为 `ILocomotion*` 位于 `LocomotionClass` 实例 **+4** 处，`[esi+8]` 正好是 `LocomotionClass::LinkedTo`，完全自洽。

**（2）被 Hook 的函数体只有 8 字节：`mov eax, 2` + `retn 4`**

⇒ **原函数根本不写 `ESI`**；且 `retn 4` 说明它是 1 个栈参数的虚函数（参数 = locomotion 自身，用来拿 `LinkedTo`）。
所以 `GET(TechnoClass*, pTechno, ESI)` 读的是**调用者留在 ESI 里的值**。

**（3）调用者只有两个，且两者都在序言里把宿主放进 `ESI`**

```
0041ADC0  push    esi                     ; TechnoClass_InWhichLayer
0041ADC1  mov     esi, ecx                ; ★ ESI = 宿主单位
0041ADC3  mov     eax, [esi+674h]         ; = Locomotor
0041ADCB  jnz     short loc_41ADD7
0041ADD2  call    RaiseError
0041ADD7  mov     eax, [esi+674h]
0041ADDD  push    eax                     ; 栈参数 = locomotion 自身
0041ADDE  mov     ecx, [eax]
0041ADE0  call    dword ptr [ecx+74h]     ; → In_Which_Layer
```
`FootClass_InWhichLayer`（`0x4DB7E0`）结构完全相同（`push esi; mov esi, ecx; …; push eax; mov ecx,[eax]; call [ecx+74h]`）。
**⇒ 在这两个调用点上，`ESI` 就是宿主 `TechnoClass*`，`GET(…, ESI)` 成立。上一轮的怀疑排除。**

**（4）但它仍然「脆弱」，建议改造**

`GET(..., ESI)` 依赖「调用者恰好在 `ESI` 里放了宿主」这一**未文档化的调用惯例**。整个函数体并不保证这一点：
一旦引擎版本变化、或被别的 DLL 抢先 Hook 这两个调用点，返回值就会**随机化**（因为 `return 0x75C7E5` 是非 0，`R->EAX(layer)` 是唯一来源，没有任何兜底）。

建议改成显式取参 + `LinkedTo` 反查（与 `TechnoExtHook.cpp:1020` 的 `LocomotionClass_Update_Ramp` 写法保持一致）：

```cpp
DEFINE_HOOK(0x75C7E0, WalkLocomotionClass_In_Which_Layer, 0x5)
{
    // 该虚函数带 1 个栈参数 = locomotion 自身（vanilla 用它取 LinkedTo）
    GET_STACK(ILocomotion*, pLoco, 0x4);
    TechnoClass* pTechno = nullptr;
    if (pLoco)
    {
        if (auto pLocoClass = locomotion_cast<LocomotionClass*>(pLoco))
        {
            pTechno = abstract_cast<TechnoClass*>(pLocoClass->LinkedTo);
        }
    }
    // 拿不到宿主时，退回与 vanilla 完全一致的 mov eax, 2（Layer::Ground）
    R->EAX(pTechno ? (int)StandLayer::GetLayer(pTechno) : (int)Layer::Ground);
    return 0x75C7E5;
}
```
> `Layer` 枚举见 `YRpp/GeneralDefinitions.h:903`：`Ground = 2`，所以 `mov eax, 2` 就是 `Layer::Ground`。

### 10.4 四项结论修正

**修正 A —— `0x6F9039` 不是「无门控」，它对普通步兵的移动攻击**根本不会执行**。**

IDA 精确门控（`ida_work/gate_check.txt`）：

```
006F9024  push    ebp                      ; idxWeapon
006F9027  call    TechnoClass::Combat_Damage
006F902C  test    eax, eax
006F902E  jge     short loc_6F9042         ; ← 伤害 >= 0（普通武器）→ 跳过
006F9030  cmp     [esi+CurrentMission], 5
006F9037  jnz     short loc_6F9042         ; ← 不是 Mission::Guard(5) → 跳过
006F9039  mov     edi, 200h                ; ★ Kratos 的 Hook 点
006F903E  mov     [esp+6Ch+wanteddistance], edi
006F9042  mov     eax, edi
006F9044  cdq
006F9045  and     edx, 0FFh
006F904D  sar     eax, 8                   ; wanteddistance / 256 = 扫描半径（格）
```

⇒ 只有「单位的 `Combat_Damage(-1) < 0`（**负伤害 = 治疗/维修武器**）**且** `CurrentMission == Mission::Guard(5)`」时才走到 `0x6F9039`。
⇒ **普通步兵在 `Mission::AttackMove(29)` 下不会触发。** 第 8.4 节把它当作「对全体单位把索敌半径放大约 5 倍」的放大器，**推断不成立，应删除该论点**。
⇒ 另外，`wanteddistance` 的**正常**赋值来自 `[edx+31Ch]`（即 `GetWeaponRange`）；`mov edi, 200h` 只是这个「治疗武器」分支里的兜底常量。

**修正 B —— `0x6F9039` 也不应列入「移动攻击专项」**：它的意图（让带治疗武器的单位在 `Guard` 时够得到友军）是真实的，但与本次复现无关，建议**单独评估**，不要与移动攻击链混在一起。

**修正 C —— 第 8.4 节的「AE 浮点末位」只在**配置了 AE** 时才成立。**

无任何 AE 时，`CountAttachStatusMultiplier()` 的初值就是 `CrateBuffData` 的默认构造值：

```cpp
// src/Ext/EffectType/Effect/CrateBuffData.h:16-23

double ArmorMultiplier     = 1.0;
double SpeedMultiplier     = 1.0;
double ROFMultiplier       = 1.0;
bool   Cloakable           = false;
bool   ForceDecloak        = false;
double RangeMultiplier     = 1.0;
double RangeCell           = 0.0;
```

⇒ `(int)(range * 1.0) == range`、`rof * 1.0 == rof`，于是：

| 位置 | 无 AE 时的实际行为 |
| --- | --- |
| `0x7012DF`（`:554`） | 算出 `range == pWeapon->Range` ⇒ `if (range != pWeapon->Range)` 为假 ⇒ `return 0` 走原流程，**恒等** |
| `0x6F72E3`（`:594`） | `R->EDI(range)` 写回**同值**，`return 0` ⇒ **恒等**（无论 EDI 原本是什么，都被原样写回） |
| `0x6FF29E`（`:995`） | `R->EAX(rof * 1.0)` ⇒ **恒等** |

⇒ **第 8.4 节的机制无法解释「无标签」复现**，应降级为「**仅当配置了 AE 的射程/ROF 加成时才成立**」。

**修正 D —— `TechnoClass::Greatest_Threat` 内部没有任何随机数调用。**

对 `0x6F8DF0`–`0x6F9DAF` 全函数扫描 `Random` 相关指令：**命中 0 条**（`ida_work/key_checks.txt` §5）。
⇒ 「索敌半径变化 → 随机数消耗次数变化」这条链条**不成立**（目标选择结果当然会影响**之后**开火阶段的随机数消耗，但那要走「目标分歧 → 开火分歧」的间接链）。

风险点是**写法**：原版引擎也会改这三个字段（箱子类效果、引擎自身的倍率运算），

#### 10.6.2 「它写的是共享数据」—— IDA 实证

`TechnoClass::GetWeapon`（`0x70E140`，`ida_work/gate_check.txt`）：

```

0070E154  lea     ecx, [esi+Veterancy] ; call Veterancy_IsElite

`TechnoType_GetWeapon`（`0x7177C0`）：

```
007177C0  mov     eax, [esp+a2]                ; index
007177C4  lea     edx, ds:0[eax*8]
007177CB  sub     edx, eax                     ; edx = index * 7

```

⇒ **`GetWeapon(i)` 返回的是 `&TechnoTypeClass::Weapons[i]`**（步长 `7*4 = 0x1C = 28 = sizeof(WeaponStruct)`），
也就是**「类型级共享数据」，不是「实例级数据」**。精英分支指向同一类型的 `EliteWeapons` 数组（IDA `0x7177E0` 版本里可见 `+0A94h`）。

⇒ 于是 `CrawlingFLH::OnUpdate` 实际做的是：
**用一个单位的「实例状态」（`Veterancy.IsElite()`、`InfantryClass::Crawling`）+ 本机 `art(md).ini` 的值，
去覆写「该兵种全体共享」的 `WeaponStruct::FLH`。**

#### 10.6.3 为什么这很危险

1. **它把「某一发子弹从哪里出膛」变成了「本兵种最后一个被更新的那个步兵的状态」。**
   原版里 `WeaponStruct::FLH` 是**加载期一次性**写入的类型常量；Kratos 把它变成了每帧被重写的「最后写入者胜」变量 ——
   **这打破了「一个单位的射击只依赖它自己的状态」这个不变量。**
2. **FLH 直接决定枪口位置 → 子弹的出生坐标。** 而 `BulletClass` 是 `ObjectClass`，会被 `DisplayClass::Submit` 放进层数组；
   校验函数 `sub_64DAB0` 会遍历 `vec_ObjectsInLayers`，把每个对象的 `[+0x9C]`（X、Y）混进滚动哈希。
   ⇒ **枪口位置一旦不同，下一帧校验值就不同，立即报「游戏失去同步」。**
3. **FLH 的取值来自本机 Art INI**：

   ```cpp
   const char* section = pTechno->GetTechnoType()->ID;
   std::string image  = INI::GetSection(INI::Rules, section)->Get("Image", std::string{ section });
   _crawlingFLHData   = INI::GetConfig<CrawlingFLHData>(INI::Art, image.c_str())->Data;
   ```

   经 `Rules → Image=` 的**间接寻址**去取 `[Art]` 段。
   **只要两端的这一点点 INI 不同（`Image=` 指向不同段、`PrimaryFireFLH` 缺省、或一端用了别的 art 覆盖包），出膛位置就会系统性不同。**
   而普通步兵的 `PrimaryFireFLH` / `SecondaryFireFLH` 在 RA2/YR 的 `art(md).ini` 里**确实存在**
   （步兵的武器 FLH 就定义在这两个键上），所以这条路径**一定会被走到**。
4. `CrawlingFLHData` 的缺省是 `CoordStruct::Empty`（`CrawlingFLHData.h:11-18`）；
   `Read()` 虽做了「缺省回落到 `PrimaryFireFLH`」的兜底，但只要某端 `[Art]` 段里没有这些键、
   或 `Image=` 解析到的段不同，两端拿到的 FLH 就不同。

#### 10.6.4 与复现描述的吻合度

### 10.7 层数组顺序 = 校验值的一部分（必须守住的纪律）

**（1）校验函数按数组下标顺序做顺序敏感哈希**

```
0064DCFA  mov     edx, [ebp-0Ch]          ; 层数组基址
0064DCFD  mov     esi, [edx+edi*4]        ; arr[i]
0064DD1B  lea     edx, [esi+9Ch]          ; X, Y
0064DD2B  mov     edx, [esi]
0064DD31  call    dword ptr [edx+2Ch]     ; WhatAmI()
```
5 个层结构体位于 `0x8A0364 + k*0x18`（`k = 0..4`），遍历以 `0x8A03E8` 为终点；
每一项都是 `sum = sum*2 + value` 的**顺序敏感**累加。
⇒ **只要两个对象的相对顺序不同，校验值必然不同**，与它们的位置是否相同无关。

**（2）Kratos 会改变层内顺序的两条路径**

| 位置 | Kratos 代码 | 效果 |
| --- | --- | --- |
| `0x4DA87A FootClass_Update_UpdateLayer` | `StandExtHook.cpp:231` | `DisplayClass::Instance->Submit(pTechno)` —— 把对象**重新提交**进层（通常挪到数组尾部）；**每帧、每个 FootClass 都判一次** |
| `0x55DBC3 MainLoop_ShortLayerClass` | `StandExtHook.cpp:225` | `DisplayClass::GetLayer(Layer::Air)->Sort()` —— **每个主循环**给 Air 层排序 |

**（3）引擎的排序函数是「单趟冒泡」，无自愈能力**

`sub_551A30`（vanilla 在 `0x55DBC8` 调用它，Kratos 的 Hook 插在它**上一条指令** `0x55DBC3`）反汇编：

```
00551A37  mov     eax, [ebp+10h]            ; count
00551A3D  jle     short loc_551A81
00551A44  mov     esi, [eax+ebx*4+4]        ; arr[i+1]
00551A48  mov     edi, [eax+ebx*4]          ; arr[i]
00551A4F  call    dword ptr [edx+0B8h]      ; key(arr[i+1])
00551A5D  call    dword ptr [eax+0B8h]      ; key(arr[i])
00551A63  cmp     [esp+14h+var_4], eax
00551A67  jge     short loc_551A76          ; key(i+1) >= key(i) 不交换
```
比较键 = `obj->vt[0xB8]()`（即 YSort 一类）。**注意这里没有外层循环** —— 只做一趟相邻比较。
⇒ **给定同一输入序，结果是确定的**（同键不交换，行为稳定）；
但**一旦输入序分叉，排序不可能把两端重新拉回一致**。

**（4）纪律**

> **任何会调用 `DisplayClass::Submit` / `LayerClass::Sort` / 直接改层数组的改动，
> 都必须先证明它「在两端的输入序完全相同」；否则等价于直接改校验值。**

   都让「Air 层的数组顺序」由 **`Get_YSort()` 渲染坐标**决定。Phobos 用 B 做了实战检验并失败，
   ⇒ **被否决的是「做法的类别」，而不是某一段代码。**

2. **Phobos 的 B 与「§12.5 方案 B」是同一类做法。**
   因此 §12.5 的**方案 B 已被下游实战否决**（见 §12.5 的修正说明）。

3. **Phobos 最终选的是「定点重提交」（C），而不是任何形式的排序。**
   这是**原理层面**对 §12.5 方案 A 的最强背书：**需求方是谁，就修谁；不要动整层。**

> **一条同时成立的补充**：`0x54B8E9`（`JumpjetLocomotionClass_In_Which_Layer_Deviation`）两个项目
> **地址与 hook 名完全相同**，且在 Phobos 里是被 `86c0c2b7`（引入 B 的那次提交）判为「已过时」而删除的。
> 即：Phobos 在那次提交里同时做了「删掉逐帧/逐单位的层修补」+「换成按 Y 键排序」，**方向正好相反于它后来
> 在 `1cd953a2` 做的事** —— 一次完整的「试错 → 回退」闭环。

### 11.2 硬证据：层数组就是校验值的输入（本轮 IDA 闭环）

上一轮只能说「层数组顺序疑似参与校验」。本轮用 IDB 把这条链**逐字节闭环**了。

**(a) 原版只在 `DisplayClass::Submit` 里对 `layer == 2` 开启「有序插入」**

```
; 函数名：W?Submit$:DisplayClass$n(pnx$ObjectClass$$$LayerType$$)v  [004A9720-004A976D]
004A973D  call    dword ptr [eax+78h]        ; 取该对象自己的层
004A9740  mov     edi, eax
004A9747  cmp     edi, 2                     ;  2 == Layer::Ground
004A974A  lea     edx, [edi+edi*2]           ;  edx = layer * 3
004A974D  setz    cl                         ;  sortable = (layer == Ground)
004A9750  push    ecx; sortable              ; ← Phobos 当年替换的 9 字节起点
004A9751  push    esi; a2
004A9752  lea     ecx, [edx*8 + 0x008A0360]  ;  ← 原始字节 8D 0C D5 60 03 8A 00
004A9759  call    MapClass_AddObjectToALayerX
```

反汇编里的位移 `0x008A0360` 是**硬编码在机器码里**的（`8D 0C D5 60 03 8A 00`），
所以 `vec_ObjectsInLayers` 的层数组基址 = **`0x8A0360`**，步长 `edx*8 = layer*0x18` = **`0x18`**。
⇒ 层下标 `k` 的地址 = `0x8A0360 + k*0x18`。

**(b) `0x55DBC3` 传的参数 = 层下标 2 = `Layer::Ground`**

```
0055DBC3  mov     ecx, offset unk_8A0390      ; (0x8A0390 - 0x8A0360) / 0x18 = 2
0055DBC8  call    sub_551A30                  ; LayerClass::Sort
```

这与 Kratos 自己的注释「WWSB 只排序在地面的 layer，不排序在空中的 layer」**完全吻合**：
原版排的是 **Ground**（下标 2），Kratos 额外去排 **Air**（下标 3 = `0x8A03A8`）。

**(c) 同步校验函数 `sub_64DAB0` 逐层、按**下标顺序**遍历同一数组**

```
0064DCE4  mov     ebp, offset vec_ObjectsInLayers.length   ; &layer[0].Count
0064DCFA  mov     edx, [ebp-0Ch]                           ; layer[k].Items（= ebp-0xC = layer+4）
0064DCFD  mov     esi, [edx+edi*4]                         ; layer[k].Items[i]
...（对每个对象做 WhatAmI / 坐标 / 朝向 的滚动哈希）
0064DD79  mov     eax, [ebp+0]                             ; layer[k].Count
0064DD7C  inc     edi
0064DD83  jl      loc_64DCFA                               ; 内层：遍历本层全部对象
0064DD89  add     ebp, 18h                                 ; 外层：下一层（步长 0x18）
0064DD8C  cmp     ebp, offset dword_8A03E8
```

`ebp` 从 `0x8A0360 + 0x10 = 0x8A0370` 起步，每轮 `+0x18`，直到 `0x8A03E8`：
`(0x8A03E8 - 0x8A0370) / 0x18 = 5` ⇒ **正好 5 层（Underground / Surface / Ground / Air / Top）**。

**哈希是顺序敏感的**（`sum = sum*2 + value`），所以：

> `LayerClass::Sort` 重排的是 `vec_ObjectsInLayers[Air].Items` 的**下标顺序**，
> 而 `sub_64DAB0` **按下标顺序**把这些指针喂进滚动哈希。
> ⇒ **排序结果不同 = 校验值不同 = 失同步。**

**(d) `LayerClass::Sort` 的排序键依赖渲染坐标**

```
00551A4F  call    dword ptr [edx+0B8h]       ; 右元素的 vt[0xB8]()
00551A5D  call    dword ptr [eax+0B8h]       ; 左元素的 vt[0xB8]()
00551A63  cmp     [esp+14h+var_4], eax
00551A67  jge     short loc_551A76           ; 不换
00551A69  ...     swap [ecx+ebx*4+4] <-> [edx+ebx*4]
```

`vt[0xB8]` 解析为 `ObjectClass::ReturnRealYSort`（`0x5F6BD0-0x5F6C06`）：

```
005F6BDB  mov     eax, [esi]
005F6BE0  call    [eax+vt_..GetCoords_]      ; 取坐标 A
005F6BE8  mov     edi, eax
005F6BF1  call    [edx+vt_..GetCoords_]      ; 取坐标 B
005F6BF7  mov     ecx, [edi+4]               ; A.Y   ← Kratos 的 GetYSort Hook 落点
005F6BFA  mov     edx, [eax]                 ; B.X
005F6BFC  add     ecx, edx                   ; 返回 X + Y
```

⇒ **排序键 = 渲染坐标的 `X + Y`**（与 Kratos 源码注释一致）。
这同时解释了 **(e)**：Kratos 的 `ObjectClass_GetYSort`（`0x5F6BF7`，`StandExtHook.cpp:529`）
是**改排序键**，和 `Layer::Air->Sort()` 是**同一套机制的两端**，
两者叠加后 Air 层的顺序会被「替身从 Master 处取得的渲染坐标」决定 —— 这比 Phobos 当年的做法**更激进**。

### 11.5 Phobos 的「遍历无序容器」失同步教训 —— Kratos 经查是干净的

Phobos 修过一个和本项目容器结构**几乎同构**的失同步（提交 `b02a821a`）：

```cpp
// Fix a desync caused by interceptors —— src/Ext/Techno/Body.Update.cpp
- for (auto const& [pBullet, pBulletExt] : BulletExt::ExtMap)
+ // DO NOT iterate BulletExt::ExtMap here, the order of items is not deterministic
+ // so it can differ across players throwing target management out of sync.
+ for (auto const& pBullet : *BulletClass::Array())
```

Kratos 的 `Container` 底层同样是 `std::unordered_map`（`src/Utilities/Container.h:151`）
且暴露了 `begin()/end()`（`:493/:498`），所以本轮**专门复查**了 Kratos 是否也犯这个错。

**复查结论：Kratos 干净。** 全工程对 `Container::Items` 的遍历只有两处，
且都在**指针失效回调**里，结果与顺序无关：

```cpp
// src/Utilities/Container.h:328 / :339
void InvalidateExtDataPointer(void* const ptr) const
{ for (const auto& i : this->Items) i.second->InvalidatePointer(ptr); }   // 每个扩展只修自己的指针
void DetachExtDataPointer(void* const ptr, bool all) const
{ for (const auto& i : this->Items) i.second->Detach(ptr, all); }
```

其余容器也都是确定序的：

| 容器 | 底层 | 结论 |
| --- | --- | --- |
| `Container` / `ContainerMap` | `std::unordered_map` | **只被 `find` 使用**；仅有的两处遍历见上，序无关 ✅ |
| `Enumerable<T>::Array` | `std::vector` | 插入序确定 ✅ |
| `Component::_children` | `std::vector<Component*>` | 插入序确定；`Foreach` / `ForeachChild` 全走它 ✅ |
| `Component::_creatorMap` | `std::map<std::string, ...>` | 按 key 有序；且只用于创建 ✅ |

> 这一条**不是本次复现的成因**，但它是「同类平台踩过的坑」，值得留一条纪律：
> **任何 `unordered_map` 的遍历都不得参与模拟决策**。

### 11.7 更正：Phobos **有** Attach Unit（源自 Kratos 的 Stand），只是不叫 Stand

**本节修正上一版的一个错误结论。** 上一版据「Phobos 全源码（229 `.cpp` + 143 `.h`）中 `stand`
只作为 `standard` / `instance` / `stand-in` 出现」判定「Phobos 没有替身类功能、不存在对应实现」。
**这个判断是错的** —— 按关键字搜不到只是因为**命名不同**：这套功能在 Kratos 叫 **Stand**、
在 Phobos 叫 **Attach Unit**，而 **Attach Unit 的源头正是 Kratos 的 Stand（经原作者亲自授权）**。

更正后的事实对照：

| 项 | Kratos（含 DPKratos 原生实现） | Phobos（Attach Unit） |
| --- | --- | --- |
| Stand / Attach Unit 功能本体 | 有 | **有（源自 Kratos）** |
| Air / Top 层排序 | 有 · `0x55DBC3`（每帧 `Layer::Air->Sort()`） | **曾用另一段代码试过、0.4 已删除**（`0x4A9750`，把 Air/Top 交给有序插入） |
| 排序键 YSort 改写 | 有 · `0x5F6BF7` | 未见 |
| ZAdjust 改写 | 有 · `0x4DB091` | 未见 |
| 5 个 loco `In_Which_Layer` 覆写 | 有 | 未见 |

**这个更正让结论反而更干净、更强。** 既然 Phobos 继承的是同一套功能，
那它在 0.4 的处置就构成一次**受控对照实验**：

> Phobos **保住了功能、只拆掉了层排序** ⇒ 层排序**不是功能的必要条件**，
> 而是一个可以被替换的实现细节。**这正是 §12.5 方案 A 的立论基础，
> 也意味着「删掉 `Sort()` 会导致替身功能坏掉」这个担心基本可以排除。**
>
> **并且，Phobos 拆掉排序后用的替代方案（定点重提交）已经被它自己上线运行至今** ——
> 所以「替换掉排序」这条路不仅被证明**可行**，还被证明**够用**。

**原先那条「无实战背书」论点需要换一种表述** —— 它本身仍成立，但理由不同：
Kratos Stand 里那几处 Hook（`0x55DBC3` 排 Air 层、`0x5F6BF7` 改 YSort、`0x4DB091` 改 ZAdjust、
5 个 loco `In_Which_Layer`）**在 Phobos 侧要么从未出现、要么已被删除** ——
即这套「**实现细节**」在当前 Phobos 版本里并不运行。而它们在 Kratos 侧是**无条件挂载**的，
**这也解释了为什么「没有任何 Kratos 标签」照样会失同步**。

> **一条重要的方法论教训**（已记入 §11.10）：跨平台比对**不能只按关键字检索** ——
> 同一功能在两边可能用完全不同的名字（`Stand` vs `Attach Unit`）。
> 以后核对必须先确认**功能别名**（或直接查两边 changelog / 文档里的功能名），再比实现。

另附 Phobos 侧一处干净的层覆盖写法（与本议题无关，仅作风格参照）：

### 11.11 追加结论：链式加载顺序带来的「掐断」效应（Ares → Kratos → Phobos）

> 本节是 §11 的收尾，来自用户实测给出的**挂载顺序**：**Ares 先跑，然后 Kratos，最后 Phobos**。
> 这条顺序信息把「同址冲突」的性质从「多方和平共存」改成了「**先跑的可以把后面的踢掉**」，
> 直接影响**失同步排查的取证可信度**。逐条判定数据见 `ida_work/hook_chain.tsv`，
> 工具 `tools/analyze_hook_chain.py`，完整四档表见 `docs/Hook地址冲突清单.md` §10。

**11.11.1 机制**

同一地址上的多个 hook 是**链式**执行的：

- hook 体 `return 0` ⇒ **续链**（继续下一个 hook，或将控制权交回原指令重放）；
- hook 体 `return <非 0 地址>` ⇒ **立即跳转**，**整条链被掐断** —— 后面的 hook 与原始指令重放**全部跳过**。

配合给定顺序，谁能掐谁是一目了然的：

| 位置 | 返回非 0 时的后果 |
| --- | --- |
| **Ares**（最先） | Kratos **和** Phobos 在该地址**一起失效** |
| **Kratos**（居中） | **Phobos 失效**；Kratos 自己正常（它后面只剩 Phobos） |
| **Phobos**（最后） | 只是「跳过原指令」，无人可掐，行为正常 |

所以**风险方向是单向的**：Kratos 掐 Phobos、Ares 掐所有人；反过来不会。

**11.11.2 逐条判定结果（Kratos 与 Phobos 的共享地址）**

用 `tools/analyze_hook_chain.py` 抽出 Kratos 在每个共享地址上的**顶层 `return`**（已过滤 lambda 内的 `return`），分四档：

| 档位 | 处数 | 含义 |
| --- | --- | --- |
| **`ALLPATHS`（必定掐断）** | **30** | Kratos 体内**没有任何 `return 0`**，全路径跳走 ⇒ 该地址上 **Phobos 的 hook 永不执行** |
| `BRANCH`（条件掐断） | 14 | 既有非 0 又有 0，看分支/门控（如 `0x6FC339 CanFire` 只在 `DisableWeapon`/`ceaseFire` 时跳） |
| `ZERO`（安全） | 92 | 全 `return 0`，Phobos 正常接链 |
| 静态改写（不走链） | 8 | 5 处 `DEFINE_JUMP`（4 个 `DEFINE_JUMP` + 1 个 `DEFINE_FUNCTION_JUMP`）、2 处 `DEFINE_PATCH`，另有 1 处 Kratos 挂 `DEFINE_HOOK` 而 Phobos 写 `DEFINE_JUMP`（`0x6D481D`）。**方向相反**：后写的 **Phobos 覆盖 Kratos** |

**11.11.3 一个反直觉点：静态改写方向是反的**

`DEFINE_HOOK` 走 Syringe 链（先跑的掐后面的）；而 `DEFINE_JUMP` / `DEFINE_PATCH` 是**直接写字节、不与 Syringe 协商**。
既然 Phobos 后写，那么在这类地址上**是 Phobos 覆盖 Kratos**。典型如 `0x6D481D`
（Phobos `DEFINE_JUMP(LJMP, 0x6D481D, 0x6D482D)` vs Kratos `DEFINE_HOOK(0x6D481D, ..., 0x7)`）
—— 两者抢同一段内存，**谁后写谁生效，另一个被静默抹掉**。

**11.11.4 对失同步排查的三点影响**

1. **不能假设 Phobos 的失同步修复一定生效。** Phobos 官方修过的失同步若与 Kratos 同址且被掐断，
   「Phobos 修过的问题」在 `Ares + Kratos + Phobos` 组合下会**复现**。
   这条给「明明开了 Phobos 却没用」这类现象提供了机制解释。排查时凡涉及 Phobos 修复的项，
   先用 `ida_work/hook_chain.tsv` 查它是否同址、是否被掐。
2. **落在模拟路径上的掐断优先级最高**（会直接改变每帧模拟结果，可能进校验值）：
   `0x71A88D TemporalClass_Update`、`0x4690C1 BulletClass_Detonate`、`0x48A551 AnimList_SplashList`、
   `0x467E53 PreDetonation`、`0x6F348F WhatWeaponShouldIUse`。建议优先逐条读 Kratos 侧实现，
   确认它是否**完整复刻**了 Phobos 的同址逻辑（复刻不完全 = 行为分歧）。
3. **SyncLog 取证要留意**：`0x64736D Queue_AI_WriteDesyncLog` 是**同名同址**，Kratos 先跑并返回 `0x647372`
   ⇒ **Phobos 的 SyncLog 埋点永不执行**。实际只会得到 Kratos 的 `SYNC*.TXT`，
   不会有 Phobos `EnableMPSyncDebug` 的 `SYNC%d_%03d.TXT` —— 别误以为「日志没写就是没分歧」。

**11.11.5 两处「明知故犯」而非缺陷**

30 处 `ALLPATHS` 里，有 4 处是 Kratos **主动接管**（源码留下了明确标记），不算 bug，但属长期隐患：

| 地址 | Kratos hook | 依据 |
| --- | --- | --- |
| `0x4147F9` / `0x73C47A` | `AircraftClass_Draw_Shadow_SkipPhobos` / `UnitClass_DrawAsVXL_Shadow_SkipPhobos` | 名字即 `SkipPhobos`，开关 `AllowTakeoverPhobosShadowMaker` **默认 `true`**；**渲染路径，不影响同步** |
| `0x6F36DB` | `TechnoClass_SelectWeapon` | 源码注释：「Phobos 在此处对目标进行强制武器筛选，要兼容就得**复刻一套一样的逻辑**」 |
| `0x702299` | `TechnoClass_Destroy_VxlDebris_Remap` | 源码注释：「Phobos hook 这个地址，**要自己算随机数**」；开关 `AllowMakeVoxelDebrisByKratos` **默认 `true`**。同步性已核：两边都走 `ScenarioClass::Instance->Random`，**不会**造成两端消耗次数不同 |

⇒ 这类「**复刻型接管**」的风险是：Kratos 复刻的是**当时**的 Phobos 逻辑，
Phobos 一改两边就不一致，且不会报错。

**11.11.6 好消息**

Phobos 的 `DeploysIntoDesyncFix`（`0x73FEC1` / `0x47C640` / `0x7396D2`）**与 Kratos 无同址**
⇒ 该失同步修复**不会被掐断**，是可依赖的。

**11.11.7 Ares 侧无法静态枚举**

Ares 只有二进制、无源码，**无法静态列出**它在哪些地址返回非 0。
但方向已定：**Ares 返回非 0 的地址上 Kratos 与 Phobos 双双失效**。
这能解释「Kratos 某个 hook 写了却像没生效」；要确认只能**运行时打点**（在 hook 体首尾埋标志位）。

**11.11.8 建议的排查纪律（新增）**

> 在 `Ares + Kratos + Phobos` 组合下做任何「已修复」判断前，**先查同址与链序**：
> ① 该地址是否有多个写入者？② 先跑者是否 `return 0`？
> 工具：`python tools/analyze_hook_chain.py --kratos-src src --phobos-src <Phobos>/src --out-tsv ida_work/hook_chain.tsv`

本节信源：`ida_work/hook_chain.tsv`（判定数据）、`tools/analyze_hook_chain.py`（分析器）、
`docs/Hook地址冲突清单.md` §10（四档完整表 + 逐条分析）。

## 12. 处置建议：`Layer::Air->Sort()` 该怎么优雅地拿掉

> 本章回答一个具体问题：**Kratos 的 `Layer::Air->Sort()` 该怎么处理才优雅？**
> 结论是「照 Phobos 的思维方式退役它」——即**不用全局排序，改为直接维护那个不变量**，
> 并给出了一个**纯位置运算**的精准替代（§12.5 方案 A，反汇编已确认落点可行）。
>
> **⚠️ §12.1 先澄清一段容易被误解的源流**：Phobos 的 Attach Unit **源自** Kratos 的 Stand
> （经原作者授权），而 KratosPP 是 DPKratos（C# 版）的移植 ——
> 所以**不要用两个 C++ 仓库的 git 日期判断先后**。
> **同时也要注意反向的坑**：**不能因此就认定「Phobos 用的是同一段代码」** ——
> 本轮 git 逐仓库溯源证明，Phobos 那份**是另一段实现**（`0x4A9750`），见 §11.1 附表与 §12.1「事实三」。

### 12.1 先澄清源流：这个**需求**源自 Kratos，Phobos 是它的下游实现者

> **本节更正上一版结论。** 上一版写下「Phobos 比 KratosPP 早约 13 个月，因此是两个项目**独立**想到同一解法」。
> **这个结论是错的** —— 错在把 C++ 仓库的提交日期当成了发明时间。事实见下。

**事实一：Phobos 的 `Attach Unit` 源自 Kratos 的 `Stand`，经原作者亲自授权。**

**事实二：`KratosPP` 不是原生实现，而是 `DPKratos`（C# 版）的 C++ 移植。**

⇒ **这套手法的发明在 `DPKratos`（C#）**，而 `KratosPP` 仓库里的提交日期是**移植日期**。
拿 `KratosPP` 与 `Phobos` 两个 C++ 仓库的 git 日期比先后，**在方法上就是无效的** ——
被移植的实现天然晚于它的原生版本。**这不是「Phobos 更早」，而是「Kratos 的 C++ 移植版建仓更晚」。**

**事实三（本轮新增）：被继承的是「需求」，不是「代码」。**

用户授权的是**功能**（Stand → Attach Unit）以及随之而来的**需求**（「飞行单位上挂接物要能正确分层」）。
但**满足这个需求的具体实现，两边是各写各的** —— 本轮用 `git log --all -S "<地址>"` 逐仓库核查：

```
DPKratos (C#)  ── 发明 Stand 功能 + 「飞行单位上挂接物要分层」这个需求 ──┐
    │                                                                   │（原作者授权）
    └──移植──▶ KratosPP (C++)                                          ▼
    │                          Phobos Attach Unit（继承功能 + 继承需求）
    │                                                                   │
    │                     各自独立实现「层序修正」，代码互不相同：        │
    │                       • KratosPP : 0x55DBC3  每帧排整层 Air        │
    │                         （Phobos 仓库内搜不到这个地址）             │
    │                       • Phobos   : 0x4A9750  让 Air/Top 走有序插入  │
    │                         （KratosPP 仓库内搜不到这个地址）           │
    │                                             │                      │
    │                        0.4 真实联机实战 ▸ Phobos 那套吃到失同步     │
    │                                             ▼                      │
    │                                     删除排序，功能保留
    │                                     改用「定点重提交」（0x54B18E）
    ▼
（KratosPP 那套 0x55DBC3 至今仍在）
```

> **为什么这个区分必须写清楚**：如果误以为「Phobos 用的是同一段代码」，
> 就会得出「Phobos 只否决了它自己那份实现，跟 Kratos 这段无关」——
> 那结论就被削弱了。**事实相反**：两套代码**属于同一失败类别**（让 Air 层顺序由 `Get_YSort()` 决定），
> Phobos 的实战结果因此**同样命中 Kratos 这段**。**结论覆盖面变大，而不是变小。**

**事实四：`0x54B8E9` 是完全同址同名的共享代码。**

`JumpjetLocomotionClass_In_Which_Layer_Deviation`（`0x54B8E9`）在两个仓库里**地址与 hook 名一字不差**，
且 Phobos 是在 `86c0c2b7`（**引入** `0x4A9750` 排序的那次提交）里把它判为「已过时」删除的。
即 Phobos 走过一条完整闭环：

> 先**逐单位**修补喷气机层（`0x54B8E9`）→ 判其过时 → 改成**按 Y 键排序**（`0x4A9750`）→
> 排序吃到失同步 → 再回退成**定点重提交**（`0x54B18E`）。

**为什么这个更正让结论更硬，而不是更软：**

上一版的说法是「两个项目碰巧撞上同一个坑」—— 那只是**弱旁证**。更正后是：

> **Phobos 是「飞行单位上挂接物分层」这个需求的下游实现者。
> 它把需求接了过去、自己实现了一版、上线了、在真实联机环境里吃到失同步、然后连同实现一起退役了它。**

这是一次**有下游受众、有 issue 反馈、有明确替代方案的实战检验**，证据强度远高于「巧合」。
⇒ **§11.1 的结论不但成立，而且应当上调**（而且是**上调到做法类别**，不是上调到某一段代码）。

而且 `1cd953a2` 里**功能被完整保留**，只删掉了排序（见 §12.2）—— 这一点对 §12.5 的方案选择至关重要。

> **方法论教训**：跨仓库比较**不能只看 git 提交日期**，必须先确认**源代码流与移植关系**。
> 一个项目的 C++ 仓库建仓晚，不代表它的设计晚。

### 12.2 Phobos 的替代方案原文（这是唯一经过实战验证的解法）

退役时它一次性做了两件事：**删掉全局排序** + **改成在提交对象时把它挂接的东西一起放对层**。

```cpp
// Phobos src/Ext/Techno/Hooks.Misc.cpp（提交 1cd953a2 新增，沿用至今）

// Update attached anim layers after parent unit changes layer.
static void __fastcall DisplayClass_Submit_Wrapper(DisplayClass* pThis, void* _, ObjectClass* pObject)
{
    pThis->Submit(pObject);

    if (auto const pTechno = abstract_cast<TechnoClass*>(pObject))
        TechnoExt::UpdateAttachedAnimLayers(pTechno);   // ← 顺带把挂接动画重新提交到正确的层
}

DEFINE_FUNCTION_JUMP(CALL, 0x54B18E, DisplayClass_Submit_Wrapper);  // JumpjetLocomotionClass_Process
DEFINE_FUNCTION_JUMP(CALL, 0x4CD4E7, DisplayClass_Submit_Wrapper);  // FlyLocomotionClass_Update
```

同时**删除**（`src/Misc/Hooks.BugFixes.cpp`）：

```cpp
// Enable sorted add for Air/Top layers to fix issues with attached anims etc.
DEFINE_HOOK(0x4A9750, DisplayClass_Submit_LayerSort, 0x9)
{
    GET(Layer, layer, EDI);
    R->ECX(layer != Layer::Surface && layer != Layer::Underground);
    return 0;
}
```

**思路精髓**：它没有去"让排序变正确"，而是回头问「我到底要解决什么」——
需求方是**挂接动画放错层**，那就**只修那个动画**（`UpdateAttachedAnimLayers` 里逐个
`DisplayClass::Instance.Submit(pAnim)`，让动画跟着宿主进对层），而**不是排整层**。

⇒ **用一次"精准的、O(1) 的定位操作"，替掉了"每帧对整层做一次全局重排"。**

### 12.3 为什么「排整层」在结构上就是危险的

不管根因具体是哪一条，这个做法有三条**结构性**问题：

**(1) 它改的是模拟数据，不是渲染数据。**
`vec_ObjectsInLayers` 同时是**校验值的输入**（`sub_64DAB0` 按序遍历做顺序敏感哈希 `sum = sum*2 + value`）
和**渲染的输入**。任何改变下标的操作都同时改了「游戏状态」和「画面」—— 这是把渲染需求写进了模拟状态。

**(2) `LayerClass::Sort`（`sub_551A30`）只是单趟相邻冒泡，没有外层循环。**
本轮反汇编把比较规则也定死了：`jge → 跳过交换`，即 **升序、且等值不交换（稳定）**。
它**不是完整排序**，结果**依赖调用瞬间的初始顺序**，而且**没有自愈能力** ——
单趟冒泡只能把一个元素推到正确位置，全靠**每帧重复**收敛：一旦某帧两端顺序分叉，之后就一路错位。
（见 §10.7 的反汇编：`sub_551A30` 仅一趟。）

> **附注**：Kratos 的 `0x55DBC3` 是 `return 0`，会**重放** vanilla 的 `mov ecx, offset <Ground>`，
> 所以 vanilla 的 **Ground 排序本来就被保留了** —— Kratos 是**额外多排了一层 Air**（详见 §12.4 的机制表）。

**(3) Air 层里混着动画类对象 —— 它们的"存在性"可能带视觉层差异。**
`vec_ObjectsInLayers` 是 `ObjectClass*`，其中包含 `AnimClass`。
原版**故意不排 Air/Top 层**，本质是在**容忍**这类视觉层面的细微差异；
而一旦每帧排序，这些差异就被放大成**顺序差异**，顺序差异又直接变成**校验值差异**。
这正好呼应 §11.8 里 Phobos 的那条工程建议 ——
「SyncLog 要补 `AnimCreations` 埋点，因为层数组里含动画，动画创建顺序直接进校验值」。

> **一个可验证的推论**：如果这个假设成立，那么两端「排序前的 Air 层对象列表」应该能比出差异
>（同一帧、同一层，一端多/少一个对象，或顺序不同）。这是最直接的验证方式，见 §12.6 第 2 步。

**综上**：这不是「排序写错了」，而是「**排序这件事本身不该出现在这里**」。
它把一个**顺序敏感的哈希输入**交给了排序算法，而排序结果的对端一致性**没有任何保证机制**。

### 12.4 需求的精确表述：这条排序**确实在做事**，但它用错了工具

> **本节修正上一版的结论。** 上一版写过「Kratos 可能**根本不需要**这个排序」。
> 据作者确认，**这个判断是错的** —— 需求是真实存在的：
>
> **Stand 对象（`TechnoClass`）的构造晚于 Master。在 Aircraft / Jumpjet 上附加替身时，
> 必须让替身渲染在 Master 之上；否则它会被 Master 遮挡（渲染在 Master 下方）。**
> `Layer::Air->Sort()` 就是为这个目的而加的。

所以**需求必须保留**。但「需求真实」不等于「实现正确」——
关键在于：**这个需求真正要求的，是「两个特定对象的相对顺序」；
而当前实现动用的是「整层的全局重排」。**

先把需求翻译成精确的不变量：

> **不变量（Stand Drawing Order）**：在同一层数组里，**替身的下标必须大于其 Master 的下标**。
>
> **依据（本轮已由反汇编实证，不再是推测）**：层数组的**下标顺序就是绘制顺序**。
> `Tactical_Draw_All_6D8DB0`（`0x6D8DB0`）对每一层各做**一遍升序** `Items[0..Count-1]` 遍历，
> 后画的盖住先画的 ⇒ 下标越大越在上；层与层之间又是**整层 pass**。完整链路见 §12.4.1。

#### 本轮反汇编确认的完整机制链

| 环节 | 地址 | 事实（本轮逐字节确认） |
| --- | --- | --- |
| `Submit` 决定层 | `0x4A973D` `call [eax+78h]` | 层来自**对象自己的** `InWhichLayer()`；等于 `Layer::None` 则直接返回 |
| `sortable` 开关 | `0x4A9747` / `0x4A974D` | `sortable = (layer == 2 /* Ground */)` |
| 层插入原语 | `0x4A9759` → `LayerClass::AddObject` @ `0x5519B0` | **`sorted == false` ⇒ 纯追加**（`Items[Count++] = pObject`，见 `0x551A0A`）；**`sorted == true` ⇒ 调 `0x551A90`** |
| 有序插入算法 | `0x551A90` | **从下标 0 起线性扫描**，用 `ObjectClass::CompareYSortValues`（`0x5F6220`）判断，命中即**整体后移一格再插入**（**不是二分**） |
| 排序键 | `vt[0xB8]` → `ObjectClass::Get_YSort` @ `0x5F6BD0` | body = 调两次 `GetCoords()`（`vt+0xAC`）后返回 **`Y + X`**。**已确认 `0x5F6BD0` 就是各 ObjectClass 派生 vtable 的 `+0xB8` 槽**（本体 `+0xAC` 是 `GetCoords`） |
| Kratos 覆写 | `0x5F6BF7` | 替身的键 = `Master->GetRenderCoords()` ± `ZOffset` ⇒ **≈ Master 的键**（写入的是**栈上临时副本**，不污染真实渲染坐标） |
| 整层排序 | `0x55DBC3` → `LayerClass::Sort` @ `0x551A30` | **单趟**相邻冒泡、**升序**、**等值不交换**（`jge` 跳过交换） |

#### 这张表暴露了三个事实

**(a) 原版对 Air 层的插入是"纯追加"。**
`vec_ObjectsInLayers[Layer::Air]` 的顺序 = **提交顺序**。
原版**故意**不排序 Air 层（Kratos 的注释也承认这一点：「WWSB 只排序在地面的 layer，不排序在空中的 layer」）。

**(b) `Sort` 在等值时"不交换" ⇒ 它对「替身 vs Master」这对的相对顺序其实无能为力。**
只有当**替身的键严格大于 Master 的键**（即 `ZOffset > 0`）时，冒泡才会把替身往后推；
`ZOffset == 0` 时两者同键、**排序完全不动它们**；`ZOffset < 0` 时排序反而会把替身推到 Master **之前**。

> ⚠️ 这意味着 **`ZOffset` 的符号对当前实现的正确性是"隐式关键依赖"**，需要实测确认
> （建议先打印一次 Aircraft / Jumpjet 替身的 `MyStandData.ZOffset`）。
> 但无论符号是哪一种，结论都一样：**把正确性挂在一个偏移量的符号上是不稳的。**
>
> **并且，这个失败面已经被下游实测过一次。** Phobos 的 `0x4A9750`（把 Air/Top 交给同一套
> `Get_YSort()` 有序插入）在 0.4 上线后直接吃到失同步，被 `1cd953a2` 连同排序一起删除，
> changelog 原文 `Fixed a desync error caused by air/top layer sorting`。
> ⇒ **"让 Air 层顺序由 Y 排序键决定"这一整类做法，都有了实战负结果。**（详见 §11.1 附表）

**(c) 所以这条排序的真实作用是：`ZOffset > 0` 时，在数组顺序因任何原因被打乱之后，
把替身"重新推回" Master 之后。**

换句话说：**它在用一个"每帧的全局重排"，去修补一个"局部的相对顺序"。**

这就是工具错配 —— **要维护的不变量是局部的（两个对象之间），
动用的机制却是全局的、依赖渲染坐标的、且单趟无自愈能力的**。
它每帧都要跑，却只为了维持一个「替身紧跟在 Master 后面」的关系。

⇒ 结论：**不是"不要这个效果"，而是"换一个工具实现这个效果"。**

### 12.4.1 渲染路径实证（本轮 IDA 闭环）—— 层数组**就是**绘制列表

上一版只能引用 Kratos 自己的注释来论证"下标序 = 绘制序"。本轮把整条渲染路径反汇编到底，
**前提已从"推测"升级为"实证"**。

**完整链路（逐字节确认）**

```
W?Main_Loop$n()i  @0x55D360
  └─ GScreenClass_DrawOnTop @0x4F4480     （Main_Loop 内 3 处：0x55D84F / 0x55D8F2 / 0x55DBBE）
       └─ TacticalClass_Draw @0x6D3D10
            └─ Tactical_Draw_All_6D8DB0 @0x6D8DB0    ← ★ 层数组唯一的绘制消费者
```

**`Tactical_Draw_All_6D8DB0` 的内部结构：外层遍历 5 个层、内层**升序**遍历 `Items[]`、共两遍**

```asm
; ===== 第一遍：逐层 + 按下标升序，画主体 =====
006D8F19  lea  ebx, [eax+eax*2]                      ; eax = 层号
006D8F24  shl  ebx, 3                                ; ebx = 层号 * 0x18
006D8F2B  mov  ecx, vec_ObjectsInLayers.length[ebx]  ; Count = [基址 + 0x10 + ebx]
006D8F33  jle  loc_6D9427                             ; 空层 → 下一层
006D8F39  mov  eax, vec_ObjectsInLayers.data[ebx]    ; Items = [基址 + 0x04 + ebx]
006D8F43  mov  esi, [eax+ecx*4]                      ; ★ pObject = Items[i]   ← i 升序
          ... 视口裁剪 / 屏幕坐标换算 / 迷雾检查 ...
006D907E  mov  byte ptr [esi+99h], 1                 ; 标记「本帧已画」
006D9085  call dword ptr [edx+10Ch]
006D909E  call dword ptr [edx+104h]                  ; ★ 画主体
006D940C  mov  eax, [esp+100h+var_C8]                ; i
006D9410  mov  ecx, vec_ObjectsInLayers.length[ebx]  ; Count
006D9416  inc  eax
006D9417  cmp  eax, ecx
006D941D  jl   loc_6D8F39                            ; ← 下标递增
006D9427  cmp  eax, 2                                ; 层 == Ground(2)？
006D942A  jnz  loc_6D95A1
          ... Ground 层额外再遍历一遍 vec_Buildings ...
006D95A1  inc  eax
006D95A2  cmp  eax, 5                                ; 共 5 层
006D95A9  jl   loc_6D8F19                            ; ← 层递增

; ===== 第二遍：逐层 + 按下标升序，画 DrawExtras =====
006D95AF  mov  ecx, offset vec_ObjectsInLayers.data  ; 层游标 = &层[0].Items
006D95B8  mov  edx, [ecx+0Ch]                        ; Count
006D95CF  mov  ebx, [ecx+eax*4]                      ; pObject = Items[i]   ← i 升序
006D95D2  mov  al, [ebx+99h]                         ; 第一遍的「已画」标志
006D9789  call dword ptr [edx+110h]                  ; ★ vt+0x110 = TechnoClass::DrawExtras
006D97A8  add  ecx, 18h                              ; 层游标 += 0x18
006D97AB  cmp  ecx, (offset dbl_8A03D8+4)            ; == &层[5].Items  (= 基址 + 0x7C)
006D97B5  jl   loc_6D95B8
```

> **顺带被这条反汇编确认的两个布局事实**：`Items @ +0x04`、`Count @ +0x10`（与 `0x551A0A` 一致）；
> 层游标 `+0x18` 步进、终点 `基址+0x7C = &层[5].Items` ⇒ **数组确实是 5 × 0x18**。

**三条结论**

**(1) 层数组就是绘制列表，且下标顺序 = 绘制顺序（升序）。**
两遍遍历都是 `Items[0] → Items[Count-1]`，后画的盖住先画的
⇒ **`index(Stand) > index(Master)` 就是"替身画在 Master 之上"的充要条件。**

**(2) 层与层之间是整层 pass**（0→1→2→3→4 依次画完）
⇒ Air 层对象**必然**画在所有 Ground 层对象之上，与下标无关。

**(3) 渲染路径里没有任何"按对象的绘制优先级 / 排序"接口。**
这条路径中顺序的**唯一输入就是数组下标** —— 它既不读 `Get_YSort()`，也不读 `ZAdjust`。
⇒ **想在渲染侧实现"替身在上"，只有两条路**：
① **让数组下标本身就正确**（即：在 `Submit` 写入数组时决定）；或
② **劫持绘制循环**（改 `Items`/`Count` 的读取源，或"绘制前重排、绘制后恢复"）。

第 ② 条不可取：它会制造**"同一帧内数组有两种顺序"的窗口**，而**第二遍 `DrawExtras` 也依赖同一顺序**、
校验值又紧跟其后 —— 为了省掉一次插入时刻的 O(n) 位置运算，去换一个"窗口内一致性"的证明义务，
是明显的负收益。**故选第 ① 条（= §12.5 方案 A）。**

**层数组的全部消费者（Q1 全量 xref 扫描结果）**

| 角色 | 位置 | 读/写什么 |
| --- | --- | --- |
| **绘制** | `Tactical_Draw_All_6D8DB0` @`0x6D8DB0` | 5 层的 Items/Count，**两遍升序** |
| **联机校验值** | `sub_64DAB0` @`0x64DAB0`（游标 `0x8A0370 → 0x8A03E8`） | 5 层的 Items/Count，**顺序敏感哈希** |
| **写入点** | `DisplayClass::Submit` @`0x4A9720` / `Remove` @`0x4A9770` | 唯一的增/删 |
| 初始化 | `DisplayClass_InitClear`、`Init_DisplayClass`、`InitList_0762/0763/0770` | 建数组 / 清零 |
| 存档 | `Decode_Pointers`、`sub_4AE720` | 指针修复（只读+改指针值） |
| 查询（**只读，且只碰 Ground**） | `Encroach_Shadow/Fog`、`Reveal_The_Map` → `sub_4ADFF0`；`TacticalClass_Draw` 路径上的 `sub_6D97D0`/`sub_6D9920`/`sub_6D9A50`；`Goodie_Check` | 只读 `层[2]`（`0x8A0394`/`0x8A03A0`） |
| 只读扫描 | `sub_4AA2B0` / `sub_4AA380`（按虚函数谓词挑对象，不改数组） | 全 5 层，只读 |

⇒ **除"绘制"与"校验值"之外，没有任何其它代码消费 Air 层数组的"顺序"。**
⇒ **为渲染去改这个数组 = 直接改模拟状态。** 这是**结构性结论**，现在是实证而非推断。

**帧内时序 —— 把 Kratos 那条排序的位置钉死**

```
0x55DBBE  call GScreenClass_DrawOnTop    ; 画（消费层数组）
0x55DBC3  [Kratos 旧 Hook]               ; ← 旧实现：DisplayClass::GetLayer(Layer::Air)->Sort()
0x55DBC8  call LayerClass::Sort           ; vanilla 对 Ground（0x8A0390）排序
0x55DC9E  call LogicClass_Update          ; 模拟
0x55DE40  call sub_647260                 ; 命令流
             └─ 0x64731C call sub_64DAB0   ; ★ 校验值：按层数组顺序做哈希
```

⇒ **旧排序夹在"本帧绘制之后"与"本帧校验值之前"。**
它对本帧画面**已经没有任何作用**（绘制早了一步），却**必然进入本帧校验值**。
它"对画面有用"这一点，**完全依赖于"数组顺序会被保留到下一帧"** ——
也就是说：**它把"渲染需求"实现成了一个跨帧持久的模拟状态变更。**

**写入语义 —— 方案 A 正确性论证的最后一环**

| 操作 | 地址 | 语义 | 对 `index(Master) < index(Stand)` 的影响 |
| --- | --- | --- | --- |
| `LayerClass::AddObject`，`sorted == false`（**Air 层**） | `0x5519CF` → `0x551A0A` | **纯追加**：`Items[Count++] = pObject` | Master 被追加到队尾时**会破坏**它（替身已在前面）→ **由新 Hook 修正** |
| `LayerClass::AddObject`，`sorted == true`（Ground 层） | `0x551A90` | 从下标 0 起线性扫描插入 | 不涉及 Air |
| `DisplayClass::Remove` | `0x4A9770` | **整体前移**（`Items[i] = Items[i+1]`、`Count--`），**保序**（非"末位顶替"） | **不破坏** |
| `DisplayClass::Submit` | `0x4A9720` | 先 `Remove`（若已在某层）再 `AddObject` | 数组的**唯一**插入点 |

> **⇒ 结论：`index(Stand) > index(Master)` 只可能在"Master 被追加到队尾"这一种情况下失效，
> 而这正是新 Hook 唯一处理的情况。** 正确性论证至此完整闭环。

### 12.5 推荐方案：把「每帧整层排序」换成「提交时刻的定点校正」

#### 方案 A（推荐）：撤销 Air 整层排序，改为在提交后把替身定位到 Master 之后

**思路一句话：替身在层内的位置，不由"排序"决定，而由"Master 的位置"决定。**

**落点（本轮反汇编确认）**：`0x4A975E` —— `Submit` 里**层插入之后的第一条指令**。
此时 `ESI = pObject`、`EDI = layer` 都仍然有效：

```asm
004A9720  DisplayClass::Submit(ObjectClass* pObject)     ; esi = pObject
004A973D  call    dword ptr [eax+78h]                    ; InWhichLayer() → edi
004A9747  cmp     edi, 2                                 ; == Ground ?
004A974D  setz    cl                                     ; sortable
004A9759  call    LayerClass::AddObject                  ; ← 层插入（Air 层为纯追加）
004A975E  test    al, al                                 ; ★ 挂钩点：插入已完成，esi / edi 还活着
```

```cpp
// src/Hooks/StandExtHook.cpp:247  —— 以下是**已落地**的版本（与源码逐字一致）
// 撤销「每帧排 Air 层」，改为「提交时把替身定位到其 Master 之后」。
// 不变量：同层数组里 index(Stand) > index(Master) ⇒ 替身绘制在 Master 之上。
DEFINE_HOOK(0x4A975E, DisplayClass_Submit_KeepStandAboveMaster, 0x2)
{
	GET(ObjectClass*, pObject, ESI);
	GET(Layer, layer, EDI);

	// 只处理 Air 层：Ground 层由引擎自己的有序插入（sortable == true）负责，不动它。
	if (layer != Layer::Air)
		return 0;

	TechnoClass* pMaster = abstract_cast<TechnoClass*>(pObject);
	if (!pMaster)
		return 0;

	TechnoStatus* status = nullptr;
	if (!TryGetStatus<TechnoExt, TechnoStatus>(pMaster, status) || status->AmIStand())
		return 0;          // 替身自身被提交时不动作（防递归；它"追加到队尾"本来就是对的）

	LayerClass* pLayer = MapClass::GetLayer(Layer::Air);
	if (!pLayer || pLayer->Count < 2)
		return 0;

	if (pLayer->Items[pLayer->Count - 1] != pObject)
		return 0;          // Air 层是"追加"，刚插入的对象必然在队尾；否则不做任何假设

	// 把属于该 Master 的替身按原相对顺序搬到队尾（= Master 之后）。
	// 只移动指针，不改 Count / Capacity —— 与引擎自身的 Sort 做法一致，不触引擎簿记。
	// 注：该缓冲区只在单次调用内使用（入口 clear、用完即弃），不携带跨调用状态，
	//     与 StandYSort 那种"跨调用记忆"写法是两回事；本 Hook 不会重入自身。
	static std::vector<ObjectClass*> standBuf;
	standBuf.clear();

	const int count = pLayer->Count;
	int write = 0;
	for (int i = 0; i < count - 1; ++i)   // index (count-1) 是刚插入的 Master，保持不动
	{
		ObjectClass* pObj = pLayer->Items[i];
		TechnoClass* pTechno = abstract_cast<TechnoClass*>(pObj);

		TechnoStatus* standStatus = nullptr;
		if (pTechno && TryGetStatus<TechnoExt, TechnoStatus>(pTechno, standStatus)
			&& standStatus->AmIStand() && standStatus->pMyMaster == pMaster
			&& !standStatus->MyStandData.IsTrain)
		{
			standBuf.push_back(pObj);        // 待搬运的替身（保持原序）
		}
		else
		{
			pLayer->Items[write++] = pObj;   // 其余对象维持原相对顺序
		}
	}

	for (ObjectClass* pStand : standBuf)
		pLayer->Items[write++] = pStand;     // 追加到 Master 之后（下标必大于 Master）

	return 0;              // 重放 `test al, al`，继续 Submit 原逻辑
}
```

> **`0x2` 的由来**：`0x4A975E` 处是 `test al, al`（`84 C0`），正好 2 字节；
> `return 0` 会**重放**它（`al` 是重放上下文里 `AddObject` 的返回值，不会被 Hook 体污染），
> 然后从 `0x4A9760` 的 `jz` 继续。**落点已逐字节确认。**

> **冲突面已核查（本轮）**：`grep -rn "0x4A97" Phobos/src/` → **空**；
> `hook_conflict_new.tsv` 与 `hook_chain.tsv` 中 `4A97xx` 段**均无条目**。
> 即**当前** Ares/Kratos/Phobos 三方在该地址都没有 Hook。
> 唯一的历史邻居是 Phobos 已删除的 `0x4A9750`（长度 `0x9`，占 `0x4A9750–0x4A9758`）——
> 与 `0x4A975E` **相邻但不重叠**。（该 Hook 已删，不构成冲突。）

**同时删除**（✅ 本轮已删，原位于 `src/Hooks/StandExtHook.cpp:225`，现该行号已被新 Hook 占用）：

**方案 A 的收益不是"省掉一次排序"，而是把风险从代码里移除：**

| # | 论证 |
| --- | --- |
| 1 | **顺序判断不再依赖任何比较器**。运算只有"找下标 + 移位"，输入是「数组内容 + Master/替身关系」，输出是**纯函数**。 |
| 2 | **不再读取渲染坐标**。原实现把 `GetRenderCoords()` 拉进了"决定数组顺序"这条链；方案 A 完全不碰它。 |
| 3 | **只在"发生提交"时执行**，不是每帧。Air 层提交是低频事件（创建 / 换层），不构成每帧成本。 |
| 4 | **对层序的改动面最小**：只有**替身**被移动，其它对象严格保持 vanilla 的追加顺序。原实现是把**整个 Air 层**重排。 |

> 与失同步排查的关系：**它把"每帧重排一个校验值数组"这个最高风险动作，从代码里彻底移除了。**
> 校验值仍会与 vanilla 不同（替身被移位），但**两端必然一致** —— 与"原版对 Ground 层做有序插入"同理。

### 12.6 顺带清掉的死代码与隐患（本轮反汇编新发现）

**(1) `StandYSort` 的 4 个全局变量是死代码。**

`src/Hooks/StandExtHook.cpp:518-524` 的 `pSkip / pStand / X / Y` 被写成了"跨调用记忆"：

```cpp
if (pObject == StandYSort::pStand)     { *x = X;   *y = Y; }   // (1) 命中缓存
else if (pObject == StandYSort::pSkip) { /* 什么都不做 */ }      // (2) 纯 no-op
else { ... pStand = pObject; X = *x; Y = *y; }                  // (3) 写入缓存
```

但**排序路径上永远不会连续两次查询同一个对象**：`sub_551A30` 每次比较的是
`Items[i]` 与 `Items[i+1]` 两个**不同**对象；`0x551A90` 的比较是 `Items[i]` 与**新对象**。
⇒ 分支 (1) **永不命中**；而分支 (2)(3) 写入的值只被 (1) 读取 ⇒ **整组变量对结果零影响。**

**它是一个"有状态的比较器"的雏形 —— 留着只有风险（将来有人改动后可能真的命中），没有收益。可整组删除。**

> ✅ **2026-10-05 已整组删除**（用户点头，随 namespace 合并同一轮构建）。`0x5F6BF7` 现在只有一个
> `abstract_cast<TechnoClass*>` 分支 + 替身键改写，**无任何静态状态**；上面的代码块是清理前的快照，
> 原 `namespace StandYSort` 亦已并入 `StandLayer`。

**(2) `ObjectClass::GetYSort`（`0x5F6BF7`）的替身分支 —— 保留。**
Ground 层的替身仍依赖它（有序插入），尤其是"替身挂在建筑上时要画在建筑动画之上"
（`offset >= 0` 时加 `max(BuildingAnim[].YSort) + 16`）。方案 A 只撤销 Air 层排序，不影响这里。

**(3) `StandLayer::ZAdjust`（`0x4DB091`）的缓存 —— 建议单独评估，先不动。**
它是渲染路径（`GetZAdjustment`），不进校验值，风险等级低；但同样是"跨调用记忆"写法。
若 `FootClass::GetZAdjustment` 对同一对象确实会被连续调用，它才有意义。**为避免连带风险，本轮不处理。**

> **✅ 2026-10-05 已查（静态）—— 结论：不是死代码，与 §12.6(1) 相反。**
> `0x4DB091` 是 **`FootClass::GetZAdjustment`(`0x4DAFC0..0x4DB09F`) 的中段**（落点 = `mov ecx,[esp+8]` + `add eax,edi`，
> 恰两条整指令）；该函数被 4 张虚表引用、槽偏移恒为 **`+0x2EC`**
> （`??_7AircraftClass` / `??_7FootClass` / `??_7InfantryClass` / `??_7UnitClass`）。
> 函数体 = `TechnoClass::Get_ZAdjustment`(`0x704350`) + `max(Column/Tunnel/Cliff/Bridge 四个 ZFudge)` + locomotor `Z_Adjust`；
> hook 把后两项与 EAX 一起置零 ⇒ 等于**整体接管为"继承主身 ZAdjust"**。
> **槽 `+0x2EC` 的全部 10 个调用点**（`.text` 逐字节扫 `FF 9x EC 02 00 00`）全在渲染路径：
> `InfantryClass_Draw` / `SHPClass_Draw` / `TechnoClass_706ED0` / `TechnoClass_707280` / `sub_707480` /
> **`UnitClass_55C`(`0x73B140`) × 3** / `UnitClass_DrawSHP` / `UnitClass_DrawAt`。
> **关键**：`UnitClass_55C` 在**同一函数内对同一个 `this` 连调 3 次**（`0x73B33F`/`0x73B3B4`/`0x73B414`，
> 均为 `mov ecx,esi; call [reg+2ECh]`），两次之间只夹一个 `sub_4373B0`，而**该槽调用点表里没有它**
> ⇒ 第 2、3 次调用**必然命中 `pTechno == pStand` 分支** ⇒ 缓存是活的。
> 顺带把 `pSkip` 的作用定死了：branch(2) 与 branch(3)-else 行为**完全相同**（都是 `return 0` 走 vanilla），
> 差别只在状态写入 ⇒ **`pSkip` 存在的唯一意义就是"别让别的对象把 `pStand` 清掉"**，整套变量都为 branch(1) 服务。
> **但"命中"≠"必要" —— 差异的方向必须看清楚**：这里的差异是**缓存自己会返回过期值**，
> 而不是"缓存提供了删不得的服务"。
> ① **全部 10 个调用点都在绘制路径**（名称实证）：`InfantryClass_Draw` / `SHPClass_Draw` / `UnitClass_DrawSHP` /
> `UnitClass_DrawAt` / `UnitClass_55C`（UnitClass 虚表槽 `0x7F61CC`）/ `TechnoClass_706ED0`、`TechnoClass_707280`、
> `sub_707480` —— 后三者的唯一调用者分别是 `TechnoClass::Remap_Table`（调色板重映射）与 `VXL_DrawShadow`。
> 而绘制阶段在 `LogicClass_Update` **之前**、期间没有任何逻辑写入 ⇒ **同帧内缓存值 ≡ 现算值**，
> 连"`UnitClass_55C` 三次调用必须一致"这件事也**不依赖缓存**（输入同帧恒等）。
> ② 命中分支**只返回缓存、不刷新缓存**（`R->EAX(zAdjust)`，分支内无任何写入）⇒ 一旦同一对象被连续查询，
> 它会一直使用**上一次 miss 时**算出的值。
> ⇒ **可证推论**：若画面上**只有一个 FootClass** 在走这条槽（其余都是建筑/动画），`pStand` 永远是它自己
> ⇒ 从第二次调用起全部命中 ⇒ 该对象的 ZAdjust **只在首次算过一次、之后长期冻结**（不是"迟 1 帧"），
> 直到另一个 FootClass 来查询才刷新。Z 变化小的地面单位看不出来；**空中/升降中的单位会表现为替身纵向偏移不跟随**。
> 纯视觉、不进校验值 ⇒ **不是失同步源**。
> ⇒ **处置：已删缓存、留 hook（2026-10-05，用户拍板）** —— fresh 值在任何情况下都不比 stale 值差；缓存唯一买到的是
> 每单位每帧少算 2 次（几次乘法 + 4 个 `ZFudge` 读取 + 一次对主身的虚调用/递归），量级可忽略，
> 而代价是**查询函数非纯**（与本项目"被引擎反复询问的函数必须纯"的纪律冲突）。
> **源码现状**：`0x4DB091` 的 hook 内**已无任何静态状态** —— 原三分支（命中/跳过/计算）塌缩为
> "是替身 ⇒ 现算并把 `EDI`/`[esp+8]` 置零后写 EAX；否则什么都不做"，`namespace StandZAdjust` 随之整块删除。
> 它当初的来历（为什么会有这条缓存）见 `2026-10-05.md` §24.3 的 git 考古：`584c49e`(2024-03-31) 引入、
> `f998f66`(2024-04-02) 因"非替身被误缓存导致地形/桥/悬崖 Z 错位"而收窄为"只缓存替身"。
> 信源：`ida_work/probe_zadjust.py`、`probe_zadjust_ida.py`、`probe_zadjust_callsites.py`、`probe_zadjust_hosts.py`
> 及 `zadjust_ida_report.txt`、`zadjust_callsites_report.txt`、`zadjust_hosts_report.txt`。

### 12.8 一句话总结

> **不是"不要这个效果"，而是"换一个工具"。**
>
> 需求是「替身绘制在 Master 之上」，它是一个**局部不变量**：`index(Stand) > index(Master)`。
> 原实现却动用**每帧的整层重排**去维护它，而这条排序：
> ① **等值不交换**，所以**只在 `ZOffset > 0` 时才真的在保护这对关系** —— 正确性挂在一个偏移量的符号上；
> ② 把**整个 Air 层**（`vec_ObjectsInLayers` 是**校验值的输入**）的顺序，交给一个
> **依赖渲染坐标**、且**单趟无自愈**的排序。
>
> 正确做法就是**直接维护那个不变量**：在层插入之后（`0x4A975E`）把替身定位到其 Master 之后。
> 一步纯位置运算 —— **不依赖比较器、不依赖渲染坐标、不依赖提交顺序，且幂等。**
>
> 根本原则：**任何改变 `vec_ObjectsInLayers` 下标的操作，都不应出现在模拟阶段；
> 若不得不出现在模拟阶段，也必须让它只依赖"模拟状态"，而不是"渲染状态"。**

### 13.1 崩溃**就是**本次新增 hook 引起的（★ 2026-10-04 23:40 更正，v1 结论作废）

### 13.2 `DisplayClass::Submit` 全文语义（`0x4A9720`，**本轮确证**）

```
if (obj->LastLayer(+0x94) != -1)  Remove(obj);          // 0x4A9734
layer = obj->InWhichLayer();                             // 0x4A973D  call [eax+78h]
if (layer == -1) return;                                 // 0x4A9745
AddObject(&vec_ObjectsInLayers[layer], obj,              // 0x4A9759  MapClass_AddObjectToALayerX
          sortable = (layer == 2 /*Ground*/));           // 0x4A974D  setz cl
if (ok) obj->LastLayer = layer;                          // 0x4A9762  mov [esi+94h], edi
```

- **`Submit` 是"移动"**（先 `Remove` 再 `AddObject`），**不产生重复条目**，但会改变对象在数组中的**下标**；
  只有 `Ground(2)` 是 `sortable=true`，**其余层一律追加到队尾 ⇒ 顺序即提交顺序**。
- **`LayerClass` 索引确证**：`&vec_ObjectsInLayers[layer] = layer*0x18 + 0x8A0360`（`lea [edx*8+0x8A0360]`，`edx = layer*3`）。

### 13.3 ⚠️ 偏移更正：`+0x90` = `IsAlive`，`+0x94` = `LastLayer`

**本条更正推翻了一个长期误读。** 依据：

- `ObjectClass_DTOR`(`0x5F3D26`)、`AircraftClass_DTOR`(`0x4141FC/0x41426F`)、`BuildingClass_DTOR`(`0x43C02E`)、
  `InfantryClass_DTOR`(`0x517F83`)、`ObjectClass::Detach`(`0x5F6625`) 全是 `mov byte ptr [obj+90h], 0` ⇒ **`+0x90` 是布尔 `IsAlive`**。
- `Submit` 在插入成功后 `mov [esi+94h], edi`（新层号）⇒ **`+0x94` 是 `LastLayer`**（`YRpp/ObjectClass.h` 中 `IsAlive` 后的 `align_91[0x3]` 正对得上）。
- 因此 `FootClass::AI` 的 `0x4DA53E` / `0x4DA87A` 处 `cmp [esi+90h], bl` + `jz loc_4DAF00` 是 **`IsAlive` 守卫**，**不是 `LastLayer` 比较**。

`StandExtHook.cpp:332` 的 hook 名 `FootClass_Update_UpdateLayer` 亦建立在该误读之上。

### 13.4 新发现 A（P0）：`InWhichLayer()` 被从"纯常量函数"替换为"有状态函数"

**引擎原版**（`0x75C7E0` / `0x6A3E50` / `0x4B4820`，**三个 locomotor 字节完全相同**）：

```asm
B8 02 00 00 00   mov eax, 2      ; Layer::Ground —— 常量，不读内存、无副作用
C2 04 00         retn 4
```

**Kratos 的替换**（`StandExtHook.cpp:656` 起，共 5 处：Walk/Ship/Mech/Hover/Drive）：

```cpp

R->EAX(StandLayer::GetLayer(pTechno));   // 依赖 IsInAir() + 单槽静态缓存 pStand/layer
return 0x75C7E5;                          // 跳过原 mov eax,2
```

**危害**：`InWhichLayer()` 从**纯函数**变成**依赖运行期状态**（`IsInAir()`、缓存命中历史）的函数，
而它在**逻辑帧内**被反复调用（`ObjectClass::Update` 的层变更判断、渲染分层、射界判断…）。
任何一次 `IsInAir()` 瞬时为 `true`（桥上 / 被举升 / 倒地过渡 / 浮点误差）
⇒ 返回 `Air(3)` 而 `LastLayer` 仍是 `Ground(2)` ⇒ **不等 ⇒ `Submit`** ⇒ 对象被搬进 Air 层。
两客户端缓存命中时机不同（如视野内/外导致渲染调用次数不同）⇒ **一边 Submit 一边不 Submit ⇒ 失同步**。

> **这精确对应"地面步兵 + `Ctrl+Shift` 索敌 + 很快失同步"**：步兵用 `WalkLoco`（正是被替换之一），
> 索敌会大幅提高 `IsInAir()`/`InWhichLayer()` 的调用频次 ⇒ 抖动概率放大。
> 且这 5 条 hook **没有任何功能开关**，与"未启用任何功能标签也失同步"吻合。

### 13.8 ★ Syringe 落点契约（本轮最重要的引擎事实，**新增**）

**信源**：`D:\Workspace\ra2mod\platform\SyringeEx\SyringeDebugger.cpp:529-640`（实现）、
`D:\Workspace\ra2mod\platform\Antares\`（Ares 逆向源码，用法范例）。

| 规则 | 内容 |
| --- | --- |
| **R1** | 原码被覆盖长度 = **`max(声明的 size, 5)`**（jmp 固定 5 字节 `E9 rel32`，尾部 `nop` 补齐） |
| **R2** | `return 0` ⇒ 只重放**声明的 size** 字节，之后**无条件跳到 `addr + 5`** |
| **R3** | 覆盖区间含相对跳转（`Jcc`/`JMP`/`CALL`）时，搬迁到 trampoline 后偏移失效；只有 SyringeEx 的 `ReladdrInstructionFixup` 会修，**老版 Syringe 不修** |

**推论（决定了 hook 该怎么写）**

1. **`size >= 5`** 且覆盖**完整指令** ⇒ `return 0` 安全。
2. **`size < 5`** ⇒ `return 0` **不安全**（会落 `addr+5` 的指令中间），除非**重放块自身以 `retn`/`ret`/`jmp` 收尾**（控制流直接离开函数，`addr+5` 用不到）。
   > 这正是 Kratos/Phobos/Ares 里所有 <5 字节 hook **清一色落在 `retn` 上**的原因。
3. **`size < 5` 的另一条合法写法**：**不 `return 0`**，改为 `return` 一个**显式继续地址**。
   - Ares 范例：`Antares/src/Misc/Debug.cpp:295` `DEFINE_HOOK(0x4068E0, Debug_Log, 0x1)` → `return 0x4A4AF9;`
   - Kratos 自身亦有：`src/Hooks/LaserDrawHook.cpp:26` `size=0x0` → `return 0x550F9D;`

**全量审计结果（`ida_work/hooksize_audit.py` → `hooksize_audit.txt`，452 条）**

| 类别 | 条数 |
| --- | --- |
| **`BAD` 违反落点契约** | **0**（修复前 `0x4A975E` 稳定命中；修复后归零） |
| `size < 5` 但合法 | 8（7 条靠 `retn` 收尾 + 1 条显式返回） |
| `WARN` 覆盖区间含相对跳转且 handler 会 `return 0` | 21（**上游既存**，见 §13.7 待办） |

**本次修复**

```cpp
// 0x4A9768: 5F         pop edi    (1 字节)
// 0x4A9769: 5E         pop esi    (1 字节)
// 0x4A976A: C2 04 00   retn 4     (3 字节)   ⇒ 恰 5 字节 / 3 条完整指令 / 无相对跳转
DEFINE_HOOK(0x4A9768, DisplayClass_Submit_KeepStandAboveMaster, 0x5)
```

同时给 handler 加了 `pObject == nullptr` 前置判断（`Submit` 有若干早退分支同样汇合到该出口），
并移除已无使用点的 `#include <vector>`。
产物已确认：`Kratos.dll` 的 `.syhks00` 段内出现 `addr=0x004A9768 size=0x5`。

**教训（供以后所有 hook 复核）**：
> 写 hook 前先 `objdump`/IDA 看**落点那条指令**：
> ① 它是不是 `retn`？② 声明 size 是否 ≥5 且覆盖完整指令？③ 覆盖区间里有没有相对跳转？
> ④ handler 到底 `return 0` 还是返回显式地址？**四个问题缺一个都可能写出"能编译、能加载、开局就崩"的 hook。**

| 层 | 插入 | 每帧排序 | 顺序由谁决定 |
| --- | --- | --- | --- |
| Ground(2) | 有序插入（YSort） | 有（单趟） | 引擎 |
| Surface/Air/Top/Underground | **纯追加队尾** | **无** | **插入顺序（Kratos Hook）** |

### 14.2 `Stand.ZOffset` 只对 Ground 层替身有效

`ObjectClass::GetYSort`(`0x5F6BD0`，= `coords.X + coords.Y`) 的全部消费者：
`0x422BC3`(AnimClass)、`0x449413`(BuildingClass)，以及 `LayerClass::Sort`(`0x551A4F`/`0x551A5D`)
与有序插入(`0x551ADB`) 的 `vt[0xB8]` 间接调用 —— **全部在 Ground 路径上**。

⇒ 挂在 Jumpjet 上的替身（Air 层）**从不参与任何排序**，
`Stand.ZOffset` 对它原本完全失效（正负都一样）。这是上一版改动的功能回退，本轮已补。

### 14.3 修掉一个方向性 bug

上一版 `0x4A9768` 的实现是"把本 Master 的替身稳定搬到 `[0, count-1)` 的末尾"：

```
[ S1, A, B, S2, Master ]  →  [ A, B, S1, S2, Master ]    替身下标 2,3 < Master 下标 4
```
与函数名 `KeepStandAboveMaster` 及注释（"所有替身的下标都大于其 Master"）**恰好相反** ——
按绘制规则会把替身排到 Master **下面**。之所以此前未暴露：该 Hook 只在"非替身 Techno 被提交进
Air 层"时动作，而 Jumpjet 的重提交在 `JumpjetLocomotionClass_Process`(`0x54B18E`，带状态变化守卫)，
平时不触发；一旦宿主换层重提交就会把替身压到下面。

**新实现**（只在 `layer == Air` 且对象是 Techno 时动作；只搬指针，O(1) 额外空间、无静态状态）：

```
R1 入队的是替身：ZOffset >= 0 → 不动（队尾天然在上）；ZOffset < 0 → 左移到 Master 之前
R2 入队的是 Master：对 [0,count-1) 稳定三分类 A / D(Z<0 替身) / U(Z>=0 替身)，
                    再把 Master 左移到"第一件 U 之前" ⇒ [ A..., D..., Master, U... ]
```
非 Techno（动画/子弹）直接返回 ⇒ **AE 动画不受本 Hook 影响**。

### 14.4 AE 附加动画被 Jumpjet 遮挡的归属

vanilla `AnimClass::InWhichLayer`(`0x424CB0`)：
```
mov eax,[ecx+0CCh]  ; AnimClass::OwnerObject（+0xCC，由 Attach_To 的 0x424C37 mov [esi+0CCh],edi 写入）
test eax,eax / jz → 否则 mov eax,2 / retn     ⇒ OwnerObject 非空 ⇒ 恒返回 Ground(2)
[ecx+0C8h] = Type → Type->Layer(+0x364)；Type 为空 ⇒ Air(3)
```
⇒ **有宿主对象的附加动画在 vanilla 里恒进 Ground 层**，而 Jumpjet 在 Air(3) ⇒ 动画被盖住。

Phobos 的解法（`Phobos/src/Ext/Anim/Hooks.cpp:352`）：`AnimTypeExt::Layer_UseObjectLayer`
让动画继承 `OwnerObject->InWhichLayer()`。**Kratos 无此开关**，且其 AE 不设 `OwnerObject`
（`SetAnimOwner` 只写 `pAnim->Owner`；`AnimStatus::AttachToObject` 只记 `pAttachOwner`），
因此走 `Type->Layer` 分支。⇒ 若要修，属 Phobos 侧配置或 Kratos 侧新增开关，**与本 Hook 无关**。

### 14.5 与 Phobos 的处置对照（更新）

| | 保证替身/挂接物画在宿主之上 | 层级操作频率 |
| --- | --- | --- |

| Kratos 本轮 | 提交时刻按 `Stand.ZOffset` 正负把替身钉到宿主上/下侧（`0x4A9768`） | 事件级 |

**两项目当前都不再对 Air 层做按 Y 的排序。**

## 15. 替身倾斜与抖动 —— 根因闭环（2026-10-05 追加）

承接用户新提出的两个现象：

> ① Stand 附着 Master 后，Master 移动时 Stand 抖动；
> ② `Stand.Offset` 位移 + `Stand.Dir` 转向后，Master **坠落/下沉**时 Stand 的倾斜与位置不贴合
> （典型：**战列舰被击沉沉没时，炮塔脱离船身、自己往一边倾斜**）。

完整机理、根因对照、失同步逐项论证与验证清单见独立文档
**`docs/替身倾斜与抖动-2026-10-05.md`**（10 章）。本章只留对"失同步排查"这一主线有增量的事实。

### 15.1 引擎倾斜模型（**本节是全报告第一次给出倾斜的完整闭环**）

**（a）倾斜更新器 = `TechnoClass` 虚表槽 `+0x41C`**

| 项目 | 值 | 校验 |
| --- | --- | --- |
| `TechnoClass` 虚表基址 | `0x007F4960` | probe5 A 段 |
| 倾斜更新器（同函数两个名字） | **`TechnoClass_41C` = `0x70B570`** | `0x7F4960 + 0x41C = 0x7F4D7C`；`dword @ 0x7F4D7C == 0x70B570` ✓（probe6 H 段） |
| 唯一调用点 | `TechnoClass::Update`(`0x6F9E50`) 内 `0x6FA228 call [edx+vt.IsVoxel]` → `0x6FA236 call [eax+vt.Techno_41C]` | probe5 B 段：全库 `call [reg+0x41C]` **仅此 1 处** |

⇒ **门控是 `IsVoxel()`**（`YRpp/TechnoClass.h:190`）：**只有 voxel 单位每逻辑帧跑一次倾斜更新**。
**步兵（SHP）直接跳过** —— 这正好解释了用户的观测"地面步兵时现象不显眼/没有"。
（替身自身也是 `TechnoClass`，只要是 voxel 就同样每帧跑一次。）

**（b）★ IDB 结构体成员名比真实偏移小 4 字节**（本轮踩过的坑，务必记住）

| IDB 里的名字 | **真实偏移** | 语义（YRpp） |
| --- | --- | --- |
| `field_324` | **`0x328`** | `AngleRotatedSideways` |
| `field_328` | **`0x32C`** | `AngleRotatedForwards` |
| `field_32C` | **`0x330`** | `RockingSidewaysPerFrame` |
| `field_330` | **`0x334`** | `RockingForwardsPerFrame` |
| `field_3C9` | **`0x3CD`** | `IsSinking` |
| `field_421` | **`0x425`** | `IsCrashing` |

三路交叉校验：① `YRpp/TechnoClass.h:656-663` 的声明顺序；
② `TechnoClass::GetCRC`(`0x70C270`) 在 `0x70C3D4/0x70C3E2/0x70C3F0/0x70C3FE` 逐个 `CRC_float`，
`0x70C40C` 对 `[3CDh]` 做 `CRC_bool`；③ 积分器配对关系（见下）。
⚠️ **反汇编打印的字节列会错位 1 字节**，判读时**只认行首地址与助记符**。

**（c）★ 核心不变量：`Rocking*PerFrame` 是「每帧步进量（角速度）」，不是角度**

```
AngleRotatedSideways += RockingSidewaysPerFrame;   // 0x70B649 / 0x70B659
AngleRotatedForwards += RockingForwardsPerFrame;   // 0x70B65F / 0x70B66B
```
该加法**每逻辑帧执行一次**，故 `Rocking*PerFrame` 的语义是**角速度**。YRpp 注释
（`TechnoClass.h:660-663`）亦明证。**本轮全部问题的根都是把这四个字段的语义搞反。**

**（d）三套分支（`TechnoClass_41C` 内部）**

| 条件 | 行为 | 地址锚点 |
| --- | --- | --- |
| `IsSinking == 0` && `IsCrashing != 0` | 纯积分；`if (BalloonHover)` 才进回正分支，**非 BalloonHover 立即 `retn`** ⇒ **无 π/4 夹紧、无回正 ⇒ 无界累积** | `0x70B677 jz 0x70BCA4` |
| `IsSinking == 0` && `IsCrashing == 0` | 行走摇摆 / 自回正（读 `RulesData` 浮点）；入口 `RockingSidewaysPerFrame == 0` ⇒ 直接把 `AngleRotated*` 归零 | `0x70B700` 起，归零在 `0x70B921` |
| `IsSinking != 0` | 按船头八分圆每帧 `AngleRotatedForwards ± 0.01`，随后 `retn`，**同样无夹紧** | `0x70B5BA..0x70B625` |

**（e）倾斜的消费方 = locomotor 的 `Draw_Matrix`**

`AngleRotated*` 的浮点读取者集中在：`DriveLocomotionClass` 的 `vt+0x24`（`0x4AFF60`）、
`ShipLocomotionClass` 的 `vt+0x24`（`0x69F670`）、`0x513F40`/`0x5142A0`(Walk/Mech)、
`0x54DCC0`(Hover)。而 **`ILocomotion` 的默认实现 `LocomotionClass::ILocomotion_DrawMatrix`(`0x55A730`)
并不读倾斜**（只用 `[obj+0x388]` 朝向 + `Matrix3D_5AF1A0`），但上述 4 个 loco 全覆盖之。

⇒ **`FLH.cpp` 的 `GetMatrix3D()` 就是 `Locomotor->Draw_Matrix()`，本来就已含主身倾斜。**
因此用户"猜想：`Stand.Offset` 的位置算法不含倾斜"**被排除** —— Offset 的位置本来就跟随主身倾斜。
真正的问题是**替换了替身自己的状态**（下条的 R1）。

### 15.2 三个根因（全部落在 `StandEffect.cpp`）

**R1 —— 把「角度」写进了「每帧步进量」（抖动 + 下沉自转脱体的主因）**

旧代码：
```cpp
pStand->AngleRotatedForwards = forwards;
pStand->AngleRotatedSideways = sideways;
pStand->RockingForwardsPerFrame = forwards;   // ★ 把角度写进步进量
pStand->RockingSidewaysPerFrame = sideways;   // ★ 同上
```
引擎每逻辑帧执行 `AngleRotated += Rocking*PerFrame` ⇒ **替身每帧再加一份主身完整角度**
⇒ **无界累积**（`IsCrashing` 分支对非 BalloonHover 无夹紧、无回正）。
量级：行走摆动约 **157 帧**达到 π/2；坠落/沉没分支只有 **6~15 帧** ⇒ 肉眼看是"立刻自己翻过去"。

**`FootClass_Crash`(`0x4DEBB0`) 的实证**：
```
0x4DECCD call Random2Class::operator()(0, 0x7FFFFFFE)
0x4DECF0 fstp [esi+330h]     ; RockingSidewaysPerFrame = rand*0.15 + 0.1
0x4DED0B/0x4DED13 fchs
0x4DED45 fstp [esi+334h]     ; RockingForwardsPerFrame
0x4DEC7F mov byte ptr [esi+425h], 1   ; IsCrashing = 1
```
⇒ 坠落/沉没时引擎给的是**每帧随机翻滚步进量**。替身若同时被写进"主身角度"作为步进量，
两者叠加 ⇒ 正是"脱离船身、自己往一边倾斜"。

**R2 —— 方向旋转的手写 8 分支有缺陷**

旧实现 `switch (Data->Offset.Direction)` 中，**`0/2/6/14` 是空实现**，**`8` 漏了对 `forwards` 取反**。
（只有当 `Offset.Direction` 恰好落在 `4/10/12` 时才正确 —— 这就是用户平时没大面积撞上的原因。）

**R3 —— 下沉/坠毁时 `StickOnFloor` 把替身强压到自身格子的地面高度**

`SetLocation()` 里 `StickOnFloor` 分支无条件 `SetHeight(0)`：主身在下沉，替身却被钉在
**它自己所在格子**的地面高度 ⇒ 与主身分离（"炮塔掉到水面"）。

### 15.3 修复（`src/Ext/EffectType/Effect/StandEffect.cpp`，三处）

| 处 | 改动 |
| --- | --- |
| `OnGScreenRender` | ① `Rocking*PerFrame = 0`（角度只由主身单向驱动）；② 用两端 `PrimaryFacing` 之差的 rotZ 连续旋转替换手写 8 分支；③ 同步 `PreviousRamp`/`CurrentRamp` |
| `UpdateStateTechno` | 逻辑帧兜底再清零一次 `Rocking*PerFrame`（防某渲染帧没派发事件） |
| `SetLocation` | 加 `&& !pTechno->IsSinking && !pTechno->IsCrashing` 门控，下沉/坠毁时不强压高度 |

方向旋转的新实现（对 16 方向、`IsOnTurret`、`FreeDirection`、`LockDirection` 全部成立）：

```cpp
double theta = pStand->PrimaryFacing.Current().GetRadian()
             - pTechno->PrimaryFacing.Current().GetRadian();
while (theta >  Math::Pi) theta -= Math::TwoPi;
while (theta < -Math::Pi) theta += Math::TwoPi;
if (theta != 0.0)
{
    const double c = std::cos(theta), s = std::sin(theta);
    const float f = forwards, sd = sideways;
    forwards = static_cast<float>(f * c - sd * s);
    sideways = static_cast<float>(f * s + sd * c);
}
```
**标定基准**：旧代码 `case 4/10/12` 的实测行为与该式在 `theta = Direction * 22.5°` 下**完全等价**。

**为什么必须放渲染阶段**：引擎倾斜更新器跑在 `LogicClass_Update`(`0x55DC9E`) 内
（本报告 §三·补一 的帧内时序图，位于逻辑帧尾部）。**逻辑阶段写 `AngleRotated*` 会被引擎立刻覆盖**；
而渲染事件（`0x4F4497` Kratos `GScreenClass_Render`）处在 `TacticalClass_Draw`(`0x4F44DF`) **之前**，
是"引擎算完、绘制之前"的**唯一**写值窗口。

### 15.4 失同步评估（硬约束已满足）

## 16. P1 处置：层判定纯函数化 + 冗余 Hook 删除 + 吊运判据修正（2026-10-05 追加）

用户验收：替身渲染事项已确认（`Stand.ZOffset=-1` 能正确画在 Jumpjet **下层**，说明 §14.3 的方向性
bug 修复生效）。随即指示：**P1 项以"不造成断联"为第一优先处理。**

本章记录的三项 P1 处置**已经改码、编译并部署**（`Kratos.dll` 4,187,136 字节，01:08；
与 `output/Kratos.dll` MD5 一致 `03ab23719213fbed934723a162a31da4`；游戏目录同 hash）。

### 16.1 ★ 删除 `DEFINE_HOOK(0x4DA87A, FootClass_Update_UpdateLayer, 0x6)`（P1）

**落点实测字节**（`ida_work/p1_probe.txt` D 段）：

```
004DA87A: 38 9E 90 00 00 00    cmp   [esi+90h], bl     ← 恰好 6 字节，size=0x6 契约成立
004DA880: 0F 84 ...            jz    （未被覆盖）
```

**删除理由（三条独立成立）**：

1. **完全重复**。引擎 `ObjectClass::Update`(`0x5F3E70`) 已经做了同一件事：
   ```
   0x5F4001  call [eax+78h]      ; obj->InWhichLayer()
   0x5F4004  cmp  ebp, eax       ; vs this->LastLayer
   0x5F4006  jz   loc_5F4013
   0x5F400E  call DisplayClass::Submit
   ```
   而 `FootClass::AI`(`0x4DA530`) 开头 `0x4DA539 call TechnoClass_Update` 会先跑完上面这段，
   **之后**才轮到 `0x4DA87A` ⇒ 本 Hook 在正常情形下**恒为空转**。
2. **一旦 `InWhichLayer()` 非纯函数**（见 16.2），就会**同一帧 `Submit` 两次** ⇒ 层数组下标被搬动两次
   ⇒ 与 §16.2 的校验值问题叠加。
3. **语义读错**：原版 `cmp [esi+90h], bl` 是 **`IsAlive` 守卫**（`ObjectClass+0x90` = `IsAlive`、
   `+0x94` = `LastLayer`），**不是层比较**。Kratos 当时的注释把字段偏移搞错了（详见 §13.3），
   于是"看起来像层变更判断"的假象被当成理由保留了下来。

删除后 `0x4DA87A` 完全退回 vanilla。**该地址已从 Hook 清单中移除**，
并在 `StandExtHook.cpp` 原位留下了删除原因的注释块（防止后人再加回来）。

### 16.2 ★ `InWhichLayer()` 纯函数化 —— 这是"无标签基线也失同步"的**直接成因**（P1，实质 P0）

**原版这 5 个函数字节完全相同**（实测 `B8 02 00 00 00 C2 04 00`）：

```asm
mov  eax, 2      ; Layer::Ground —— 常量，不读内存、无副作用
retn 4
```

即 vanilla 里 `InWhichLayer()` 对地面型 locomotor 是**纯常量函数**。

**Kratos 的替换把"常量"变成了"有状态"。** 关键是要看清**真正的缺陷在哪儿**——
经 `git log -S` 追溯（`584c49e` 2024-03-31 引入 → `b2b0536` 2024-04-03 重构），
重构时写出了一个**自赋值空操作**：

```cpp
static Layer GetLayer(TechnoClass* pTechno)
{
    Layer layer = pTechno->IsInAir() && !pTechno->IsFallingDown ? Layer::Air : Layer::Ground;
    if (pTechno == pStand)                 // pStand = 命名空间全局（上一轮查询过的对象）
    {
        layer = layer;                     // ← 自赋值！本意是 layer = StandLayer::layer;
    }
    else
    {
        /* ... 替身跟随 Master 层 ... */
        pStand = pTechno;
        layer = layer;                     // ← 同样是自赋值（本意是 StandLayer::layer = layer;）
    }
    return layer;
}
```

后果有两条，第二条才是致命的：

* 命名空间里的 `layer` 缓存**从未被写入** ⇒ 它是死变量；
* **缓存命中分支（`pTechno == pStand`）跳过了"替身跟随 Master 层"整段逻辑**，
  直接返回 `IsInAir() ? Air : Ground`。

⇒ **同一个替身，在同一帧内的连续两次调用可能返回不同的层。** 反例：
`Master` 在 `Air(3)`、替身自身 `IsInAir() == false` 时 ——
第 1 次调用走 `else` 分支 → `Air(3)`；第 2 次调用走命中分支 → `Ground(2)`。

**为什么这必然导致失同步**（`InWhichLayer()` 不是纯视觉函数）：

| 消费者 | 位置 | 后果 |
| --- | --- | --- |
| 层变更 → `Submit` | `ObjectClass::Update` `0x5F400E` | `Submit` 改变 `vec_ObjectsInLayers[层]` 的**下标顺序**；每帧锁步校验值 `sub_64DAB0`(`0x64DAB0`) 对该数组做**顺序敏感哈希**（`sum = sum*2 + value`）⇒ 顺序不同 = 校验值不同 |
| 能不能开火 | `TechnoClass::CanFire` 的 `0x6FC749`：`if (layer != Layer::Ground)` 判"目标在空中" | 直接影响**模拟分支**（Kratos 自己也在该处挂了 `TechnoClass_CanFire_WhichLayer_Stand`） |

而**两个客户端在同一帧对该函数的调用次数/时机必然不同**（视野内外、渲染派发次数、
`CanFire` 次数、`IsInAir` 查询次数都有差异）⇒ 一边 `Submit`、一边不 `Submit`
⇒ 层数组顺序分叉 ⇒ **校验值不同 ⇒ 失同步**。

> 这精确对应"**没有启用任何 Kratos 功能标签、地面步兵、`Ctrl+Shift` 索敌前进就很快失同步**"：
> 步兵用 `WalkLoco`（正是被替换的 5 个之一），索敌会大幅提高 `InWhichLayer()`/`CanFire` 的
> 调用频次 ⇒ 命中/未命中分支被交替触发的概率放大。且这 5 条 Hook **没有任何功能开关**。

**修复**：改为**纯函数** —— 结果只由"当前（已同步的）对象状态"决定，不留任何跨调用状态。

```cpp
namespace StandLayer
{
    static Layer GetLayer(TechnoClass* pTechno)
    {
        // 替身：跟随 Master 所在层（唯一必须介入的情形，属功能本身）
        TechnoStatus* status = nullptr;
        if (TryGetStatus<TechnoExt, TechnoStatus>(pTechno, status)
            && status->AmIStand() && status->pMyMaster && !status->MyStandData.IsTrain)
        {
            Layer l = status->pMyMaster->LastLayer;
            if (l != Layer::None)
                return l;
        }
#if KRATOS_STAND_LAYER_STRICT
        return Layer::Ground;                 // 严格模式：与 vanilla 常量逐字节等价
#else
        return pTechno->IsInAir() && !pTechno->IsFallingDown ? Layer::Air : Layer::Ground;
#endif
    }
}
```

> **⚠️ 2026-10-05 更新**：上方的编译期开关 **`KRATOS_STAND_LAYER_STRICT` 已移除**（连同
> `KRATOS_STAND_LAYER_FIX`）—— "非替身对象直接返回原版常量 `Ground`"这条路径对替身必然错误，
> 留着只会误导；`StandLayer::GetLayer` 现在无条件走纯函数版。需要联机二分时改用
> "同一份源码 + 两个产物"的**二进制差分**，避免"同一份地图/模组仅因编译选项不同就产出不同层序"
> 这一额外分歧面。上面的代码块保留为当时的快照。

### 16.3 `IsInAir()` 是确定性函数（纯函数化安全的前提）

`TechnoClass::IsInAir()`(`0x5F6B90`) 实测反汇编：

```asm
005F6B90  mov   al, [ecx+74h]        ; [obj+0x74] —— Kratos 在 0x5F6B90 处为替身跳过的那道检查
005F6B93  test  al, al
005F6B95  jz    short loc_5F6BAF     ; 为 0 ⇒ 返回 false
005F6B97  mov   eax, [ecx]
005F6B99  call  dword ptr [eax+1C8h] ; obj->GetHeight()
005F6B9F  mov   ecx, const_int_ObjectClass_68h   ; 0x68 = 104
005F6BA5  lea   edx, [ecx+ecx]       ; edx = 208
005F6BA8  cmp   eax, edx
005F6BAA  jl    short loc_5F6BAF
005F6BAC  mov   al, 1
005F6BAE  retn
```

⇒ `IsInAir() == ([obj+0x74] != 0 && GetHeight() >= 208)`。
**输入全部来自引擎同步状态**（`GetHeight()` 由 `Location.Z` 与地形高度得到，
而 `Location.Z` 是确定性地推进的 —— 它只是没被 `sub_64DAB0` 的**粗采样**读入，并非不同步）。
⇒ 纯函数化之后，两端结果必然一致，不存在 §13.4 担心的"瞬时抖动"。

### 16.4 `JumpjetCarryall::CanLift` 的判据修正（P1）

原写法（`src/Ext/TechnoType/JumpjetCarryall.cpp:78`）：

```cpp
&& pTechno->Owner->IsControlledByCurrentPlayer() && pTechno->Owner->IsAlliedWith(...)
```

`IsControlledByCurrentPlayer()`（`YRpp/HouseClass.h:461`）在**联机下等价于
`HouseClass::IsCurrentPlayer()`** —— 即"**本机玩家**"，**各客户端结果不同**：
同一架运输机在 A 客户端返回 `true`、在 B 客户端返回 `false`。

调用链：`CanLift` ← `UnitClass::What_Action`（`0x73FD50..0x7404AA`，其中 `0x74041B` 是 Kratos 的落点；
该函数是**虚函数**，由 vtable `0x7F5CE4` 派发 ⇒ 无法用 xref 穷举调用者）
← 返回 `Action::Tote`(吊运) 还是 `Action::Select`。一旦两端结果不同，同一帧的吊运判定分叉
⇒ 目标/任务分叉 ⇒ 失同步。

**修复**：改用 **`IsControlledByHuman()`**（`HouseClass.h:452`）——
`联机下 == IsHumanPlayer`（House 级属性，**全端一致**）；
`战役下 == IsHumanPlayer || IsInPlayerControl`，与原写法**完全相同**。

| 场景 | 旧判据 | 新判据 | 差异 |
| --- | --- | --- | --- |
| 本机玩家的运输机 | true | true | **无** |
| 其它人类玩家的运输机 | false | true | 有，但本机点不到，**UX 无影响** |
| AI 的运输机 | false | false | **无** |

⇒ 对本地玩家体验与 AI 行为均**零改变**，只是把"本机"换成了"人类"。

### 16.5 §13.7 遗留 P1「21 条 WARN 复核」—— 结论：**误报，无需改码**

用 `ida_work/p1_probe.py` 对 21 条 WARN 的覆盖区间做了**逐指令解码**（`p1_probe.txt` A 段）：

| 类别 | 条数 | 说明 |
| --- | --- | --- |
| **间接调用** `call dword ptr [reg+disp]` | **17** | 如 `call [ecx+1Ch]`、`call [edi+378h]`、`call [eax+1C8h]`。**没有相对位移** —— 目标由寄存器算出，搬迁到 trampoline 后**完全不受影响**。审计脚本把 `call` 一律当成"相对跳转"，属启发式误报。 |
| **真正的 `jcc`（rel8/rel32）** | **4** | `0x42659D jz`→`0x4265A8`；`0x469EB4 jnz`→`0x469E34`；`0x70256C jnz`→`0x7024E0`；`0x7024B0 jnz`→`0x70240C`（4 条目标都在区间外）。 |

对这 4 条真 `jcc` 的判定依据（**旁证，非演绎**）：

* 这 4 条全在**极热路径**上 —— `AnimClass_SDDTOR`（动画析构）、`BulletClass_Fire`、
  `TechnoClass::ReceiveDamage` 的残骸分支（单位死亡必走）。若它们真被"搬迁后偏移失效"，
  游戏会**每次单位死亡/动画销毁都崩**，而实机长期稳定。
* 与我们自己踩过的坑一致：`0x4A975E`（size `0x2`）当时的崩溃表现是
  "**重放声明 size 字节 → 落到 `addr+5` 的指令中间**"，说明运行期 Syringe 的 `return 0`
  是在**原地址原地执行**被覆盖指令（而非搬到别处）⇒ **区间内的相对跳转不会失效**。

⇒ **判定：21 条 WARN 在当前（旧版）Syringe 下均为既存且安全的行为，不改码。**
⚠️ **触发条件**：将来若把游戏目录的 Syringe 换成 **SyringeEx**（其 `ReladdrInstructionFixup`
会对搬迁后的相对地址做重定位），这 4 条真 `jcc` 必须**逐条重审**；
另外 17 条间接调用始终安全。
