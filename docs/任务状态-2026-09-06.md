## 2. 本会话已定案的设计/结论

### 2.1 AE 继承开关

- 变形/替换/礼盒继承统一用 `DiscardOnTransform` 控制；
  `Inheritable` 已降级为兼容旧 INI 的别名（不再独立语义）。
- 提交 `64373ee` 起生效，GiftBox 与 (Un)DeploysInto 共用同一套流程。

### 2.2 AEM 交换现状（InheritAE，`src/Ext/Helper/Gift.cpp:424`）

- `InheritedStatsTo`：状态机采用**复制**继承（部分状态机不希望被继承，
  如 GiftBox/Transform 自身被排除），不是移动。
- 第一遍：把 `DiscardOnTransform` / GiftBox / Transform 类型 AE、
  以及 `CanAffectType` 不匹配的 AE 标记 `TimeToDie`，再
  `CheckDurationAndDisable(true)` + `ClearDisableComponent()` 清理。
- 第二遍：幸存 AE 重绑 `pSource = 新单位`、`pSourceHouse = 新单位实际 Owner`
  （DeploysInto 同属，GiftBox 可能异属，统一按新单位 Owner 修正）。
- 交换：`boxAEM <-> giftAEM` 用组件级原子 `MoveTo`，各自保持原 index；
  第二个失败时回滚第一个；只对被移动的 AEM 子树调用 `ExtChanged()`，
  不再向整个 GO 广播（避免 TechnoStatus 等无关组件重复 InitExt）。
- 收尾 `Attach` 指 `GiftBox.AttachEffects`，对所有礼物再做一次附加，
  不只针对变形类礼盒；盒子被销毁时需确认 AE 管理器有 Source 死亡兜底。

### 2.3 Range（Status.Range / CrateBuff.Range*）

- `0x7012DF` 同址执行顺序：Ares → Kratos → Phobos；
  前一个 hook 返回 0 才会执行到后一个。
- Kratos 最终实现：`EBX = (pWeapon->Range + RangeCell*LeptonsPerCell) * RangeMultiplier`，
  返回 `0x7012E5` 继续原流程（EBX 只影响自身武器射程段，
  不会覆盖 OpenTopped 乘客循环里的 EAX/射程）。
- 相关分析文件：`ida_work/select_weapon_dump.txt`、`range_funcs_dump.txt`、
  `docs/Hook地址冲突清单.md`。

### 2.4 箱子加成（CrateBuff）审计结论

- 拾取主流程逐条核对过，未发现「拾取即失效」的问题：
  - 选择阶段：`0x481D0E/0x481C6C/0x481CE1/0x481D3D`
    （可拾取 → `0x481D52`，已有加成 → `0x481C86` 转钱），与原版语义一致；
  - 生效阶段：`0x483226/0x482E57/0x48303A/0x48294F`
    （记录到 `TechnoStatus::CrateBuff` 后 `RecalculateStatus()`，
    返回 `0x483258/0x482E89/0x483078/0x482956`），均正确跳过原版直写。
- 写入/读点确认（IDA + Phobos 参照）：
  - 原版读物理字段处：`TechnoClass::Fire` 0x6FE33D~0x6FE352、
    `TechnoClass::EstimateDamage` 0x6FDBCD~0x6FDBE2；
  - Phobos AE 叠加处：火力 0x6FE352/0x6FDBE2、速度 0x4DB218、
    护甲 0x6FDC87/0x701966。
- 设计本身即「额外记录拾取加成 + 每帧与 AE 合并写入物理字段」，
  与 Ares/Kratos 风格一致。
- 已知的潜在丢失点（与「拾取即失效」报告不对应，暂不处理）：
  - `TechnoStatus::Clean()` 会清空 `CrateBuff`（对象池/组件移动/重建路径）；
  - (Un)DeploysInto 目前**不搬运** CrateBuff 到目标 status；
    GiftBox 的 IsTransform/SameDir 路径有搬运
    （`pGiftStatus->CrateBuff = boxState.CrateBuff`）。
