## 1. Syringe 的落点契约（源码确证，**这是本轮的关键**）

`SyringeEx/SyringeDebugger.cpp:529-640`：

```cpp
static BYTE const jmp_back[] = { 0xE9, INIT, INIT, INIT, INIT };   // 5 字节
static BYTE const jmp[]      = { 0xE9, INIT, INIT, INIT, INIT };   // 5 字节

auto const [count, overridden] = ...;               // overridden = 该地址上所有 hook 声明 size 的最大值
std::vector<BYTE> original_bytes(overridden);
ReadMem(it.first, original_bytes.data(), overridden);        // 只读「声明的 size」字节

// …把 overridden 字节搬迁(=RebuildInstructions)到调用区…
auto rebuilt = RebuildInstructions(original_bytes.data(), overridden, originalAddr, newAddr);

// 跳回：★目标写死为 addr + 5
auto const rel = RelativeOffset(base + (p_code - code.data() + 0x05),
                                static_cast<BYTE*>(it.first) + 0x05);
ApplyPatch(p_code, jmp_back);
```

```cpp
// patch original code —— ★覆盖长度 = max(声明的 size, 5)
auto const rel2 = RelativeOffset(p_original_code + 5, base);
code.assign(std::max(overridden, sizeof(jmp)), NOP);
ApplyPatch(code.data(), jmp);            // 5 字节 E9 rel32
PatchMem(p_original_code, code.data(), code.size());
```

### 提炼成三条规则

| # | 规则 | 依据 |
| --- | --- | --- |
| **R1** | 原码被覆盖的长度 = **`max(声明的 size, 5)`**，尾部以 `nop` 补齐 | 第 636-640 行 |
| **R2** | `return 0` ⇒ 只重放**声明的 size** 字节，然后**无条件跳到 `addr + 5`** | 第 605-607 行 |
| **R3** | 被覆盖区间若含**相对跳转**（`Jcc`/`JMP`/`CALL`），搬迁后偏移失效；只有 SyringeEx 的 `ReladdrInstructionFixup` 会修 | `RebuildInstructions` + README 特性表 |

### `size < 5` 到底行不行

- **`return 0` 时不行。** R1 覆盖 5 字节、R2 只重放 `size` 字节并跳到 `addr+5` ⇒ 落点在指令中间。
- **唯一例外：重放块以"控制流离开函数"的指令结尾**（`retn` / `ret` / `jmp`）。
  此时重放完就离开了，`jmp addr+5` 永远不会执行 ⇒ 安全。
  > 这就是为什么 Kratos / Phobos / Ares 里所有 <5 字节的 hook **清一色落在 `retn` 上**。
- **另一条合法写法：`size < 5` 时不 `return 0`，而是 `return` 一个显式继续地址。**
  Ares 的实例（`Antares/src/Misc/Debug.cpp:295`）：
  ```cpp
  DEFINE_HOOK_AGAIN(0x4A4AC0, Debug_Log, 0x1)
  DEFINE_HOOK(0x4068E0, Debug_Log, 0x1)     // size = 1，不在 retn 上
  {
      ...
      return 0x4A4AF9;                      // ★ 显式继续地址，而不是 return 0
  }
  ```

> ⚠️ 我原先引用 `YRpp/Syringe.h:287` 的注释（"saving the specified amount of instruction bytes **to be restored if return to the same address is used**"）
> 得出"size 就是指令长度、2 字节没问题"的结论 —— **只读懂了 R2 的一半**，漏了 R1（`max(size,5)`）
> 和"跳回目标是 `addr+5`"这两个决定性细节。**以源码为准。**

## 2. 我方 hook 为什么必然出错

```cpp
DEFINE_HOOK(0x4A975E, DisplayClass_Submit_KeepStandAboveMaster, 0x2)   // ← 病根
```

现场字节（`ida_work/crash_probe.txt`）：

```asm
004A9759  E8 52 82 0A 00     call MapClass_AddObjectToALayerX   ; 0x5519B0
004A975E  84 C0              test al, al      ← ★声明的 hook 落点，2 字节
004A9760  74 06              jz   loc_4A9768 ; al==0 则跳过 LastLayer 赋值
004A9762  89 BE 94 00 00 00  mov  [esi+94h], edi   ; obj->LastLayer = layer
004A9768  5F                 pop  edi
004A9769  5E                 pop  esi
004A976A  C2 04 00           retn 4
```

按 R1/R2 推演（`size = 2`）：

1. 覆盖长度 = `max(2, 5)` = **5 字节** ⇒ 原码 `0x4A975E..0x4A9762` 被 `E9 rel32` 吃光，
   其中 `74 06`（`jz`）与 `89 BE`（`mov` 的头两字节）**被销毁且没有备份**（只备份了 2 字节）。
2. `return 0` ⇒ 重放 `84 C0`（`test al,al`），随后 `jmp` 到 **`0x4A975E + 5 = 0x4A9763`**。
3. `0x4A9763` 是 `mov [esi+94h],edi` 的**第 2 个字节**（`BE 94 00 00 00`），于是被当作
   `mov esi, 0x94` 解码执行。

**净后果**：`jz` 判断与 `LastLayer = layer` 赋值被**整段跳过**。

⇒ `LastLayer` 停在初始值 `-1` ⇒ 下一帧 `ObjectClass::Update`（`0x5F4001 call [eax+78h]` /
`0x5F4004 cmp ebp,eax`）仍然判定"层变了" ⇒ **再次 `Submit`** ⇒ 而 `Submit` 开头
`0x4A972A cmp [esi+94h],-1` 因 `LastLayer == -1` 而**跳过 `Remove`** ⇒ **`AddObject` 只加不删**。

**每帧、每个对象，层数组都在被追加/搬动。** 这既会持续污染层数组（`Ground` 层是
`sorted == true` 的线性插入），也是**教科书级的失同步源**；下游在渲染遍历层数组时碰到
被损坏/悬垂的条目即崩溃 —— 与 22:57 快照"遍历 `Ground` 层时对象的 vtable 已是野值
`0x18EC9770`"一致。

## 4. 崩溃两次，都是同一个签名

| 时间 | EIP | ESP | 说明 |
| --- | --- | --- | --- |
| 22:57:08 | `0x1BF09EEB` | `0x001AD138` | 栈回溯落在 `Ra2md.exe` 渲染路径（`Main_Game → Main_Loop → DrawOnTop → TacticalClass::Draw → sub_6D9A50`）；顶层 EIP 不在任何静态模块内 |
| 23:23:32 | `0x1BBEBE35` | **`0x6D9A7F01`** | `ESP` 既非栈区间、也不 4 字节对齐 ⇒ **控制流进入非代码区/栈被破坏**的典型签名 |

两次都伴随 `EDI = 0xFFFFFFC0`，且两个 EIP 相差 `0x31E0B6`（≈3.2 MB）。

### ★ 更正 v1 的"无 ASLR"结论

v1 依据 PE 头的 *preferred* ImageBase 断言"全无 ASLR"——**错**。实测 `DllCharacteristics`：

| 模块 | DllCharacteristics |
| --- | --- |
| `gamemd.exe` | `0x0000`（无 ASLR） |
| **`Kratos.dll`** | **`0x0140` = `DYNAMIC_BASE`(ASLR) \| `NX_COMPAT`** |
| **`Ares.dll`** | **`0x0140` = `DYNAMIC_BASE`(ASLR) \| `NX_COMPAT`** |

三个 DLL 的 preferred base 全是 `0x10000000`，运行时必然被随机重定位（`Ares.dll` 先占
`0x10000000`，`Kratos.dll` 被搬到别处）。⇒ 那两个 `0x1BB*****` / `0x1BF*****` 的 EIP
**很可能就在重定位后的 `Kratos.dll` 内**（`sizeImage = 0x3FD000`，两个 EIP 相差 `0x31E0B6`
完全落在同一区间内），而不是 v1 说的"运行期 JIT / 堆执行代码"。

> 这也解释了"两次崩溃 EIP 不同、但形态一致"：**ASLR 每次换基址，崩溃点却是同一个函数**。

## 7. 已实施的修复

**落点从 `0x4A975E` 搬到 `DisplayClass::Submit` 的公共出口 `0x4A9768`，size 改为 `0x5`：**

```cpp
// 0x4A9768: 5F         pop edi     (1 字节)
// 0x4A9769: 5E         pop esi     (1 字节)
// 0x4A976A: C2 04 00   retn 4      (3 字节)   ⇒ 恰好 5 字节、3 条完整指令
DEFINE_HOOK(0x4A9768, DisplayClass_Submit_KeepStandAboveMaster, 0x5)
```

为什么这个落点**同时满足所有约束**：

| 约束 | 本落点 |
| --- | --- |
| R1 `overridden ≥ 5` | ✅ 恰好 5 字节 |
| 覆盖**完整指令** | ✅ 3 条：`pop edi` / `pop esi` / `retn 4` |
| R3 区间内无相对跳转 | ✅ 无 `Jcc`/`JMP`/`CALL` |
| `return 0` 后 `jmp addr+5` | ✅ 但用不到：重放块以 `retn` 结尾，控制流直接离开 |
| 寄存器可用 | ✅ `ESI = pObject`（`0x4A9721` 起未改）、`EDI = layer`（`0x4A9740 mov edi,eax`） |
| 与下游插件冲突 | ✅ Ares(Antares) / Phobos 现源码**均无任何 `0x4A97xx`**；Phobos 旧 hook `0x4A9750` 只覆盖 `0x4A9750..0x4A9758`，不相交 |

另外给 handler 加了 `pObject == nullptr` 的空值前置判断（`Submit` 有若干早退分支同样汇合到该出口）。

源码位置：`src/Hooks/StandExtHook.cpp`。（原 `KRATOS_STAND_LAYER_FIX` 编译期开关已于 2026-10-05 **移除**：

## 9. 仍然成立的失同步隐患（与本次崩溃独立，但需要处理）

### 发现 A —— `InWhichLayer()` 从纯常量函数被改成有状态函数（**正中"地面步兵"**）

引擎原版（字节实测）：

```asm
0075C7E0  B8 02 00 00 00   mov  eax, 2      ; Layer::Ground —— 常量
0075C7E5  C2 04 00         retn 4
```

`ShipLocomotionClass::InWhichLayer`(`0x6A3E50`) / `DriveLocomotionClass::InWhichLayer`(`0x4B4820`)
**字节完全相同** —— 都是"恒定返回 `Ground`"的**纯函数**（不读内存、无副作用）。

Kratos 把 **5 个 locomotor 全部替换**（`src/Hooks/StandExtHook.cpp:656` 起，`Walk` 正是步兵用的那个），
改成 `StandLayer::GetLayer()` —— 依赖 `IsInAir()` + **单槽静态缓存** `pStand`/`layer`：

- 任何一次 `IsInAir()` 瞬时为真（桥上 / 举升 / 爬行倒地过渡 / 浮点高度误差）
  ⇒ 返回 `Air(3)` ≠ `LastLayer(Ground=2)` ⇒ 触发 `Submit` ⇒ 对象被搬进 `Air` 层；
- 单槽缓存让结果**依赖调用历史**（同一帧两次调用可能不同）；
- 两客户端若渲染调用次数不同（一方在视野内）⇒ 缓存命中时机不同 ⇒ **一边 Submit 一边不 Submit** ⇒ **层数组顺序分叉 ⇒ 失同步**；
- 这 5 条 hook **无条件生效**，与"未启用任何 Kratos 功能标签也失同步"完全吻合。

**修法方向**：仅在"对象确属替身侧"时才介入，否则 `return 0` 让原版 `mov eax,2` 透传，
恢复纯函数语义；同时删掉 `StandLayer::GetLayer` 里的单槽缓存。

### 发现 B —— `0x4DA87A` 把引擎已有的"层变更 → Submit"又写了一遍

引擎 `ObjectClass::Update`（`0x5F4001 call [eax+78h]` / `0x5F4004 cmp ebp,eax` / `0x5F400E call Submit`）
本来就做了同样的事。Kratos 在 `0x4DA87A` 又写一遍 ⇒ 结合发现 A 会**同一帧 Submit 两次**。建议整条删除。

> 另更正一个长期误读：`+0x90` 是 **`IsAlive`**，`+0x94` 才是 **`LastLayer`**
> （`0x4A9762 mov [esi+94h], edi` 更新）。
