# Kratos++ 设计文档

> 版本：对应仓库 main 分支（VERSION 0.2.2p11 之后，含 2026-08 异步日志工具包）
> 本文面向想理解 Kratos++ 内部架构的开发者，描述系统的分层、核心机制与关键数据流。

## 1. 项目定位

Kratos++（KratosPP）是基于原 DPKratos 的 C++ 移植版，是《尤里的复仇》（Yuri's Revenge，简称 YR）的引擎扩展平台。它以 DLL 注入方式运行在 `gamemd.exe` 进程中，通过 INI 标签为 MOD 提供大量新功能。

与 DPKratos 相比，本版本：

- 舍弃了全部"动态特性"（动态编译/热加载），改用 C++ 预编译，追求更快、更轻；
- 以 `Kratos.dll` 为成品，配合注入器（Syringe / RunAres）随游戏启动；
- 逻辑以"扩展（Extension）"+"组件（Component）"的方式挂接到原版游戏对象上，不修改原版代码文件。

## 2. 总体架构

系统在运行时分为四层：

```
┌─────────────────────────────────────────────────────┐
│                    MOD（Rulesmd.ini 等）              │  数据层
├─────────────────────────────────────────────────────┤
│              Kratos.dll（本仓库产出）                 │  功能层
│  Ext/ 目录：AE 效果器、状态、单位/弹头/动画逻辑        │
│  Hooks/ 目录：游戏函数钩子、事件广播                  │
├─────────────────────────────────────────────────────┤
│            YRpp（游戏符号/类定义头）                  │  符号层
├─────────────────────────────────────────────────────┤
│        gamemd.exe（尤里的复仇游戏本体）               │  运行时
└─────────────────────────────────────────────────────┘
```

### 2.1 分层职责

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 数据层 | MOD 的 `rulesmd.ini` / `artmd.ini` / `aimd.ini` 等 | 通过 INI 标签声明行为 |
| 功能层 | `src/Ext/`、`src/Hooks/`、`src/Extension/` | 本仓库源码，实现全部游戏逻辑 |
| 符号层 | `YRpp/` 子模块 | 原版类/结构/函数地址的头文件描述（源自 Phobos 改良版） |
| 运行时 | `gamemd.exe` | 被注入的游戏进程 |

功能层的入口是 `src/Hooks/KratosHook.cpp`：它在静态构造时向事件系统注册 `ExeRun`（加载初始化）、`GScreenRenderEvent`（激活提示）与 `SidebarRenderEvent`（版本号绘制）等处理器，把 DLL 接入游戏生命周期。


## 4. 核心机制设计

### 4.1 事件系统（EventSystem）

事件系统是"游戏函数钩子"与"逻辑代码"之间的解耦层。游戏函数被 hook 后，不直接调用具体逻辑，而是向事件系统广播事件，由注册的处理器响应。

四个事件管理器：

| 管理器 | 用途 |
| --- | --- |
| `EventSystems::General` | 全局生命周期：ExeRun、CmdLineParse、ScenarioStart、ScenarioClearClasses |
| `EventSystems::Render` | 渲染：GScreenRenderEvent、SidebarRenderEvent |
| `EventSystems::Logic` | 逻辑帧：LogicUpdateEvent（每帧 + 延迟帧两阶段）、TypeChangeEvent |
| `EventSystems::SaveLoad` | 存档：SaveGameEvent、LoadGameEvent |

典型事件（`src/Common/EventSystems/EventSystem.h`）：

| 事件 | 触发时机 |
| --- | --- |
| `ExeRun` | YR 进程初始化完成后（hook 0x7CD810） |
| `ExeTerminate` | 进程退出前 |
| `CmdLineParse` | 命令行参数解析（hook 0x52F639） |
| `ScenarioClearClassesEvent` | 场景清理类（读档/重开前），用于清空扩展注册表 |
| `ScenarioStartEvent` | 场景开始，用于重置各管理器 |
| `LogicUpdateEvent` | 每逻辑帧（hook 0x55AFB3 / 0x55B719，后者带 `EventArgsLate` 标识晚阶段） |
| `GScreenRenderEvent` / `SidebarRenderEvent` | 战术画面/侧边栏渲染 |
| `PointerExpireEvent` / `DetachAll` / `ObjectUnInitEvent` | 指针失效、对象脱离、对象销毁 |
| `SaveGameEvent` / `LoadGameEvent` | 存档/读档 |

事件使用 `Event(Name, Dest)` 值作为 key，处理器通过 `Delegate`（`Common/MyDelegate.h`）绑定。广播为同步调用：`Broadcast(e, args)` 依次调用所有处理器。

### 4.2 扩展容器（Extension<T> / Container<T>）

扩展机制源于 Phobos 的类扩展标准，是"给游戏类附加额外数据"的基础。

#### Extension<T>

`Extension<T>` 是"某游戏对象实例的扩展数据"的基类，持有：

- `AttachedToObject`：被扩展的原版对象指针；
- `Initialized`：初始化状态机（Blank → Constanted → Ruled → Inited → Completed）。

`LoadFromINI()` 按状态机依次调用 `InitializeConstants()` → `InitializeRuled()` → `Initialize()` → `LoadFromRulesFile()` → `LoadFromINIFile()`，保证规则数据按正确顺序只初始化一次。

#### Container<T>

`Container<TExt>` 是"类型 TExt 的所有扩展数据"的容器，内部是 `std::unordered_map`（对象指针 → 扩展数据指针）。每个具体扩展类（如 `TechnoExt`）都有一个静态 `ExtMap` 实例。

容器提供：

- `TryAllocate` / `Find` / `Remove`：对象指针到扩展数据的映射；
- `PointerGotInvalid` / `ObjectWantDetach`：指针失效与脱离时向所有扩展数据广播；
- `LoadStatic` / `SaveStatic` / `PrepareStream`：单个对象的存读档流处理。

#### TypeExtension<TBase, TExt>

类型扩展（Type）挂在"类型类"上（如 `TechnoTypeClass`），数据是类型级配置。`ExtData` 中一般有一个 `INIConfig` 派生类（如 `TechnoTypeExt::TypeData`），在 `LoadFromINIFile` 时读取 `[类型ID]` 段落的标签。

#### GOExtension<TBase, TExt>

对象扩展（实例）除自身数据外，还内嵌一个 `GameObject`（见 4.3），用于承载运行时组件。`ExtData` 构造时：

1. 记录自身/宿主指针的调试字符串（thisId/thisName/baseId/baseName）；
2. 创建 `GameObject` 并 `SetExtData(this)`；
3. 调用 `AttachComponents()` 把该对象类型的"全局脚本"列表挂到 GameObject 下（但不激活，读档时由存档状态决定激活时机）。

析构时 `EnsureDestroy()` 递归销毁所有组件并归还对象池。

### 4.3 组件系统（Component / GameObject / ComponentPool）

组件系统是 Kratos++ 区别于传统 YR 扩展平台的核心设计，类似 Unity 的组件模型。

#### 组件状态机

每个 `Component` 有一个三态状态机：

| 状态 | `_awaked` | `_disable` | 说明 |
| --- | --- | --- | --- |
| Uninitialized | false | false | 刚创建或 Clean 后 |
| Active | true | false | 已唤醒并启用 |
| Disabling | true | true | 已标记禁用，等待 Foreach 结束后移除 |

生命周期接口（`IComponent`）：

- `Awake()`：启用时初始化（如读取 AE 配置、启动计时器）；
- `Destroy()`：销毁时清理；
- `OnUpdate()` / `OnUpdateEnd()`：每帧逻辑更新；
- `ExtChanged()`：宿主类型变化时响应（如变身）；
- `OwnerIsRelease(void*)`：宿主指针销毁时响应；
- `Load` / `Save`：存读档序列化；
- `Clean()`：组件回到对象池时重置。

#### GameObject

`GameObject` 是组件的根容器，每个 `GOExtension::ExtData` 持有一个。它负责：

- 子组件挂载（`AddComponent`）与递归唤醒/销毁（`EnsureAwaked` / `EnsureDestroy`）；
- `Foreach` 遍历结束时统一清理标记为 Disabling 的组件（`OnForeachEnd`）；
- `ExtChanged` 标记传播：宿主扩展数据变化时通知所有子组件。

#### 组件池（ComponentPool）

组件实例统一由单例 `ComponentPool` 管理：

- `Acquire<T>()`：从池中取内存并用 placement new 构造，随后 `ResetForReuse()`；
- `Release(T*)`：析构并归还池；
- `Create(name)`：通过组件工厂按注册名创建（`DECLARE_COMPONENT` 宏自动注册，`ComponentFactory` 维护名称→创建函数映射）；
- `Clear`：场景开始时清空全部组件。

宏 `DECLARE_COMPONENT(CLASS_NAME, ...)` 为每个组件生成：构造函数、`Create()`、`Clone()`、`CopyFrom()`、`FreeComponent()`、静态 `ScriptName` 与自动注册。

#### 脚本组件（ScriptComponent / ObjectScript）

`ScriptComponent` 是挂接在 GameObject 下、能访问宿主游戏对象的组件；`ObjectScript` 进一步支持 Techno 与 Bullet 两种宿主：

- `pTechno` / `pBullet` / `pObject`：通过 `dynamic_cast` 探测宿主类型（`DetectOwnerType`）后访问；
- 提供 `OnInit` / `OnUnInit` / `OnPut` 等 Techno 生命周期回调接口（`ITechnoScript`）。

### 4.4 AE 效果器系统（AttachEffect）

AE（AttachEffect，附着效果）是 Kratos++ 最主要的扩展玩法机制，结构是三层嵌套：

```
GameObject
  └─ AttachEffect（管理器，一个对象一份）
       ├─ AttachEffectScript#0（一条 AE，对应一个 [AE Section]）
       │    ├─ EffectScript#0（效果器：Animation、AutoWeapon……）
       │    ├─ EffectScript#1
       └─ AttachEffectScript#1
            └─ EffectScript#0……
```

#### 数据流

1. **INI 读取**：`[AE Section]` 的所有标签由 `AttachEffectData::Read()` 读入，按 `EFFECT_VAR_*` 宏批量读取各效果器数据（`EffectData` 派生类），并调用 `GetScriptNames()` 生成需要挂载的效果器脚本名列表；
2. **附加**：`AttachEffect::Attach()` 按名单创建 `AttachEffectScript`，每个脚本再创建对应的 `EffectScript` 子组件；支持来源、来源所属、弹头位置、分组（aeMode）、乘客等上下文；
3. **运行**：`AttachEffectScript` 管理一条 AE 的寿命（Duration/InitialDelay/RandomDelay）、暂停（Pause/Recover）、分组冲突、继承（InheritedTo）、死亡判定（IsAlive，任一效果器失效则整条 AE 移除）；
4. **移除**：`TimeToDie()` / `DetachByName()` / 宿主销毁。

#### 效果器与状态器

- **效果器（Effect）**：`src/Ext/EffectType/Effect/*Effect.*`，如 Animation、AutoWeapon、Broadcast、Counter、DamageSelf、ExtraFire、FireSuper、Host、Immune、Info、Mark、Revenge、Stack、Stand、Vector、Vampire、TurretSpin、BodySpin、CrateBuff、AttackBeacon、CountTrigger、Ammo、AmmoTrigger；
- **状态器（State）**：`src/Ext/StateType/State/*State.*`，如 AntiBullet、BlackHole、DamageReaction、Deselect、DestroyAnim、DestroySelf、DisableWeapon、ECM、Freeze、GiftBox、NoMoneyNoTalk、OverrideWeapon、Paintball、Pump、Scatter、Teleport、Transform。

每个效果器由三个文件组成：`XxxData.h`（INI 数据）、`XxxEffect.h/.cpp`（效果器脚本）、可选 `XxxState.h/.cpp`（状态器脚本，用于 TechnoStatus 常驻状态）。`EFFECT_SCRIPT(Xxx)` 宏自动生成 `GetData()` 并命名脚本。

### 4.5 状态组件（TechnoStatus / StateScript）

`TechnoStatus` 是每个 Techno 的基础组件之一（`TechnoExt::AddGlobalScripts` 注册：AircraftPut、TechnoStatus、AttachEffect），承担单位级别的常驻逻辑：

- 替身管理（SetupStand / AmIStand / StandArray）；
- 空袭（SetAirstrike / CancelAirstrike）；
- 目标激光（StartTargetLaser / CloseTargetLaser）；
- 炮塔/车身旋转（TurretSpin / BodySpin）；
- 状态效果器的托管（通过 `StateScript` 挂载各 `XxxState`）；
- 武器相关状态（FireFLH、DeployTo、Passengers、AirstrikeData 等）。

状态器与效果器的区别：效果器挂在 `AttachEffectScript` 下、随 AE 生命周期；状态器常驻在 TechnoStatus 下，可被多个来源的标签开关（如 `[TechnoType]` 直接启用 Freeze/Paintball 等），并通过 `StateEffectScript` 与 AE 联动。

### 4.6 INI 读取系统

`src/Common/INI/` 提供了一套不直接依赖 CCINIClass 的缓存读取机制：

- **依赖链**：`INI::MakeDependency()` 按游戏模式（战役/遭遇战）生成文件依赖列表，如 `rules = [Map.ini, GameMode.ini, rulesmd.ini]`，保证地图/模式覆盖规则；
- **缓冲**：`INIBufferManager` 按（依赖列表，Section）缓存解析结果 `INILinkedBuffer`，避免重复解析；
- **读取器**：`INIBufferReader` 提供类型安全的 `Get<T>` / `GetList<T>` / `GetChanceList` / `GetPercent` / `GetDir16` 等，底层通过 `Parser<T>` 特化解析（`Utilities/Parser.h` 与 `Ext/Helper/StringEx.h`）；
- **配置基类**：`INIConfig` 定义 `Read(INIBufferReader*)` 与序列化接口，所有数据类（EffectData、StateData、TypeData）继承它。

全局段（`[CombatDamage]`、`[AudioVisual]`、`[General]`、`[SideType]` 等）与类型段（`[TechnoType]`、`[WeaponType]` 等）的"通用设置"由各 TypeData 的 `Read()` 统一读取并合并。

### 4.7 存档/读档系统

扩展数据通过 `ExStreamReader` / `ExStreamWriter`（`Utilities/Stream.h`）序列化，写入游戏存档流：

- **对象级**：每个游戏对象的 `SaveToStream` / `LoadFromStream` 由对应 Ext 实现，`GOExtension::Serialize()` 先写自身数据再写 GameObject（组件树由组件各自实现 Load/Save）；
- **全局级**：`ExtTypeRegistry::SaveGlobals / LoadGlobals` 在存档头/尾写入全局状态（如 GameModeName），通过 C++20 concept 自动判断哪些扩展实现了 `GlobalSaveLoadable`；
- **存档标识**：`SAVEGAME_ID`（由 Version.h 版本号组成）写入 `SavegameInformation.InternalVersion`，读档时校验，版本不兼容的存档会被拒绝。

注册表分发（`src/Extension.cpp`）：

```
TypeRegistry<AnimExt, BulletExt, TechnoExt, ……>
  ├─ Clear()               → ScenarioClearClassesEvent
  ├─ InvalidatePointer()   → PointerExpireEvent
  ├─ DetachAll()           → DetachAll 事件
  ├─ SaveGlobals()         → 0x67D32C（SaveGame）
  └─ LoadGlobals()         → 0x67E826（LoadGame）
```

新增扩展类型只需把类名加入 `TypeRegistry<>` 模板参数列表，即可自动接入清空/指针失效/存读档流程（基于 concept 的编译期分发，无虚函数开销）。

### 4.8 Hook 系统

Hook 通过 YRpp 的 `DEFINE_HOOK(地址, 名称, 指令长度)` 宏实现，在静态初始化阶段把游戏函数入口改写为跳转到钩子函数（`Utilities/Patch.h` + `Helpers/Macro.h`）。

常用宏：

- `DEFINE_HOOK` / `DEFINE_HOOK_AGAIN`：一个钩子函数复用多个地址；
- `GET(reg, 变量)` / `GET_STACK(reg, 偏移)` / `REF_STACK`：从寄存器/栈读取参数；
- `DEFINE_JUMP`：无条件跳转（如进程退出接管）；
- `DEFINE_PATCH`：静态字节补丁；
- `NAKED` + `SET_REG32` / `CALL`：内联汇编跳板。

钩子职责：**只负责捕获时机与参数，然后调用组件/管理器/事件系统**，不直接实现业务逻辑。

### 4.9 调试与日志

- `Debug::Log` 系列（`Utilities/Debug.h`）：Debug 构建输出到控制台与日志文件；`FatalErrorAndExit` 崩溃出口；
- `SyncLogging`（`Utilities/SyncLogging.h` + `SyncLogging.cpp`）：环形缓冲记录 RNG 调用、朝向变化、目标变化等，`-SYNCLOG` 命令行开启，用于排查联机不同步；
- `AsyncLogging`：2026-08 新加入的异步日志工具包；
- `Common::DetachFromDebugger()`（Debug 构建）：启动时弹出"附加调试器"提示，并自动终止 Syringe 以便附加 VS 调试器；
- `-DebugAE`（仅 Debug 构建）：AE 调试开关。

## 5. 关键数据流

### 5.1 进程启动

```
Syringe 注入 Kratos.dll
  → DllMain (DLL_PROCESS_ATTACH)
  → 静态对象构造：各 Hook 类构造函数注册事件处理器
  → YR_Boot hook (0x52BA60)
  → ExeRun hook (0x7CD810) → EventSystems::General.Broadcast(ExeRun)
       ├─ Common::ExeRun：应用静态补丁、Debug 附加调试器流程
       └─ Kratos::ExeRun：加载初始化
  → CmdLineParse hook (0x52F639) → 解析 -SYNCLOG 等参数
  → 进入主循环
```

### 5.2 单位创建/销毁

```
TechnoClass_CTOR (0x6F3260) → TechnoExt::ExtMap.TryAllocate(unit)
  → ExtData 构造：创建 GameObject、AttachComponents（AircraftPut/TechnoStatus/AttachEffect）
TechnoClass_Init (0x6F42ED) → GameObject->Foreach(ITechnoScript::OnInit)
TechnoClass_Put → Foreach(OnPut)
每次 Foreach 结束 → 清理 Disabling 组件、传播 ExtChanged
TechnoClass_DTOR (0x6F4500) → Foreach(ITechnoScript::OnUnInit) → ExtMap.Remove
  → ExtData 析构 → GameObject::EnsureDestroy → 各组件 Destroy → 组件归还对象池
```

### 5.3 AE 附加/运行/移除

```
弹头爆炸 / 武器反馈 / TechnoType 携带
  → AttachEffect::Attach(AttachEffectData)
       → 校验：冲突类型、金额、单次、继承规则
       → 创建 AttachEffectScript（含 Duration/InitialDelay/分组）
       → 按 GetScriptNames() 挂载各 EffectScript 子组件
  → 每帧：AttachEffectScript 检查寿命计时
       → 各 EffectScript.OnUpdate() 执行效果
       → IsAlive() 任一失效 → 整条 AE 移除
  → TimeToDie() / DetachByName() / 宿主死亡 → 逐级销毁
```

### 5.4 存读档

```
存：TechnoClass_SaveLoad_Prefix → ExtMap.PrepareStream
    → TechnoClass_Save_Suffix → ExtMap.SaveStatic → ExtData::SaveToStream
    → GameObject::Save → 各组件 Save
    → SaveGame_Ext (0x67D32C) → ExtTypeRegistry::SaveGlobals
读：TechnoClass_SaveLoad_Prefix → ExtMap.PrepareStream
    → TechnoClass_Load_Suffix → ExtMap.LoadStatic → ExtData::LoadFromStream
    → GameObject::Load（按 InstanceId 匹配组件，清理多余组件，_awaked 状态恢复）
    → LoadGame_Ext (0x67E826) → ExtTypeRegistry::LoadGlobals
```

## 6. 设计要点与权衡

1. **预编译替代动态编译**：功能全部静态编译，启动更快、体积更小、无运行时编译风险；代价是新增功能必须重新编译 DLL。
2. **组件化替代单一大类**：每个 Techno 只有一个 ExtData + GameObject，功能以组件（脚本）形式挂载，新增功能不修改既有类，降低耦合。
3. **对象池复用**：组件频繁创建/销毁（AE 是最典型的场景），对象池避免堆碎片与分配开销；代价是组件必须正确实现 `Clean()` 以复位状态。
4. **事件解耦**：Hook 只负责广播，逻辑通过事件注册，便于多个功能监听同一时机而不互相侵入。
5. **编译期注册分发**：`ExtTypeRegistry` 用 C++20 concept + fold expression 在编译期展开，无虚函数、无运行时反射，兼顾扩展性与性能。
6. **存读档兼容优先**：组件树按 InstanceId 匹配、每个组件自带序列化，`SAVEGAME_ID` 版本校验，最大限度保证旧档可读。
7. **兼容性**：部分全局行为提供开关（如 `AllowTakeoverPhobosShadowMaker`、`AllowAnimDamageTakeOverByKratos`），避免与 Ares/Phobos 冲突时强行接管。
