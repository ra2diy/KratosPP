# 替身渲染层级与遮挡（2026-10-04 复核）

> 起因：开局崩溃已修复。接着需要厘清三件事 ——
> ① AE 附加的动画为什么被 Jumpjet 遮挡；② `Stand.ZOffset` 有没有被考虑；
> ③ 本次改动是否"只换了渲染顺序"，不影响层级 / 遮挡。
>
> 全部结论来自 `gamemd` 反汇编（IDB 副本）与 Phobos / Antares / SyringeEx 源码，
> 证据文件见文末「证据索引」。

---

## 0. 结论速览

| 问题 | 结论 |
| --- | --- |
| 本次改动动了什么 | **只动 Air 层层内下标顺序**（`DisplayClass::Submit` 出口的指针搬运）。 |
| 有没有影响"层级" | **没有**。层级（进哪个层数组）由 `StandLayer`（5 个 loco 的 `InWhichLayer` 替换）决定，本轮未改。 |
| 有没有影响"遮挡" | **有，而且这正是它唯一的机制**。YR 没有 Z-buffer，"遮挡"就是绘制先后；同层内下标大者后画 ⇒ 在上。 |
| `Stand.ZOffset` 有考虑吗 | **上一版没有，是个真漏洞**：Air 层从不被引擎排序 ⇒ 空中替身的 ZOffset 完全失效。本轮已补。 |
| 顺带发现的 bug | 上一版的分区方向**写反了**，把替身排到 Master **之前**（下层），与函数名 `KeepStandAboveMaster` 及注释都相反。本轮已修。 |
| AE 动画被 Jumpjet 遮挡 | **不是本 Hook 的事**。根因在 `AnimClass::InWhichLayer`（0x424CB0）的 vanilla 语义 + AE 未设置 `OwnerObject`；属 Phobos `Layer_UseObjectLayer` 的职责面。 |

## 1. YR 的渲染模型：只有两个旋钮，没有 Z-buffer

### 1.1 绘制顺序

`Tactical_Draw_All_6D8DB0`（`0x6D8DB0`）的结构：

```
外层：层号 eax = 0..4                     0x6D8F19 lea ebx,[eax+eax*2] / shl 3   → &vec_ObjectsInLayers[lyr]
      0x6D95A1 inc eax ; cmp eax,5 ; jl 0x6D8F19        ← 层号升序
内层：下标 ecx = 0..Count-1
      0x6D8F39 mov eax, vec_ObjectsInLayers.data[ebx]
      0x6D8F43 mov esi, [eax+ecx*4]                     ← Items[index]
      ...
      0x6D93FA call dword ptr [edx+104h]                ← 主体绘制
      0x6D93DA mov byte ptr [esi+99h], 1                ← 标记"需要第二遍"
      0x6D9410 mov ecx, vec_ObjectsInLayers.length[ebx]
      0x6D941D jl 0x6D8F39                              ← 下标升序
第二遍（DrawExtras）：0x6D95AF 起，同样层号升序 × 下标升序，只画 [obj+99h] != 0 的
      ⇒ vt+0x110
```

⇒ **绘制顺序 = 层号升序 × 层内下标升序。下标越大越后画 ⇒ 越在上。**

### 1.2 引擎只排序 Ground 层

`Main_Loop`（`0x55D360`）里每帧一趟：

```
0055DBBE  call GScreenClass_DrawOnTop
0055DBC3  mov  ecx, offset unk_8A0390     ← 0x8A0360 + 2*0x18 = Ground 层对象
0055DBC8  call sub_551A30                 ← LayerClass::Sort
```

（`0x8A0360` = `vec_ObjectsInLayers` 基址，`sizeof(LayerClass) == 0x18`；
`Ground(2)` = `0x8A0390`，`Air(3)` = `0x8A03A8`。）

`LayerClass::Sort`（`0x551A30`，共 0x55 字节）是**单趟相邻冒泡、没有外层循环**：

```
00551A37  mov eax,[ebp+10h] ; dec eax ; test/jle            ← Count-1
00551A44  mov esi,[eax+ebx*4+4]                             ← Items[i+1]
00551A48  mov edi,[eax+ebx*4]                               ← Items[i]
00551A4F  call dword ptr [edx+0B8h]                         ← ysort(Items[i+1])
00551A5D  call dword ptr [eax+0B8h]                         ← ysort(Items[i])
00551A63  cmp var_4, eax ; jge skip                         ← 若 ysort(i+1) >= ysort(i) 不换
          …交换…
00551A79  inc ebx ; dec eax ; jl 0x551A41
```

⇒ 按 `vt[0xB8]`（`GetYSort`）**升序**排一趟；因为只走一趟，它本身**没有自愈能力**，
只是把"插入时基本有序"的数组维持住。

### 1.3 `Submit` 只给 Ground 开有序插入

`DisplayClass::Submit`（`0x4A9720`）：

```
004A972A  cmp dword ptr [esi+94h], -1 ; jz 0x4A9739        ← LastLayer == -1 则跳过 Remove
004A9734  call DisplayClass::Remove
004A973D  call dword ptr [eax+78h]                          ← InWhichLayer() → edi
004A9742  cmp edi,-1 ; jz 0x4A9768                          ← Layer::None → 退出
004A9747  cmp edi, 2
004A974D  setz cl                                           ← ★ sortable = (layer == 2) 仅 Ground
004A9759  call MapClass_AddObjectToALayerX                  ← 0x5519B0
004A975E  test al,al ; jz 0x4A9768
004A9762  mov [esi+94h], edi                                ← LastLayer = layer
004A9768  pop edi ; pop esi ; retn 4
```

`AddObjectToALayerX`（`0x5519B0`）两个分支：

```
sortable != 0 → 005519C0 call MapClass_AddObjectToALayer (0x551A90)   ← 有序插入
sortable == 0 → 00551A0A mov eax,[esi+10h]
                00551A13 mov [esi+10h], ecx                          ← Count++
                00551A1A mov [edx+eax*4], ecx                          ← Items[Count-1] = obj
                ⇒ 纯追加到队尾
```

而有序插入 `0x551A90` 的下标 0 起线性扫描，比较器是
`ObjectClass::CompareYSortValues`（`0x5F6220`，调用点 `0x551ADB`）：

```
00551AD4  mov eax,[esi+4]                                  ← Items
00551AD8  mov ecx,[eax+edi*4]                              ← Items[i]
00551ADB  call ObjectClass_CompareYSortValues
00551AE2  jnz loc_551AEC                                   ← 命中即在此位插入，其后整体右移
```

**⇒ 结论：**

| 层 | 插入方式 | 每帧排序 | 顺序由谁决定 |
| --- | --- | --- | --- |
| Ground(2) | 有序插入（按 YSort） | 有（`0x55DBC8` 单趟冒泡） | 引擎 + `GetYSort` |
| Surface(1) / Air(3) / Top(4) / Underground(0) | **纯追加到队尾** | **无** | **插入顺序**（= Kratos 的 Hook） |

## 2. Kratos 的替身有三套机制，各自管一个旋钮

| 机制 | 落点 | 管什么 |
| --- | --- | --- |
| `StandLayer::GetLayer` | `0x75C7E0` / `0x6A3E50` / `0x5B19D0` / `0x517100` / `0x4B4820`（5 个 loco 的 `InWhichLayer`） | **进哪个层数组**（层级）。替身取 `pMyMaster->LastLayer`。 |
| `StandLayer`（原 `StandYSort`） | `0x5F6BF7`（`ObjectClass::GetYSort` 内） | **排序键**：替身取 `master->GetRenderCoords() + ZOffset`。只经 Ground 的排序/有序插入生效。<br>★ 2026-10-05：原 `pSkip/pStand/X/Y` 跨调用缓存**已整组删除**（报告 §12.6(1) 判定零影响），现为无状态纯键改写。 |
| `StandLayer::ZAdjust`（原 `StandZAdjust`） | `0x4DB091`（`FootClass::GetZAdjustment`） | **精灵的屏幕纵向偏移**（顺带影响 `GetYSort` 的输入坐标）。 |
| `StandLayer::Classify` + 本轮改的 | `0x4A9768`（`DisplayClass::Submit` 出口） | **Air 层的层内下标顺序**（= Air 层唯一的遮挡机制）。 |

> ★ 2026-10-05：上述四处**已统一收进 `namespace StandLayer`**（顶层只留一个名字，子空间按"回答哪个问题"划分；
> 原 `StandLayerFix` / `StandYSort` / `StandZAdjust` 三个并列名已取消），见 `MEMORY.md 2026-10-05 §二十二`。

**所以"替换渲染顺序"和"层级/遮挡"不是两件事：**

- 换的是"Air 层内谁先谁后"；
- 而在 Air 层内，**先后就是遮挡**（没有别的机制）；
- 但跨层不会被影响 —— 下标再怎么排，Air 层的对象永远画在 Ground 层之后。

## 3. `Stand.ZOffset` 为什么对空中替身失效

`GetYSort`（`vt[0xB8]`，实现 `0x5F6BD0`）= `coords.X + coords.Y`（内部两次 `call [eax+0ACh]` 取坐标）。
Kratos 在 `0x5F6BF7` 处改写这两个坐标分量（`*x = r.X + offset; *y = r.Y + offset;`）。

**谁消费 `GetYSort`？**（对 `0x5F6BD0` 的全量直接调用扫描）

```
call @00422BC3   in AnimClass_ReturnRealYSort
call @00449413   in BuildingClass_B8
call @00551A4F   （LayerClass::Sort 内，vt 间接调用）
call @00551A5D   （LayerClass::Sort 内，vt 间接调用）
call @00551ADB   （AddObjectToALayer 有序插入内，vt 间接调用 0x5F6220→比较器）
```

全部集中在：**Ground 层的每帧排序** + **Ground 层的有序插入**。

**⇒ `Stand.ZOffset` 只对 Ground 层的替身有效。**
地面单位 / 建筑上的替身照旧工作；挂在 Jumpjet 上的替身（Air 层）**完全不参与任何排序**，
所以上一版改成"提交时刻强制定位"之后，`Stand.ZOffset` 对空中替身**彻底失效** ——
既不能上移，也不能下移（负值也无效）。这是一个真实的功能回退，本轮已补。

## 4. 本轮修正

### 4.1 修掉的 bug：分区方向反了

上一版（`0x4A9768`）的实现是"把本 Master 的替身稳定搬到 `[0, count-1)` 的末尾"：

```
原数组（Master 刚落队尾）： [ S1, A, B, S2, Master ]
分区后：                    [ A, B, S1, S2, Master ]     ← 替身下标 2,3 < Master 下标 4
```

注释写的是"结果：… items[count-1] = Master ⇒ 所有替身的下标都**大于**其 Master"，
但 `items[count-1] = Master` 意味着 Master 的下标是**最大**的 —— 结论与自身前提矛盾。
按绘制规则（下标大者在上），这会把替身排到 Master **下面**。

**为什么之前没暴露**：该 Hook 只在"**非替身的 Techno 被提交进 Air 层**"时动作。
Jumpjet 的重新提交发生在 `JumpjetLocomotionClass_Process`（`0x54B18E`，带状态变化守卫），
不是每帧；平时替身是按自然顺序追加的（晚于 Master ⇒ 天然在上），
所以常见情况下 Hook 根本不触发，看起来"能用"。一旦宿主换层重提交，它就会把替身压到下面。

### 4.2 新实现：按 `ZOffset` 正负摆位

只在 `DisplayClass::Submit` 出口、`layer == Air`、对象是 Techno 时动作；
只搬指针，无静态状态、无堆分配、无函数调用（除只读的 ExtMap 查询），O(1) 额外空间。

```
R1  刚入队的是【替身】
      ZOffset >= 0 → 什么都不做（队尾天然在 Master 之上）
      ZOffset <  0 → 把队尾的它左移到其 Master 之前  ⇒ "负值在下层"

R2  刚入队的是【Master】，且层内已有它的替身
      对 [0, count-1) 做稳定三分类：
         A「其它对象」 / D「本 Master 的替身且 ZOffset < 0」 / U「本 Master 的替身且 ZOffset >= 0」
      再把队尾的 Master 左移到"第一件 U 之前"
      ⇒ 最终布局 [ A..., D..., Master, U... ]
```

额外守卫：

- `abstract_cast<TechnoClass*>` 为 null ⇒ 直接返回（**动画 / 子弹不受影响**）；
- `count > pLayer->Capacity` ⇒ 数组已被破坏，不做任何写入；
- `items[count-1] != pObject` ⇒ 不假设队尾身份，不动作；
- 找不到 Master（R1）⇒ 不动作；
- 没有 U（R2）⇒ 不动作（全部要求在下层时原顺序已正确）。

> **联机安全性**：Hook 仍是"数组内容的纯函数"（分类只读 ExtMap 与 INI 数据），
> 不引入时间/随机/本地状态；只要两端 `Submit` 调用序列一致，产出的顺序就一致。
> 它**不排序、不引入新的校验值输入**，与已删除的 `0x55DBC3`（每帧整层排序）性质不同。

## 5. AE 附加动画为什么被 Jumpjet 遮挡（归属：Phobos）

### 5.1 vanilla 语义

`AnimClass::InWhichLayer`（`0x424CB0`，Phobos 在此处 hook 6 字节）：

```
00424CB0  mov  eax, [ecx+0CCh]          ; AnimClass::OwnerObject
00424CB6  test eax, eax
00424CB8  jz   0x424CC0
00424CBA  mov  eax, 2                   ; ⇒ return Ground(2)
00424CBF  retn
00424CC0  mov  eax, [ecx+0C8h]          ; AnimClass::Type
00424CC6  test eax, eax
00424CC8  jz   0x424CD1
00424CCA  mov  eax, [eax+364h]          ; ⇒ Type->Layer
00424CD0  retn
00424CD1  mov  eax, 3                   ; ⇒ return Air(3)
```

`OwnerObject` 就是在 `+0xCC`：`AnimClass::Attach_To`（`0x424B50`）里
`00424C37 mov [esi+0CCh], edi`（edi = 新宿主），随后 `00424C7C call DisplayClass::Submit`。

⇒ **只要动画有 `OwnerObject`，vanilla 一律把它放进 Ground 层**，与宿主的层无关。
Jumpjet 在 Air(3)，动画在 Ground(2)，Air 后画 ⇒ **动画被 Jumpjet 盖住**。这正是观察到的现象。

### 5.2 Phobos 的解法

`Phobos/src/Ext/Anim/Hooks.cpp:352`：

```cpp
DEFINE_HOOK(0x424CB0, AnimClass_InWhichLayer_AttachedObjectLayer, 0x6)
{
    enum { ReturnValue = 0x424CBF };
    GET(AnimClass*, pThis, ECX);
    if (pThis->OwnerObject)
    {
        auto const pTypeExt = AnimTypeExt::Fetch(pThis->Type);
        if (pTypeExt->Layer_UseObjectLayer.isset())
        {
            Layer layer = pThis->Type->Layer;
            if (pTypeExt->Layer_UseObjectLayer.Get())
                layer = pThis->OwnerObject->InWhichLayer();   // ← 继承宿主层
            R->EAX(layer);
            return ReturnValue;
        }
    }
    return 0;
}
```

⇒ 让附加动画继承宿主层（`Layer_UseObjectLayer=yes`）之后，动画与 Jumpjet 同在 Air 层，
层内按插入顺序：动画晚于 Jumpjet 创建 ⇒ 排在后面 ⇒ 在上。

### 5.3 Kratos 这边

Kratos 的 AE（`AnimationEffect`）创建动画后只做了两件事：

```cpp
// src/Ext/EffectType/Effect/AnimationEffect.cpp
pIdleAnim = GameCreate<AnimClass>(pAnimType, location);
SetAnimOwner(pIdleAnim, pTechno);                  // 只写 pAnim->Owner（阵营）
GetStatus<AnimExt, AnimStatus>(pIdleAnim)->AttachToObject(pObject, offsetData);
                                                   // 只记录 pAttachOwner 并每帧挪位置
```

`SetAnimOwner`（`src/Ext/Helper/Status.cpp`）只设 `pAnim->Owner`；
`AnimStatus::AttachToObject` 只设扩展里的 `pAttachOwner`。
**两者都没有调用 `AnimClass::SetOwnerObject`** ⇒ `OwnerObject` 保持 null
⇒ 动画走 vanilla 的 "`Type->Layer`" 分支，取 `[AnimType]` 的 `Layer=` 值。

而 **Kratos 没有 `Layer_UseObjectLayer` 这个功能**（全库 grep 为空）。

### 5.4 为什么 Phobos 的现成方案对 Kratos 的 AE **不适用**（2026-10-04 补充）

Phobos 那套解法从头到尾挂在 `OwnerObject` 上：

```cpp
// Phobos/src/Ext/Anim/Hooks.cpp:352 —— 入口就要求 OwnerObject 非空
DEFINE_HOOK(0x424CB0, AnimClass_InWhichLayer_AttachedObjectLayer, 0x6)
{ ... if (pThis->OwnerObject) { ... } return 0; }

// Phobos/src/Ext/Anim/Body.Internal.cpp:259 —— 也按 OwnerObject 反查归属
void TechnoExt::UpdateAttachedAnimLayers(TechnoClass* pThis)
{
	if (!pThis->HasParachute) return;
	for (auto const pAnim : AnimClass::Array)
	{
		if (pAnim->OwnerObject != pThis) continue;   // ← 只认 OwnerObject
		DisplayClass::Instance.Submit(pAnim);
	}
}
```

而 **Kratos 的 AE 刻意不设 `OwnerObject`** —— 这是既定设计：
`SetOwnerObject` 是强关联，动画被移除/UnInit 时容易留下悬挂指针。
（`AnimationEffect::KillIdleAnim` 里那句注释 `// 包含了 SetOwnerObject(0) 0x4255B0`
正是这个链条的痕迹。）Kratos 自己改用 `AnimStatus::pAttachOwner` 这个**弱引用**
（带 `ObjectUnInitEvent` 处理器）来表达附着关系。

⇒ 两条推论：

1. Phobos 的 `Layer_UseObjectLayer` 与 `UpdateAttachedAnimLayers` **都会跳过 Kratos 的 AE 动画**；
2. Kratos 侧的解法**同样不能依赖 `OwnerObject`**，必须走 `pAttachOwner`。

### 5.5 Kratos 侧方案（**已实施**，2026-10-05 落地 + 2026-10-06 迁址）

分两步，都不触碰 `OwnerObject`：

**第 1 步 · 层跟随宿主** —— hook `0x424CCA`（`AnimExtHook.cpp` `AnimClass_InWhichLayer_FollowAttachOwner`，size `0x6`）：

```
00424CB0  8B 81 CC 00 00 00     mov  eax,[ecx+0CCh]   ; OwnerObject   ← Phobos 的 hook 占这里
00424CB6  85 C0                 test eax,eax
00424CB8  74 06                 jz   0x424CC0
00424CBA  B8 02 00 00 00        mov  eax,2            ; Ground
00424CBF  C3                    retn
00424CC0  8B 81 C8 00 00 00     mov  eax,[ecx+0C8h]   ; AnimClass::Type
00424CC6  85 C0                 test eax,eax
00424CC8  74 07                 jz   0x424CD1
00424CCA  8B 80 64 03 00 00     mov  eax,[eax+364h]   ; Type->Layer   ← ★ 落点：恰好一条 6 字节指令
00424CD0  C3                    retn                  ; ← 覆盖时显式 return 0x424CD0
00424CD1  B8 03 00 00 00        mov  eax,3
00424CD6  C3                    retn
```

handler：`pThis` 是 Kratos 的 AE 动画且 `pAttachOwner` 存活 ⇒ `R->EAX(max(Type->Layer, pAttachOwner->LastLayer))`
（**只升不降**），`return 0x424CD0`；否则 `return 0` 走原逻辑（重放 6 字节 → 落 `0x424CCF` 的 NOP → `0x424CD0` 的 `retn`）。

| 选它的理由 | 说明 |
| --- | --- |
| 满足落点契约 | 6 字节 = 一条完整指令 `mov eax,[eax+364h]`；`return 0` 的重放块长度与声明 size 相等，回跳 `addr+5` 落在 NOP 填充上；覆盖路径直接跳到 `0x424CD0` 的 `retn` |
| **不与 Phobos 同址** | Phobos 占 `0x424CB0`（6 字节 → `0x424CB0..0x424CB5`），`0x424CCA..0x424CCF` 与 Ares / Phobos / Kratos 三边均不重叠。⚠️ 初版曾直接挂在 `0x424CB0`；因 SyringeEx 的链式语义（hook 返回非 0 ⇒ 立即跳转、**跳过链上后续 hook 与原始指令重放**），那会静默掐掉 Phobos 的 `Layer_UseObjectLayer` |
| 天然只作用于目标 | 该处只在 `OwnerObject == nullptr` 且 `Type != nullptr` 的分支上，即"没有强关联的动画" |
| 不引入强关联 | 读的是弱引用 `pAttachOwner`，不影响 Kratos 原有的生命周期设计 |
| 联机安全 | 纯读 + 确定性输入（AE 状态 + `LastLayer`），同一帧两端结果一致 |
| 取 `LastLayer` 而非 `InWhichLayer()` | `LastLayer`(`+0x94`) 只由 `DisplayClass::Submit` 写，是"宿主**当前所在层数组**的索引"，与第 2 步的监视器同源；避免"宿主 `InWhichLayer()` 已变但尚未重提交 ⇒ 动画先跳层、宿主后提交把动画压回去"的反向遮挡，也免掉一次虚调用与 `FootClass` locomotor 的空指针路径 |

**第 2 步 · 顺序跟随宿主**（`AnimStatus::OnUpdate`，2026-10-05 实施）：`InWhichLayer` 一旦跟随宿主，
动画与宿主进入**同一个层数组**，而 Air/Top 层不做 `LayerClass::Sort` ⇒ 绘制顺序 = `Submit` 顺序。
监视宿主 `LastLayer` 变化时调用引擎 `DisplayClass::Instance->Submit(pAnim)` 重新入队，
使动画重新追加到宿主之后。**两环不可互替**：重提交只能在**同一层数组内**重排，跨层只能靠第 1 步。

⚠️ **触发范围（实测，务必记住）**：第 1 步只在 `宿主层 > Type->Layer` 时改写。`[AnimType] Layer` 默认是
**Air(3)**（`0x4276D4: C7 86 64 03 00 00 03 00 00 00`），而全引擎 12 个 locomotor 里**只有 `Fly`(`0x4CFCF0`)
会返回 Top(4)**（`GetHeight()>0 ⇒ 4`，否则 2）；`Jumpjet`(`0x54B8D0`) 原本可到 4，但被本项目的
`0x54B8E9` 钉死在 Air(3)。⇒ **对 Kirov/ZEP 这类 Jumpjet 宿主，第 1 步恒为空转**，ZEP+MININUKE
的现象完全由第 2 步解决；第 1 步承重的是 **Fly 机动的飞机宿主**（动画默认 Air(3)，宿主在 Top(4)，
不跨层就会被飞机整层盖住）以及 art 里**显式写 `Layer=ground/surface/underground`** 的 AE 动画。

> 原建议里的"加一个开关（`Animation.LayerFollowHost`，默认关）"**未采纳**：开关会让同一份
> 地图/模组在不同设置下产出不同的层数组顺序，反而扩大联机分歧面；改为无条件按上述条件生效。
