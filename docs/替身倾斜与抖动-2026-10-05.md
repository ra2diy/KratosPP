# 替身（Stand）倾斜与抖动 —— 机理分析、根因定位与修复

- 日期：2026-10-05
- 范围：`StandEffect` 附着在 Master 上之后的**视觉倾斜同步**与**位置抖动**
- 约束：**不得引入联机失同步**
- 结论：**找到并使单一根因闭环 —— 把「角度」写进了「每帧步进量」字段**，导致替身自己的倾斜积分器无界累积。已修复、已编译、已部署。
- 涉及代码：`src/Ext/EffectType/Effect/StandEffect.cpp`（`OnGScreenRender` / `UpdateStateTechno` / `SetLocation`）
- **本轮未新增或改动任何 Hook，落点表无变化**（`docs/Hook地址冲突清单.md` 无需更新）

---

## §0 结论速览

用户报的两个现象：

1. Stand 附着在 Master 身上之后，**Master 移动时 Stand 会抖动**；
2. Master 处于**坠落/下沉**时（战列舰），**炮塔（Stand）脱离船身，自己往一边倾斜**。

| # | 现象 | 根因 | 证据 | 处置 |
| --- | --- | --- | --- | --- |
| **R1** | 抖动 + 下沉时自转脱体 | `OnGScreenRender` 把 Master 的**角度** `AngleRotated*` 写进了替身的**每帧步进量** `Rocking*PerFrame`。引擎对每个 voxel 单位每逻辑帧做一次 `AngleRotated += Rocking`，于是替身每帧在自己的角度上再加一份 Master 的完整角度 ⇒ **无界累积**。 | `StandEffect.cpp` 旧代码 `pStand->RockingForwardsPerFrame = forwards;`；引擎积分器 `0x70B649`/`0x70B659`、`0x70B65F`/`0x70B66B`；调用点 `0x6FA236` | ✅ **已修**：`Rocking*PerFrame = 0`（步进量清零，角度只由主身单向驱动） |
| **R2** | 倾斜角在替身体坐标系里算错 | 原实现用手写 8 分支处理 `Offset.Direction`：`0/2/6/14` 是**空实现**（完全不旋转），`8` **漏了对 `forwards` 取反**。 | `StandEffect.cpp` 旧 `switch (Data->Offset.Direction)` | ✅ **已修**：改成按两端真实朝向差做连续二维旋转，自动覆盖 16 个方向 |
| **R3** | 下沉时炮塔掉到水面 | `SetLocation` 的 `StickOnFloor` 分支在 `pTechno->GetHeight() <= 0` 时无条件 `SetHeight(0)`；主身下沉/坠落时其 Z 由沉没逻辑支配，把替身压到**自身格子**的地面高度会与主身分离。 | `StandEffect::SetLocation` | ✅ **已修**：主身 `IsSinking` / `IsCrashing` 时不强制贴地 |
| — | 「Offset 位置算法不含倾斜」这一猜想 | **不成立（已排除）** | `GetMatrix3D` = `Locomotor->Draw_Matrix`，而 `Draw_Matrix` 的实现（`DriveLocomotionClass` 的 vt+0x24 = `0x4AFF60`、`ShipLocomotionClass` 的 `0x69F670`）**本身就读 `AngleRotated*`** ⇒ Offset 已经随主身倾斜一起转 | 无需改动 |

## §1 引擎的倾斜模型（IDA 实证）

### 1.1 倾斜更新器 = `TechnoClass` 虚表槽 `+0x41C`

```
0x006FA224  mov  edx, [esi+vt]
0x006FA228  call [edx+vt_TechnoClass.IsVoxel]      ; 门控：只有 voxel 单位才走
0x006FA22E  test al, al
0x006FA230  jz   short done_voxel                  ; 非 voxel ⇒ 跳过整个倾斜更新
0x006FA232  mov  eax, [esi+vt]
0x006FA236  call [eax+vt_TechnoClass.Techno_41C]   ; ★ 倾斜更新
```
- 所属函数：`TechnoClass::Update`（`0x6F9E50`，`TechnoClass` 虚表槽 `[0x05C]`）。
- 槽位校验：`TechnoClass` 虚表基址 `0x007F4960`，`dword @ 0x7F4D7C = 0x70B570`，而 `0x7F4960 + 0x41C = 0x7F4D7C` ✓
- `TechnoClass_41C` 的唯一代码引用就是这一处（全 `.text` 内 `call [reg+0x41C]` 仅 1 处）。其余 5 处 `XrefsTo` 全是各子类虚表（`FootClass` / `InfantryClass` / `UnitClass` / `AircraftClass` / `BuildingClass`）—— 即该虚函数未被任何子类覆盖。
- ⇒ **每个 voxel 单位，每逻辑帧跑一次倾斜更新。替身自己也是 `TechnoClass` / voxel，所以替身也会跑一次。**
- ⇒ 这也是为什么用户在「地面步兵」场景下问题不显眼：**步兵是 SHP，不是 voxel，直接跳过整个倾斜更新**。

### 1.2 字段偏移的真相（一个容易踩的坑）

IDB 里的结构体成员名比**真实偏移小 4 字节**（历史命名遗留）。以 `0x70B570` 的机器码逐字节核对：

| IDB 符号名 | 真实偏移 | YRpp 字段名 |
| --- | --- | --- |
| `_TechnoClass.t.field_324` | **0x328** | `AngleRotatedSideways` |
| `_TechnoClass.t.field_328` | **0x32C** | `AngleRotatedForwards` |
| `_TechnoClass.t.field_32C` | **0x330** | `RockingSidewaysPerFrame` |
| `_TechnoClass.t.field_330` | **0x334** | `RockingForwardsPerFrame` |
| `_TechnoClass.t.field_3C9` | **0x3CD** | `IsSinking` |
| `_TechnoClass.t.field_421` | **0x425** | `IsCrashing` |

**交叉校验（三路一致，可信）**
1. `YRpp` 的声明顺序是 `AngleRotatedSideways / AngleRotatedForwards / RockingSidewaysPerFrame / RockingForwardsPerFrame`（4 个连续 float，`TechnoClass.h:656-663`）。
2. `TechnoClass::GetCRC`（`0x70C270`）按这个顺序把它们逐个喂 `CRC_float`：
   ```
   0x70C3D4  mov ecx,[esi+328h] ; AngleRotatedSideways
   0x70C3E2  mov edx,[esi+32Ch] ; AngleRotatedForwards
   0x70C3F0  mov eax,[esi+330h] ; RockingSidewaysPerFrame
   0x70C3FE  mov ecx,[esi+334h] ; RockingForwardsPerFrame
   0x70C40C  mov dl, [esi+3CDh] ; IsSinking  → CRC_bool
   ```
3. 积分器的配对关系 `[328h] += [330h]` 与 `[32Ch] += [334h]` 语义自洽。

> 踩坑记录：一开始按「IDB 名字就是偏移」去搜 `fld [esi+324h]`，全库 0 处命中，导致误判「倾斜角无人读取」。纠正后（+4）一切自洽。

### 1.3 倾斜更新器的三套分支

`0x70B570` 的骨架：

```
if (IsSinking == 0)                    // [0x3CD]
{
    if (IsCrashing != 0)               // [0x425]  ← FootClass::Crash 置 1
    {
        AngleRotatedSideways += RockingSidewaysPerFrame;   // 0x70B649 / 0x70B659
        AngleRotatedForwards += RockingForwardsPerFrame;   // 0x70B65F / 0x70B66B
        if (TechnoType->BalloonHover) { …±π/4 夹紧、≥π 则 Sink/爆炸… }
        return;                        // 0x70B677 jz 0x70BCA4：非 BalloonHover 直接返回
    }
    // ↓ 行走摇摆 / 自回正（0x70B700 起，用 RulesData 的两个浮点做回正速度）
    //   注意：入口先看 RockingSidewaysPerFrame == 0 ⇒ 0x70B921 把 AngleRotated* 归零
}
else                                   // IsSinking != 0
{
    // 0x70B5BA..0x70B625：按船头所在的八分圆，每帧 AngleRotatedForwards ± 0.01
    // 末段直接 retn，无夹紧、无回正
}
```

**关键不变量（三套分支共有）**：`AngleRotated* += Rocking*PerFrame` **每逻辑帧执行一次**。
⇒ **`Rocking*PerFrame` 的语义是「每帧步进量（角速度）」，不是角度。** 这与 `YRpp` 的注释完全一致：

> `TechnoClass.h:660-663` — *"set these and leave the previous two alone! if these are set, the unit will roll up to pi/4, by this step each frame, and balance back"*

而 `FootClass_Crash`（`0x4DEBB0`，写点 `0x4DECF0` / `0x4DED13`）正是用 `ScenarioClass::Random` 去设这个"步进量"：
```
0x4DECBB  mov  eax, Scenario
0x4DECC0  push 7FFFFFFEh
0x4DECC5  push 0
0x4DECC7  lea  ecx, [eax+218h]
0x4DECCD  call Random2Class::operator()
…
0x4DECF0  fstp [esi+330h]        ; RockingSidewaysPerFrame = (rand) * 0.1 或 0.1+r*0.15 等
0x4DED0B  fld  [esi+330h]
0x4DED13  fstp [esi+330h]        ; fchs 后回写（随机方向）
0x4DED45  fstp [esi+334h]        ; RockingForwardsPerFrame
…
0x4DEC7F  mov  byte ptr [esi+425h], 1   ; ★ IsCrashing = 1
```
⇒ 坠落/沉没时引擎给的是**每帧随机的翻滚步进量**。**把它一比一抄给替身，等于让替身每帧随机再翻一次。**

### 1.4 倾斜的消费方 = locomotor 的 `Draw_Matrix`

`AngleRotated*` 的浮点读取者（排除 `0x70B570` 自身）集中在：

| 读取点 | 归属 | 说明 |
| --- | --- | --- |
| `0x4AFF25` / `0x4AFF3A` / `0x4AFFC0` / `0x4AFFD5` / `0x4B005D` / `0x4B0072` / `0x4B0102` | `DriveLocomotionClass` 的 vt+0x24 槽 = **`Draw_Matrix`** | 0x328(前) 与 0x32C |
| `0x4B046B` / `0x4B0480` | 同上体系 | |
| `0x69F635` / `0x69F6D0` / `0x69F743` / `0x69F758` / `0x69F782` / `0x69F7F9` / `0x69F812` | `ShipLocomotionClass` 的 vt+0x24 槽（`0x69F670`）= **`Draw_Matrix`** | 战舰走这条 |
| `0x513F53` / `0x514117` / `0x51412C` / `0x5141BC` / `0x5142B0` / `0x513F6C` / `0x5140ED` / … | `0x513F40` / `0x5142A0`（Walk / Mech 体系） | |
| `0x54DCEB` / `0x54DD97` / `0x54DDAC` / `0x54DE3C` / `0x54DD00` / … | `0x54DCC0`（Hover 体系） | |
| `0x70C3D4…` | `TechnoClass::GetCRC` | 见 §5 |

`ILocomotion` 的默认实现 `LocomotionClass::ILocomotion_DrawMatrix`（`0x55A730`）本身**不读**倾斜（只用朝向 + `Matrix3D_5AF1A0`），但 **Drive / Ship / Walk / Hover 都覆盖了它**，在各自实现里把倾斜角并入矩阵。

⇒ **结论：倾斜是经由 `Draw_Matrix` 进入绘制矩阵的。** 而 `FLH.cpp` 的 `GetMatrix3D()` 正是
`((FootClass*)pTechno)->Locomotor->Draw_Matrix(pKey)`，**所以替身 `Stand.Offset` 的 FLH 解算本来就已经包含主身的倾斜**。
**「Offset 位置算法没考虑倾斜」这一猜想被排除。**（真正出问题的只有 §3 的累计角度与 §4 的方向旋转。）

## §2 根因 R1：把「角度」写进了「每帧步进量」

修复前的代码（`StandEffect::OnGScreenRender`）：

```cpp
float forwards = pTechno->AngleRotatedForwards;
float sideways = pTechno->AngleRotatedSideways;
// …按 Offset.Direction 做 8 分支旋转…
pStand->AngleRotatedForwards    = forwards;
pStand->AngleRotatedSideways    = sideways;
pStand->RockingForwardsPerFrame = forwards;   // ★ 把角度写进了步进量
pStand->RockingSidewaysPerFrame = sideways;   // ★ 同上
```

代入 §1.3 的不变量，替身每逻辑帧会发生：

```
替身. AngleRotatedForwards += 主身. AngleRotatedForwards      ← 每帧再加一份完整角度
替身. AngleRotatedSideways += 主身. AngleRotatedSideways
```

- 这不是"把替身摆到和主身一样的角度"，而是**命令替身每帧再转一个主身角度**。
- 对**非 `BalloonHover`** 单位（战列舰、坦克都算），`IsCrashing` 分支是**纯积分 + 立即 `retn`**（`0x70B677 jz 0x70BCA4`）—— **既没有 π/4 夹紧，也没有回正** ⇒ 角度**无界增长**。
- 即便走"行走摇摆"分支，`AngleRotated*` 依然会被 `+= Rocking*` 影响，且在 `IsCrashing` 被置位后立刻切到无夹紧的积分分支。

### 数值量级（为什么会一眼看出来）

- 主身 `AngleRotatedForwards` 在行走摇摆下量级约 `1e-2` 弧度；按 `1e-2`/帧算，**约 157 帧（≈10 秒）就累积到 π/2**。
- 下沉/坠落时 `FootClass_Crash` 给的步进量在 `0.1 ~ 0.25` 量级（`0x4DECF0` 用 `(rand)*0.15+0.1`），**约 6~15 帧就超过 π/2**。
- 而 `YRpp` 对这两个字段的原始注释就是：*"in this frame, in radians - if abs() exceeds pi/2, it dies"* ⇒ 越界意味着"翻船"级别的大角度。

## §3 一个根因，两个现象

| 用户观察 | 机理 |
| --- | --- |
| **Master 移动时 Stand 抖动** | 主身只要在动，行走摇摆就会让 `AngleRotated*` 非零且**每帧变化**；替身把这份"当帧角度"当成"当帧步进"再累加一次 ⇒ 替身角度成了主身角度的**积分**，每帧都在变 ⇒ 替身的绘制矩阵每帧剧变。<br>此外替身的渲染坐标 `ObjectClass` 的 `vt+0x48`（`W?Center_Coord`，`0x5F65A0`）会经 `ILocomotion::Draw_Point` 用到 locomotion 变换 ⇒ **替身的画面位置也随之每帧漂**，表现为抖动。 |
| **战列舰下沉时炮塔脱离船身、自己往一边倾斜** | 下沉时 `FootClass_Crash` 把 `IsCrashing=1` 且用**随机数**设 `Rocking*PerFrame`；Kratos 又把主身角度抄进替身步进 ⇒ 替身每帧加一个"主身角度"⇒ 角度爆炸式增长 ⇒ 炮塔被自己的绘制矩阵转飞，视觉上就是**脱离船身 + 自己往一边倒**。 |

> 顺带解释一个细节：替身的 `IsSinking` 在 `UpdateStateTechno` 里**被复制**，`IsCrashing` **没有**被复制。所以下沉场景下主身走 `IsSinking` 分支、替身也走 `IsSinking` 分支（一致）；而**坠落**场景下主身走 `IsCrashing` 分支、替身却走"行走摇摆"分支。本轮修复后，因为 `Rocking*PerFrame` 恒为 0，**两支分支都不可能再改变替身的角度**，分支分歧不再有视觉后果，因此**不需要额外复制 `IsCrashing`**（避免让替身被卷入坠机行为，风险更大）。

## §4 根因 R2：方向旋转的缺陷

原实现（`switch (Data->Offset.Direction)`，0..15，16 分圆）：

| `Direction` | 几何含义 | 旧行为 | 正确值 |
| --- | --- | --- | --- |
| 0 (N) | 与主身同向 | 不旋转 ✅ | 不旋转 |
| **2 (NE)** | +45° | **空实现 ❌** | 45° 旋转 |
| 4 (E) | +90° | `f'=-s, s'=f` ✅ | 一致 |
| **6 (SE)** | +135° | **空实现 ❌** | 135° 旋转 |
| 8 (S) | 180° | 只做 `s'=-s`，**漏了 `f'=-f`** ❌ | `f'=-f, s'=-s` |
| 10 (SW) | 225° | 与 12 同款（近似到 90°）⚠️ | 225° 旋转 |
| 12 (W) | 270° | `f'=s, s'=-f` ✅ | 一致 |
| **14 (NW)** | 315° | **空实现 ❌** | 315° 旋转 |

**物理解释**：`AngleRotatedSideways` 是绕主身"前轴"的 roll，`AngleRotatedForwards` 是绕主身"侧轴"的 pitch。
若替身相对主身偏航了 `θ`，则主身坐标系下测得的 `(forwards, sideways)` 在替身体坐标系里就是一次平面旋转：

```
f' = f·cosθ − s·sinθ
s' = f·sinθ + s·cosθ
```

以旧代码的 `case 4`（`f'=-s, s'=f`）为标定基准 ⇒ `θ = +90°` ⇒ 与 `θ = Direction · 22.5°` 完全等价。
`θ=180°` 时代入即得 `f'=-f, s'=-s` —— 正是旧 `case 8` 漏掉的那一半。
`θ=0°` 时恒等 —— 旧 `case 0` 也是对的。⇒ **旧实现在 90° 倍数上的行为被完整保留，只是补全了缺失的方向。**

### 修复后：不依赖 `Direction`，而用「两端真实朝向差」

```cpp
double theta = pStand->PrimaryFacing.Current().GetRadian()
             - pTechno->PrimaryFacing.Current().GetRadian();
// 归一到 (−π, π]
if (theta != 0.0) { f' = f·cos − s·sin; s' = f·sin + s·cos; }
```

为什么用真实朝向而不是 `Offset.Direction`：

- `GetRelativeDir`（`FLH.cpp:183`）内部：`targetDir = Radians2Dir(sourceRad − DirNormalized(Direction,16).GetRadian())`，
  而 `DirNormalized(d,16)` 的弧度是 `−d·22.5°` ⇒ 替身朝向 = 主身朝向 + `Direction·22.5°` ⇒ 两端相减正好得到 `θ`。
  **⇒ 与静态 `Direction` 完全等价（这是自洽性校验）。**
- 但替身的朝向**不一定**由 `Offset.Direction` 决定：
  - `Offset.IsOnTurret = yes` 且主身有炮塔时，`GetRelativeDir` 用的是 `GetRealFacing()`（炮塔朝向），而炮塔每帧在转向；
  - `Stand.FreeDirection = yes` 时 `SetFacing` 根本不写朝向；
  - `LockDirection` / `HasTurret` / `TurretSpins` 的各种组合下 `SetFacing` 的行为不同。
- 用**两端实际 `PrimaryFacing` 之差**，上述所有情形自动正确 —— 因为替身的 `Draw_Matrix` 用的就是它自己的 `PrimaryFacing`。

## §5 位置：哪些是真问题，哪些不是

### 5.1 不是问题：Offset 已经含倾斜（见 §1.4）

`GetRelativeLocation` → `GetFLHAbsoluteCoords(TechnoClass*, …)` → `GetMatrix3D` → `Locomotor->Draw_Matrix`，
而 `Draw_Matrix` 覆盖实现里读了 `AngleRotated*`。⇒ **Master 倾斜时，`Stand.Offset` 的 FLH 偏移跟着一起转。无需补偿。**

### 5.2 是问题：下沉时被强行"贴地"

```cpp
// 修复前
pStand->SetLocation(location);
if (!Data->IsTrain && Data->SameMoving && Data->StickOnFloor
    && !pStand->GetTechnoType()->JumpJet
    && pTechno->GetHeight() <= 0)
{
    pStand->SetHeight(0);        // ← 把替身压到「替身自己所在格子」的地面高度
}
```

下沉/坠落时主身的 Z 由沉没逻辑支配（`IsSinking` 分支每帧持续下沉），`SetHeight(0)` 会把替身拉到**它自己那个格子**的地面/水面高度 ⇒ 与船体分离。
典型现象正是用户描述的"炮塔掉出来"。

**修复**：加上 `&& !pTechno->IsSinking && !pTechno->IsCrashing`。

### 5.3 关于渲染坐标 vs 逻辑坐标

- `ObjectClass::GetCoords`（`0x5F6C80`）实际走 `call [eax+0x48]` = `GetRenderCoords`（`W?Center_Coord`，`0x5F65A0`）。
- `GetRelativeLocation`（`FLH.cpp:217`）对 Techno 分支**不使用** `pOwner->Location`，而是重新取 `pTechno->GetCoords()`（= 渲染坐标）作基准。
- 写入侧是 `pStand->SetLocation()`（**逻辑坐标**），替身绘制时再叠加它自己的渲染补偿。

⇒ 这在**结构上**看着像"基准混用"，但两点让它实际可用：
1. 主身的 `GetRenderCoords()` 与替身 `SetLocation` 后各自的渲染补偿在**平地上抵消**（同一 `Draw_Matrix` 语义、同一 `Center_Coord` 口径）；
2. `sub_64DAB0` 的锁步校验只用 `Location.X/10`、`Location.Y/10`（像素粒度）——**Z 完全不参与**（见 §6.1）。

**本轮不改这条通道**（改动面太大、收益不确定），仅在文档中记录为"已知结构性隐患，待有实机症状再动"。

## §6 失同步评估（关键章节）

用户硬约束：**不得引入失同步。** 下面逐项证明本轮改动是同步安全的。

### 6.1 每帧锁步校验值 `sub_64DAB0` 的输入（逐指令核对）

```
0x0064DAD6  lea  ecx, [eax+9Ch]        ; &Location
0x0064DADC  mov  edi, [eax+9Ch]        ; X
0x0064DAE2  mov  ebx, [ecx+4]          ; Y
0x0064DAE5  mov  edx, [ecx+8]          ; Z  → 存进 var_4，之后【无人读取】
0x0064DAED  lea  ecx, [eax+388h]       ; PrimaryFacing
0x0064DAF7  call Desired_Facing256     ; → 折成 0/1 位
0x0064DAFE  mov  eax, 66666667h        ; ★ magic：sar 2 ⇒ 除以 10
0x0064DB03  imul ebx                   ; Y/10
…
0x0064DB23  add  ebp, edx              ; ebp = ((Y/10)<<16) + facingbit
0x0064DB25  imul edi                   ; X/10
0x0064DB41  add  eax, ecx              ; sum = sum*2 + (X/10 + ((Y/10)<<16) + facingbit)
```

**⇒ 锁步校验值 = `Σ (X/10, (Y/10)<<16, 朝向粗位)` 的顺序敏感滚动哈希。**

由此得到三条硬结论：

1. **`Location.Z` 不在锁步校验值里。** ⇒ `SetHeight(0)` 及其门控（本轮 R3 修复）**不可能造成锁步失同步**。
2. **`AngleRotated*` / `Rocking*PerFrame` 也不在锁步校验值里**（全部偏移扫描确认：只有 `+9Ch`、`+388h`、`+3A0h`）。⇒ 倾斜同步的**取值**不会造成锁步失同步。
3. 因此**真正需要守的只有 X/Y** —— 即 `pStand->SetLocation()` 的 X/Y 必须是"两端完全一致的纯函数"。

### 6.2 本轮改动的逐项同步论证

| 改动 | 是否触碰锁步字段 | 论证 |
| --- | --- | --- |
| `Rocking*PerFrame = 0`（渲染帧 + 逻辑帧） | 否（不在 `sub_64DAB0`） | 写入常量 `0.0f`，也是**最确定性**的取值。`Data->SameTilter` 是 INI 驱动，两端相同。 |
| `AngleRotated* = 旋转后的主身角度` | 否（不在 `sub_64DAB0`） | 取值是「主身已同步状态 + 两端各自一致的朝向」的纯函数。`theta` 由两端各自的 `PrimaryFacing` 差得到，而 `PrimaryFacing` 本身是同步状态。 |
| `theta` 用 `std::cos/std::sin` | 否 | 两端同一二进制 + 同一 CRT ⇒ 浮点结果一致。 |
| `SetHeight(0)` 增加 `!IsSinking && !IsCrashing` 门控 | **只触碰 Z** | `IsSinking` / `IsCrashing` 是主身的引擎模拟状态（`FootClass::Crash` 里 `IsCrashing=1` 的置位路径是模拟路径，非随机）；两端主身状态相同 ⇒ 门控结果相同 ⇒ Z 相同。而 **Z 不进锁步校验值**（§6.1）。 |
| 未改动任何 Hook / 落点 / 层序 | 否 | 层数组顺序是校验值的输入（既有结论），本轮零改动。 |

### 6.3 残留风险（诚实披露）

`TechnoClass::GetCRC`（`0x70C270`）**确实**把这 4 个倾斜 float 与 `IsSinking` 都喂进了 `CRC_float` / `CRC_bool`：

```
0x70C3D4 [328h] → CRC_float     0x70C3F0 [330h] → CRC_float
0x70C3E2 [32Ch] → CRC_float     0x70C3FE [334h] → CRC_float
0x70C40C [3CDh] → CRC_bool
```

它的消费者是：

- `Multiplay_LogToSYNC_NOMPDEBUG`（`0x64DEA0`，24 处 `call [reg+0x34]`）→ 同步日志（`SYNC%d_%03d.TXT`、`GameSyncLogging`、`MPSYNCDEBUG`）
- `Multiplay_LogToSync_MPDEBUG`（`0x6516F0`）
- `Game_GetCRC`（`0x67C6E0`，56 处 `call [reg+0x34]`）→ `ExtraSyncCheck` 路径

⇒ **锁步每帧比对不看这些字段，但"同步日志 / 额外同步检查"看。** 处置：
1. 本轮让这些字段变成「**逻辑帧：`Rocking*` 恒 0；渲染帧：`AngleRotated*` 被逐个覆盖为纯函数值**」—— 比修复前（角度无界累积）**方差小得多**；
2. **不要开 `ExtraSyncCheck` / `MPSYNCDEBUG` 去做联机验收**：那是调试工具，本体就会对渲染时序差异敏感；
3. 若日后要在这些字段上追求 100% 零残留，唯一彻底的方案是**完全不再写 `AngleRotated*`**，改为复刻引擎的 `IsSinking` / `IsCrashing` 状态机让替身自己演化 —— 但那样必须同时同步 `IsCrashing`、且受替身朝向的八分圆符号影响，**同步确定性反而更差**，本轮不采用。

### 6.4 为什么倾斜同步必须放在渲染阶段（而不是逻辑阶段）

帧内时序（既有结论，`W?Main_Loop`）：

```
iteration i:  ① CRC(sub_64DAB0)  ② DoList  ③ GScreenClass_DrawOnTop（含渲染事件）
                                          ④ LayerClass::Sort(Ground)  ⑤ LogicClass_Update
```

- 引擎的倾斜更新器跑在 ⑤ 内部（`TechnoClass::Update`）⇒ **逻辑阶段写 `AngleRotated*` 会被 ⑤ 立刻覆盖/污染**；
- 渲染事件在 ③ 的最前面（`0x4F4497`），而真正的绘制在 `TacticalClass_Draw`（`0x4F44DF`）里 ⇒ **③ 里写值 = "引擎算完、绘制之前"的唯一窗口**。

⇒ 原作者把倾斜同步放在 `OnGScreenRender` **位置是对的**，错的只是**写的内容**（把角度写进了步进量）。本轮保留这个时机。

### 11.2 ★ 纠错一：`0x70A280` 不是"第二个 `+0x32C` 写入族"

之前报告的「`0x70A280` 有 14 处写 `+0x32C`，是第二条倾斜写入路径」是**假阳性**——
`0x70A280` 本身处于错位字节上，根本不是函数入口。

真反汇编结果：`TechnoClass::AngleRotatedForwards(+0x32C)` 的**写入者只有两处**：

- `0x70B570`（倾斜积分器，`TechnoClass` vt`+0x41C`）
  `0x70B619` / `0x70B631`（`IsSinking` 分支 `±0.01`）、`0x70B659`（`+= RockingForwardsPerFrame`）、
  `0x70B6A4`、`0x70B9F7`、`0x70BA49`、`0x70BA85`、`0x70BBE1` …
- `0x53D2CB`（唯一独立写入者）：沿 `[esi+0x30]` 链表遍历，算 `-k*x` 写入，与沉船无关。

而**读取者（消费点）全部是 locomotor 的 `Draw_Matrix`**：
`0x4AFF60`(Drive)、`0x69F670`(Ship)、`0x4CF6E7`(Fly)、`0x513F6C`/`0x514xxx`、`0x54DD00`/`0x54DExx`。

⇒ **「两条路」在"字段"层面不成立**：沉船倾斜（`IsSinking` 分支）与地形坡道倾斜
（`CurrentRamp`/`PreviousRamp` → `VoxelRampMatrix`）确实是**两个数据来源**，
但它们在 `Draw_Matrix` 的 **A 路径里汇合进同一个矩阵**，因此不存在"另一条绕开 `Draw_Matrix` 的倾斜"。

```
0x69F6C8  test ah,0x40 (C3)  /  0x69F6CB je 0x69F6FE     ; t != 1.0        → A
0x69F6D0  fld [ecx+0x328] fabs fcomp [0x7E44E8]=0.005
0x69F6E0  test ah,1          /  0x69F6E3 je 0x69F6FE     ; |ARS| >= 0.005  → A
0x69F6E5  fld [ecx+0x32C] fabs fcomp 0.005
0x69F6F5  test ah,1          /  0x69F6F8 jne 0x69F9C3    ; |ARF| <  0.005  → B
                                                          ; 落空             → A
```

⇒ **A ⟺ `t != 1.0 || |ARS| >= 0.005 || |ARF| >= 0.005`；B ⟺ 三者全否。**
沉船时 `|ARF|` 数帧内即 ≫ 0.005 ⇒ **必走 A**。
（`[ecx+0x328]` = `[ecx+8]->AngleRotatedSideways`，`[ecx+0x32C]` = `...AngleRotatedForwards`，`[ecx+8]` = `LinkedTo`。）

乘法链（`MatrixMultiply` = `__fastcall`，`ECX:ret, EDX:A, [esp+4]:B`，`ret 4`）：

```
0x69F994/95/96  push var_1B0 ; push base ; push RM          ; 栈上 B 依次为 base → var_1B0
0x69F997  lea edx,[esp+0x5c] -> var_1E0   ; A
0x69F99B  lea ecx,[esp+0x14c] -> ret1
0x69F9A2  call MatrixMultiply             ; ret1 = var_1E0 × base
0x69F9A7  mov edx,eax                     ; A = ret1
0x69F9A9  lea ecx,[esp+0x1a8]
0x69F9B0  call MatrixMultiply             ; ret2 = ret1 × var_1B0
0x69F9B7  lea ecx,[esp+0x114] ; jmp 0x69FAEA   ; 拷进隐藏返回指针
```

⇒ 返回值 = **`TranslateZ(δ) × base(坡道+朝向) × (RotateX(ARS) · RotateY(ARF))`**
—— **倾斜确实并入返回矩阵**（B 路径只有 1 次 `MatrixMultiply`，无任何 `Translate`/`Rotate`）。
`RotateY` 只改第 0/2 列（X-Z 面 = 俯仰），`RotateX` 只改第 1/2 列（Y-Z 面 = 横滚），`Translate` 只改第 3 列。

于是 `GetFLHOffset` 的结果：

```
res.Z = M[2][3] + flh.x·M[2][0] + flh.y·M[2][1] + flh.z·M[2][2]
      ≈ M[2][3] + 1050·(±sin ARF) + 75·cos ARF
```

`Stand.Offset=1050,0,75`、`ARF→π/4` 时 **ΔZ ≈ 1050·0.707 ≈ 742 leptons** —— **数学上必然抬起**。
⇒ **"需要手动补偿倾斜带来的 FLH 位移"不成立**（§5.1 的结论仍然正确）。
