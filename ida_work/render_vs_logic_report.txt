================================================================================
问题 1：0x4F4497 在主循环里被调用的频率与条件
================================================================================

结论（一句话）：**不是"每逻辑帧恰好一次"**。正常对局中它每帧至少 1 次，但
(a) 联机模式下同一逻辑帧内可能被调用多次（帧尾限速器 0x55E271）；
(b) 存在多个分支让某一帧完全不渲染（最常见：窗口失焦 GameInFocus==0），
    而该帧的逻辑更新与校验值照跑（联机模式）。

证据 1-A：帧首渲染的完整门控（原文，0x55D878-0x55D8FD）
    0055D878  mov     ecx, arg_ATTRACT_Flags
    0055D87E  test    cl, 2
    0055D881  jnz     short loc_55D8FF          ; ← 回放(bit1)时跳过帧首渲染
    0055D883  mov     eax, dword_A8EDA0
    0055D888  xor     edi, edi
    0055D88A  cmp     eax, edi
    0055D88C  jnz     short loc_55D901          ; ← 有挂起动作时跳过
    0055D88E  mov     al, GameInFocus
    0055D893  test    al, al
    0055D895  jz      short loc_55D901          ; ← 窗口失焦时跳过
    0055D897..0055D8E3  GScreenClass::Input(0x55D8AB) / Keyboard_Process(0x55D8B4)
                        DrawMPDebug(0x55D8C4) / sub_4D2370(0x55D8E8)
    0055D8F2  call    GScreenClass_DrawOnTop    ; ★ 正常帧首渲染
    0055D8F7  mov     ecx, arg_ATTRACT_Flags
    0055D8FD  jmp     short loc_55D901
对应 Hex-Rays：
    if ( (arg_ATTRACT_Flags & 2) == 0 && !dword_A8EDA0 && GameInFocus )
        { GScreenClass::Input(...); Keyboard_Process(...); ...; GScreenClass_DrawOnTop(&Map); }

证据 1-B：窗口失焦（Alt-Tab）时"逻辑照跑、渲染全跳"
    0055D377  mov     al, GameInFocus
    0055D37A  test    al, al
    ...       jnz     -> LABEL_8（正常）
    失焦时：
      0055D390  cmp     Session.idxGameMode / 0 或 5  → 进入 while 循环：
                0055D3A0  call Sleep(500) / 0055D3A2 call sub_5D4D50  （自旋，整帧不推进）
      否则（联机模式 1..4）：
                0055D3B4  call Sleep(10)  / 0055D3B6 call sub_5D4D50
                → 落到 LABEL_8 继续执行 [6][7][8]：Sort、LogicClass_Update、校验值
    再叠加 1-A 的 0x55D895 跳过 → 该逻辑帧渲染次数 = 0，逻辑与校验值次数 = 1。
GameInFocus 的唯一写入点（全二进制 XrefsTo 0xA8ED80 只有一处写）：
    007778CE  mov     GameInFocus, al           ; in W?Windows_Procedure$n(pnvuiuil)l
    上下文：007778A0 cmp edi, hWndParent / 007778AC mov eax,[esp+arg_8] /
            007778B2 cmp eax,ebx / 007778B4 setnz cl / 007778B9 mov dl,GameInFocus /
            007778BF cmp edx,ecx / 007778C1 jz ... / 007778CE mov GameInFocus,al
            007778D5 push offset aFocus_loss; "Focus_Loss()\n" / call WWDebugString
            （同分支还更新 Mouse_Captured / byte_A8ED81）
    ⇒ 就是窗口激活/焦点消息（WM_ACTIVATE / WM_ACTIVATEAPP 一类）的处理分支，
      失焦 = GameInFocus 置 0。

证据 1-C：帧尾限速器可以再渲染 0..N 次（同一逻辑帧内多次调用）
    sub_55E160（每帧末 0x55DE9A 调用）反编译要点：
      if (Session.idxGameMode && Session.idxGameMode != 5)      // 联机模式
      {
        while (1) {
          ... TimerNFT 剩余时间到期 -> goto LABEL_38（结束）
          Call_Back();
          if (!dword_A8EDA0 && GameInFocus == 1) break;          // ★ 0x55E1F8/0x55E204
          Sleep(0);                                              // 0x55E2xx
        }
        v6 = TimerNFT.TimeLeft - elapsed;
        if (v6 > 10) { GScreenClass::Input(...); Keyboard_Process(...);
                       (*(TacticalMap->vt+23))(TacticalMap);
                       GScreenClass_DrawOnTop(&Map); }           // ★ 0x55E271 再渲染
        LABEL_19 -> 检查剩余 -> goto LABEL_23(Sleep(0)) -> 回到 while(1)
      }
    反汇编原件（写入点与 break 条件）：
      0055E204  cmp     GameInFocus, 1
      0055E271  call    GScreenClass_DrawOnTop
    ⇒ 只要帧预算还有 >10ms，就会反复"输入处理 + 渲染"，直到时间用完；
      因此联机模式下一个逻辑帧内 DrawOnTop（及 mod 的 0x4F4497/0x4F4583）可以被调用多次。
      失焦时该循环不 break（只 Sleep(0) 到超时）→ 一次都不渲染。

证据 1-D：其余会"跳过/替代"渲染的分支
    (1) GameActive==0：0x55D36B test al,al → return 1，整帧不做（无渲染）。
    (2) 有挂起游戏动作 dword_A8EDA0 != 0：0x55D88C 跳过帧首渲染。
        dword_A8EDA0 是一个"待处理的游戏动作"状态码：写入点包括
        Networking_RespondToEvent(0x4C7939=1, 0x4C80FF=7)、sub_4F11B0(0x4F14E2=5,0x4F16D2=2,0x4F16E0=3)、
        sub_4E1FE0(0x4E237E=6,0x4E23A3=4)、RadarClass_MouseMove(0x65393A=8,0x653946=9,0x653959=1)、
        sub_6ABC40(0x6ABC49=8)；Main_Game 开局清零(0x48CE6D)。它由帧循环里的 sub_48C8B0 处理
        （0x48C8B0 第一句 `if (!dword_A8EDA0) return;`，非 0 时走投降/失败/暂停对话框状态机，
         并调用 ScenarioClass_Pause）。
        该类状态下渲染改由别处做（例如 ScenarioClass_Pause 内 0x683F9A call GScreenClass_DrawOnTop）。
    (3) 回放/录像 arg_ATTRACT_Flags & 2：0x55D881 跳过帧首渲染；同帧稍后读完回放指令后
        在 0x55DBBE 再渲染一次（0055DBB4 call GScreen_FlagToRedraw; 0055DBBE call GScreenClass_DrawOnTop）。
        录制(bit0)不影响渲染次数。
    (4) 单机暂停分支：Session.idxGameMode==0/5 且 Scenario->field_62C != 0
        0055D826  mov     ecx, [eax+ScenarioClass.field_62C]
        0055D82C  test    ecx, ecx
        0055D82E  jz      short loc_55D878
        0055D84F  call    GScreenClass_DrawOnTop
        0055D854  call    sub_55E160
        → 渲染后立即 return：本帧不排序、不跑 Logic、不算校验值、Frame 不递增。
        （联机模式在 0x55D7CE 就 jnz loc_55D878，走不到这里 → 不影响 lockstep。）
    (5) 帧外的额外渲染路径（可能在帧中途触发）：
        Networking_RespondToEvent(0x4C6CB0) 内有 0x4C7B0E call GScreenClass_DrawOnTop；
        它由 DoList(0x64C911/0x64CC0A) 调用，而 DoList 正是 sub_647260/sub_6475F0 在
        算完校验值后处理网络事件时调用的 → 网络事件可在同一帧的后半段再插入一次渲染（含 mod 两个 hook）。
        另有 sub_648350/sub_648710(结算/对话框)、sub_685670/sub_685DC0/sub_6863E0、
        TActionClass_Execute(0x6DEF16/0x6DEF87)、sub_6E2860/sub_6E28DC、sub_55E160(0x55E271)、
        ChronoScreenEffect_Update(0x53B66B) 等非帧序列调用点。

证据 1-E：关于"帧率限制"
    未发现"无渲染/no-render"全局标志；帧率节流有两处，都不在 Main_Loop 的渲染门控里：
      - sub_55E160 的 TimerNFT/Sleep(0) 等待（作用=同帧内多次渲染，不是跳过渲染）；
      - GScreenClass::Do_Blit(0x4F4780) 内部 004F4B90 call ds:Sleep; 32h（50ms，垂直回扫等待），
        由窗口过程消息分支调用（0x777717 call GScreenClass::Do_Blit，窗口化模式重绘路径）。
    ⇒ "帧率限制"不会让 DrawOnTop 少跑；真正会让它少跑的是焦点(dword GameInFocus)/挂起码(dword_A8EDA0)/
      GameActive/回放 bit1/单机暂停。

================================================================================
问题 2：渲染期修改对象 Location 会不会进校验值 / vec_ObjectsInLayers 何时重建
================================================================================

结论（三选一）：**"在渲染回调里改单位 Location，会让两端校验值分歧"——因为该写入进入本帧校验值**
（不是"只在下一帧生效"，也不是"完全不影响"）。准确表述：
  · 渲染回调位于本帧 LogicClass::Update 与校验值计算之前 ⇒ 写入在同一逻辑帧内即生效并参与哈希；
  · 只要该帧两端都执行了渲染回调且结果一致（纯函数），两端校验值一致；
  · 一旦某一端把这一帧的渲染整体跳过（例如 GameInFocus==0，而联机模式下逻辑照跑），
    该端对象位置停在旧值、另一端已更新 ⇒ 本帧 dword_AC51FC 立即分歧。

证据 2-A：sub_64DAB0 读的字段 = 对象坐标三元组（Location / CoordStruct）
    层循环本体（0x64DCE4-0x64DD92）：
      0064DCE4  mov     ebp, offset vec_ObjectsInLayers.length   ; = 0x8A0370（层0 的 length 域）
      0064DCE9  mov     eax, [ebp+0]
      0064DCF4  jle     loc_64DD89
      0064DCFA  mov     edx, [ebp-0Ch]        ; = 层基址+4 = .data 指针
      0064DCFD  mov     esi, [edx+edi*4]      ; esi = ObjectClass*
      0064DD02  mov     eax, [esi]
      0064DD04  call    dword ptr [eax+2Ch]   ; WhatAmI()
      0064DD07  cmp     eax, 4
      0064DD0A  jnz     short loc_64DD1B
      0064DD0C..0064DD19  （对 Building 额外虚调用 [esi+4]->vt+0x10，若返回 -2 则跳过该对象）
      0064DD1B  lea     edx, [esi+9Ch]        ; ★ 坐标三元组起点
      0064DD23  mov     edi, [edx]            ; X = [obj+0x9C]
      0064DD25  mov     ebx, [edx+4]          ; Y = [obj+0xA0]
      0064DD28  mov     eax, [edx+8]          ; Z = [obj+0xA4]  → 只存进 var_4
      0064DD2D  mov     [esp+24h+var_4], eax
      0064DD31  call    dword ptr [edx+2Ch]   ; WhatAmI() 再取一次
      0064DD36  mov     eax, 66666667h
      0064DD3B  imul    ebx / sar edx,2 / （符号修正）         ; = Y/10（0x66666667 + sar 2 = 除 10）
      0064DD4C  shl     edx, 10h
      0064DD4F  add     ecx, edx              ; ecx = WhatAmI + (Y/10 << 16)
      0064DD51  imul    edi / sar edx,2 / 符号修正              ; = X/10
      0064DD58  add     edx, ecx / shr eax,1Fh / add eax,edx    ; eax = WhatAmI + (Y/10<<16) + X/10
      0064DD5F  mov     edx, dword_AC51FC
      0064DD65..0064DD6E  （*3，符号修正）
      0064DD71  add     ecx, eax
      0064DD73  mov     dword_AC51FC, ecx      ; hash = 3*hash + (WhatAmI + (Y/10<<16) + X/10)
      0064DD89  add     ebp, 18h               ; 下一层（stride 0x18）
      0064DD8C  cmp     ebp, offset dword_8A03E8
      0064DD92  jl      loc_64DCE9             ; ⇒ 共 5 层 [0..4]
    随后对 vec_Logics 做同样的处理（0x64DD98-0x64DE33），再混入 Scenario->Randomizer
    （0x64DE33 lea ecx,[Scenario+218h] / call Random2Class::operator()，0x64DE54 累加），
    最后 0x64DE70 call sub_650A90（把 dword_AC51FC + 随机数 + Frame 写进联机同步记录表）。
    Z 分量是否进哈希：函数内 var_4 的全部引用只有 5 处，且**全是写入**——
      0x64DAF3 mov [esp+28h+var_4], edx
      0x64DB8A mov [esp+24h+var_4], ecx
      0x64DC48 mov [esp+24h+var_4], ecx
      0x64DD2D mov [esp+24h+var_4], eax     ← 对象 Z
      0x64DDDD mov [esp+24h+var_4], eax     ← vec_Logics 对象 Z
    ⇒ Z 被读出来但从不参与累加，"Z 不进校验值"成立。

证据 2-B：0x9C 就是引擎自己写 Location 的地方（mod 的 SetLocation 落到同一字段）
    · ObjectClass::SetPosition（0x5F6940）—— 即虚函数 SetLocation：
        005F6940  mov     eax, [esp+arg_Coords]
        005F6944  add     ecx, 9Ch
        005F694C  mov     [ecx], edx        ; X → obj+0x9C
        005F6951  mov     [ecx+4], edx      ; Y → obj+0xA0
        005F6957  mov     [ecx+8], eax      ; Z → obj+0xA4
    · ObjectClass::SetZ（0x5F6060）：
        005F607A  mov     [esi+0A4h], ecx   ; Z 在 0xA4 → 反证三元组起点是 0x9C
    · 虚表槽位核对：0x5F6940 出现在 .rdata 0x7E4070，该 vtable 起点 0x7E3EBC，
      槽位 = +0x1B4 —— 与 idb 里 vt_ObjectClass 的成员 "SetCoords @+0x1B4" 完全一致
      （同表 +0xA8 GetCoords_TwoArguments、+0xAC GetCoords_、+0x18C UpdatePosition）。
    · YRpp 侧：KratosPP/YRpp/ObjectClass.h:175 `virtual void SetLocation(const CoordStruct& crd)`，
      mod 的 StandEffect::SetLocation → `pStand->SetLocation(location)`（StandEffect.cpp:564-586）
      就是走这个槽位 ⇒ 写的正是 [obj+0x9C/+0xA0/+0xA4]。
    · 【实机核对发现的 idb 类型偏差，建议知悉】idb 里 ObjectClass 结构体把成员 `pos` 标在 +0x98
      （size 12，见 probe_render_vs_logic5.txt U1）。指令级证据（SetPosition 写 0x9C/0xA0/0xA4、
      SetZ 写 0xA4、hash 读 0x9C/0xA0/0xA4、vtable +0x1B4=SetCoords）表明真实三元组在 0x9C，
      即 idb 的 struct 注释整体偏了 4 字节。本次结论一律以指令为准。
      （Kratos 自己在 StandEffect.cpp:578-579 的注释"sub_64DAB0 只用 Location.X/Y"在指令级成立。）

证据 2-C：vec_ObjectsInLayers 的"重建点"——不是每帧重建，也不在 Draw 里重建
    (1) 唯一的"整体清空"：DisplayClass_InitClear(0x4A88C0)
        004A88C0 ... v2 = vec_ObjectsInLayers;  do { (v2->vt->Clear)(v2); ++v2; } while (v2 < &dbl_8A03D8);
        调用者（XrefsTo 0x4A88C0，向上两级）：
          0x652DE3 RadarClass_InitClear ← 0x63F737 PowerClass::Init_Clear ← 0x6A5036 SidebarClass::Init_Clear
        ⇒ 只在开局/重开（Init_Clear）时清空，**不是每帧**。
    (2) 每帧的成员/顺序维护发生在**逻辑期**（LogicClass_Update 0x55DC9E 之内）：
        ObjectClass::Update 里
          005F3FFD  mov eax,[this] / 005F4001 call [eax+78h]   ; InWhichLayer()
          005F4004  cmp ebp, eax / 005F4006 jz  short loc_5F4013
          005F4008  push this / 005F4009 mov ecx, offset Map / 005F400E call DisplayClass::Submit
          005F414C  call DisplayClass::Remove                  ; InLimbo 分支
        TechnoClass_EC 里 0x5F4184(Remove) / 0x5F4196(Submit)；另外 Unlimbo、AnimClass、
        BulletClass_SetMovement、各 locomotor 等也各自 Submit/Remove。
        Submit(0x4A9720) 自身先 Remove(0x4A9738/0x4A9734) 再按层插入：
          004A9747  cmp edi, 2 / 004A974D setz cl / 004A9750 push ecx(sortable)
          004A9752  lea ecx, vec_ObjectsInLayers.vt[edx*8] / call MapClass_AddObjectToALayerX
          → 层2(Ground) 走"按 YSort 有序插入"，其余层走 AddObject 的尾插
            （LayerClass::AddObject 0x5519B0：sortable=0 时 00551A0A-00551A1A 直接 data[length++]=obj）。
    (3) Draw 路径只"读"层数组：
        GScreenClass::DrawOnTop(0x4F4480) → TacticalClass_Draw(0x6D3D10，三次调用 0x4F44DF/0x4F44F4/0x4F4515)
        → Tactical_Draw_All(0x6D8DB0，调用点 0x6D465F) 遍历 vec_ObjectsInLayers[0..4]：
          006D8F2B mov ecx, vec_ObjectsInLayers.length[ebx]
          006D8F39 mov eax, vec_ObjectsInLayers.data[ebx] / 006D8F43 mov esi,[eax+ecx*4]
          006D93FA call dword ptr [edx+104h]        ; 对每个对象调用其绘制虚函数
          006D97A8 add ecx,18h / 006D97AB cmp ecx,(offset dbl_8A03D8+4) / jl  → 5 层
        → 没有任何 Clear/重建语句。（0x6D8F48 只是把对象 +0x99 的"本帧已画"标志清零。）
    (4) Ground 层额外每帧排序一次：0x55DBC8 call sub_551A30（ECX=0x8A0390）。
        LayerClass::Sort 是"单趟相邻交换"（0x551A37-0x551A7D）：
          00551A37  mov eax,[ebp+10h] / dec eax / jle ret
          00551A4F  call dword ptr [edx+0B8h]     ; obj[i+1]->vt+0xB8 = ObjectClass::ReturnRealYSort
          00551A5D  call dword ptr [eax+0B8h]     ; obj[i]->vt+0xB8
          00551A63  cmp [esp+14h+var_4], eax / 00551A67 jge short loc_551A76   ; 逆序才交换
        ReturnRealYSort(0x5F6BD0) 内部通过 GetCoords 虚调用取对象坐标（0x5F6BE0/0x5F6BF1）
        ⇒ 排序键依赖坐标 ⇒ **改 Location 除了直接进哈希项，还可能改变 Ground 层顺序，
          而哈希是顺序敏感的**（0x64DCE4-0x64DD92 按数组下标累加）。
        （层2 的插入用的是"有序插入"，所以排序键变化会在逻辑期就把顺序改掉。）

问题 2 的三选一落锤：
    "在渲染回调里改单位 Location，会让两端校验值分歧 / 只在下一帧生效但两端一致 / 完全不影响校验值"
    → **第一类的机制成立**：它进入**本帧**校验值（不是下一帧），且在两端的渲染回调执行不一致时立即分歧；
      若两端回调在同帧都执行且写入相同，则两端一致（此时不因"写在渲染期"本身而分歧）。

================================================================================
问题 3：0x4F4497 与逻辑帧的相对位置（一帧内 0 次 / 1 次 / 多次）
================================================================================
- 相对位置：0x4F4497（以及同函数内的 0x4F4583）位于 0x55D8F2 这一次 GScreenClass_DrawOnTop 调用内部，
  在随后的 LayerClass::Sort(0x55DBC8) → LogicClass::Update(0x55DC9E) → 校验值(0x55DE40) **之前**。
  即：渲染发生在"上一帧逻辑结束后的层数组状态"上；而渲染回调里对游戏状态的写入
  （如 SetLocation）会先于本帧逻辑与本帧校验值生效 —— 这正是问题 2 结论的机制来源。
  （用户背景里给的 0x55DBBE 是"回放播放"分支的渲染点；正常对局的帧首渲染点是 0x55D8F2，
    两者都在 Sort/Logic/hash 之前，位置关系结论相同。）
- 调用次数：
  · 0 次：GameActive==0；GameInFocus==0（失焦，0x55D895 + 0x55E204）；
          dword_A8EDA0 != 0（有挂起动作，0x55D88C）；单机暂停分支则改为 0x55D84F 渲染 1 次后 return。
  · 1 次：正常联机/单机对局、有焦点、无挂起动作、非回放；或回放模式（改在 0x55DBBE）。
  · 多次：联机模式（GameMode 1..4）帧尾限速器 sub_55E160 的等待循环里每次剩余 >10ms 都会
          再执行 `GScreenClass::Input + Keyboard_Process + TacticalMap->vt+0x5C + DrawOnTop(0x55E271)`；
          另外网络事件路径（DoList → Networking_RespondToEvent 0x4C7B0E）也可能在同一帧后半段再渲染。
  ⇒ 结论："每个逻辑帧恰好一次渲染"是**错误假设**；一帧 0 次与多次都真实存在。

对 mod 的含义（KratosPP 现状）

调用链（读源码得到，未修改）：
  0x4F4497 hook → EventSystems::Render.Broadcast(GScreenRenderEvent)
    → AttachEffect::OnGScreenRender（AttachEffect.cpp:1355；args==nullptr 时走 BeginRender 分支）
    → AttachEffect.cpp:1484 ae->UpdateStandLocation(locationMark)
    → AttachEffectScript::UpdateStandLocation（AttachEffectScript.cpp:188）
    → StandEffect::UpdateLocation（StandEffect.cpp:550）→ StandEffect::SetLocation（:564）
    → pStand->SetLocation(location)  → 引擎 vt+0x1B4 = ObjectClass::SetPosition(0x5F6940)
      → 写 pStand 的 [obj+0x9C/+0xA0/+0xA4]。

1) 会不会两端分叉：**在特定条件下会。**
   对非火车编组的替身，"每帧跟随主身的位置更新"只有一个入口，就是渲染回调
   （火车编组才在渲染里走 UpdateTrainStandLocation，AttachEffect.cpp:1478/1285-1313；
    OnStart 里的 SetLocation 只做初值，StandEffect.cpp:54-59）。
   而 sub_64DAB0 会把该替身（它是有层归属的 TechnoClass，除非 InLimbo）的 X/10、Y/10、
   以及 WhatAmI 折进每帧的 dword_AC51FC。于是：
     · 一端失焦（联机模式下 GameInFocus==0 只 Sleep(10) 后继续跑逻辑与校验值，渲染全跳）
       ⇒ 该端替身 Location 停旧值 ⇒ 本帧两端校验值不同 ⇒ 触发 YR 的失同步判定/日志。
     · 失焦期间还叠加：Ground 层排序键（坐标）不同 → 顺序敏感哈希的分歧被放大。
     · 即使不考虑失焦，如果该回调里含有任何"本地相关"的量（本地输入、时钟、随机数、
       渲染次数相关的累加、依赖是否被绘制的状态），也会直接造成分歧。
   反过来：**只**看"在渲染期写 Location"这一点，如果两端每个逻辑帧都执行渲染回调、
   且写入值完全由已同步状态决定，则写入落在本帧 Logic 与 hash 之前，两端本帧哈希一致
   （也就是说：它不是"下一帧才生效"，也不是"不影响校验值"，而是"当帧即进哈希"）。

2) 需要什么前提才算安全（按优先级）：
   (a) 把"会影响游戏状态/同步"的维护从渲染回调移到逻辑期
       （例如 AttachEffect 的 OnUpdate / TechnoClass::AI 阶段，与引擎自身 UpdatePosition 同时机），
       渲染回调只做纯视觉副作用。这是本审计的推荐修法。
   (b) 若坚持留在渲染回调：必须保证"每个逻辑帧、每个客户端都恰好执行一次该更新"，而引擎不保证
       （GameInFocus==0 / dword_A8EDA0!=0 / GameActive==0 / 回放模式都会让渲染次数变成 0 或 N）。
       若要自保，需要自建门控：以 Frame（0x55DE40 之前每帧 +1，见 0x55DE73）为幂等键，
       在逻辑期兜底补一次更新（"本帧是否已按 Frame 更新过"），并让渲染期的写入严格幂等；
       同时保证失焦时逻辑期兜底仍然执行（因为失焦时逻辑确实还在跑）。
   (c) 写入函数必须是已同步状态的纯函数：只用主身坐标/朝向/配置偏移，不用本地输入、时钟、
       渲染次数、随机数、客户端本地配置；多次写入必须幂等（一帧内渲染多次）。
   (d) 不要依赖 Z 影响同步：Z 不参与哈希（SetHeight/SetZ 不会直接造成失同步），
       但 X/Y 参与且精度是 10 leptons（X/10、Y/10），偏差 ≥10 就会改哈希项；
       另外 Y 通过排序键影响层顺序。

3) 附带的两个"渲染与逻辑帧不同步"机制（本次实机核对确认存在）：
   · 失焦不停逻辑：联机模式下 GameInFocus==0 只 Sleep(10)，Sort/Logic/校验值全部照跑，
     而渲染全跳（0x55D895、0x55E204）——这是最现实的触发条件（Alt-Tab/切窗口）。
   · 一帧多渲：联机模式帧尾限速器 sub_55E160 会在剩余帧预算内反复渲染（0x55E271），
     因此渲染回调里的"累加型/非幂等"写法会在同一逻辑帧内被执行多次。
   （另有 dword_A8EDA0!=0 的挂起动作帧、以及 DoList → Networking_RespondToEvent 的帧中渲染路径。）
